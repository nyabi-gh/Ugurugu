# M5 분해: 제품 UI·복구·출력 (2026-10-09)

M5 종료 조건(계획 11절): 긴 작업 세션·강제 종료·export·IME/접근성 통과. 이를 다음 네 가지로 확인한다.

- [scope.md](scope.md) 3절의 M5 행(GIF·Animated WebP·JPEG, 색 기록·브러시 프리셋 새 형식, 자동복구, KR/EN/JP·단축키·색 설정, 도킹, UI Automation·키보드 전용 조작, 픽셀 모드, 2.x `.ugu` 가져오기)이 앱에서 동작한다. 터치는 보류(장치 없음, 2절 9)다.
- 강제 종료(프로세스 kill) 뒤 다시 실행하면 마지막 자동복구 시점까지의 작업을 되찾고, 다른 세션의 복구본을 지우거나 덮지 않는다(계획 8.2절).
- 내보낸 GIF·WebP·JPEG·PNG를 다시 디코드하면 같은 계획으로 그린 프레임과 맞고, 내보내는 동안 편집·취소가 되며, 취소·실패가 최종 경로에 부분 파일을 남기지 않는다(계획 9절).
- 긴 작업 세션 시험(자동 입력으로 획·편집·저장·내보내기·undo를 오래 반복)에서 메모리가 계속 늘지 않고 지연 목표를 유지하며, IME(ko·ja)와 `uia_probe.ps1`을 다시 통과한다.

범위는 scope.md 3절의 M5 행, M4에서 넘긴 것([m4-plan.md](m4-plan.md) 7절), M4 머지 뒤 측정에서 나온 것([m0-evidence.md](m0-evidence.md) 13절 "열기·저장·시작")이다. 2.2.13 동작은 C++ 소스에서 확인했다(각 행에 파일, 경로는 `src/` 아래).

## 3. 측정에서 시작하는 항목

### 시작 첫 프레임 0.52초 (첫 관찰, 2026-10-09)

M4 이후 Release 빌드(`target/release/ugurugu.exe`)를 `UGURUGU_LOG=debug`로 한 번 띄워 로그 시각만 봤다. 프로세스 시작 시각은 PowerShell `Start-Process` 직전 값이라 수십 ms 부정확하다.

| 구간 | 시간 |
|---|---|
| 실행 → GPU 어댑터 선택 로그 | 약 0.42s (창 표시 26ms 포함) |
| 어댑터 선택 → swapchain 생성 | 80ms |
| swapchain → 첫 캔버스 업로드 | 30ms |

대부분이 어댑터 선택 전, 곧 wgpu `Instance` 만들기와 `request_adapter`(DX12 장치 두 개를 모두 여는지, DXC를 읽는지)에 있다. M5-2에서 구간을 더 나눈다. (M5-2에서 나눴다: 어댑터 4개의 드라이버를 모두 올리는 비용이다. 진행 기록과 m0-evidence 14절.) 창이 없어도 잴 수 있는 구간(인스턴스·어댑터·장치)은 headless 도구로 먼저 잰다.

### 저장 중 render 스레드 CPU

(M5-1에서 원인을 찾아 고쳤다. 진행 기록과 m0-evidence 14절.) 저장을 시작할 때 render 스레드는 `apply_pending`과 revision별로 캐시한 문서 사본(`Canvas::snapshot`)만 한다. 그래서 p95 5.3~6.5ms의 원인이 저장 자체인지, 측정 앞의 수정 획(pen-up·썸네일)이 같은 구간에 들어간 것인지부터 나눈다. 수정 없이 저장한 ④도 5.3ms이므로 뒤쪽만은 아니다. 먼저 단계별 span 계측을 넣고 headless로 문서 사본 시간을 잰 뒤, GUI 측정으로 확인한다.
