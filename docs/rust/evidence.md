# 3.0 측정 근거

지금 코드의 설계·상수·결정이 기대는 측정만 모았다. 실패한 시도, 이후 측정으로 대체된 결과, Sandbox 회차별 재시도, 진행 기록은 뺐다. 전체 기록(옛 `m0-evidence.md`, `m2`~`m6-plan.md`, `m0-close.md`)은 커밋 `70f9454`에 있다.

각 절은 질문(무엇을 확인하려 했나), 방법, 결과, 결론과 코드 위치 순서다. 숫자는 따로 적지 않으면 Release 빌드, ms, p50 / p95다.

**환경:** Windows 11 Pro, RTX 5080, Intel Core Ultra 7 270K Plus(P코어 8 + E코어 16, 24 논리 코어), 31.3GiB, 주 모니터 3840×2160 150% 160Hz. 창은 2560×1600 또는 최대화. 2.2.13은 `6c96784` 트리 Release(Qt 6.11.2)다.

fixture ①~⑤의 구성은 2절이다.

## 1. 측정 방법과 함정

**질문:** 두 앱을 같은 조건으로 재려면 무엇을 지켜야 하나.

**입력→표시 (`tools/latency-probe`):** PresentMon 2.6.0(관리자 권한)을 앱보다 먼저 시작하고, 주 버튼을 누른 채 캔버스 가운데 나선 획을 `SendInput`으로 한 칸씩 늘린다(칸 사이 15~40ms 무작위, vsync 위상과 상관 제거). 칸마다 다음 입력 전의 첫 present가 응답이고, 지연은 `SendInput` 직전 QPC부터 `TimeInQPC + MsUntilDisplayed`(scanout 시작, 패널 응답 제외)까지다. 앱이 유휴 중 present하지 않아야 성립한다(두 앱 모두 유휴 5초 0회. 2.2.13은 재생이 켜진 채 시작하므로 `--key P`). 보통 `--steps 100 --warmup 150 --window max`, 문서를 연 상태는 `--document`(앞 200칸 버림), 앱 출력은 `--app-log`.

반드시 지킬 것:

- **PresentMon `--no_track_input`.** 기본 입력 추적은 대상의 지연을 늘린다(p50 11.7 → 18.0ms).
- **`--warmup 150`.** DWM은 창 배치가 바뀐 뒤 앱이 한동안 present해야 Independent Flip으로 올린다(5절). 워밍업 없는 M0 첫 비교는 틀린 결론("Rust가 1ms 느림")을 냈다.
- **`misses`가 0이 아닌 실행은 버린다**(가끔 실행 전체 기록이 1~3프레임뿐, 원인 미확정). 워밍업 뒤에도 Composed: Flip으로 끝난 실행도 버리고 다시 잰다.
- **계속 그리는 다른 창을 최소화한다.** 다른 창이 하드웨어 오버레이 평면을 쓰면 우리 창은 DWM 합성에 남고 PresentMon이 그 프레임을 기록하지 못한다. 측정 전에 시스템 전체를 5초 기록해 dwm.exe 말고 그리는 프로세스가 없는지 본다.
- **모니터 주사율을 확인한다.** 주 모니터가 모르는 사이 60Hz로 바뀌어 기준선이 한 프레임(present → 표시 5.2 → 9~10ms) 느렸던 적이 있다. 이 문서의 지연 값은 모두 160Hz다(M0 값도 PresentMon 기록의 갱신 간격으로 160Hz임을 확인).
- **입력은 `SendInput`(또는 `mouse_event` 절대 이동).** `SetCursorPos`는 pointer 프레임을 만들지 않는다.
- **앱 stdout 파이프를 끝까지 읽는다.** 막힌 파이프가 렌더 스레드를 막았다. 앱 로그는 비차단 writer(`tracing-appender`)다.
- Desktop Duplication은 앱을 Composed Flip으로 바꾸므로 쓰지 않는다.

**교차 검증:** `ugu_render::present::Presenter`는 `GetLastPresentCount`·`GetFrameStatistics`의 `SyncQPCTime`을 표시 시각으로 쓴다. PresentMon과 프레임 단위로 짝지으면(4회) DXGI − PresentMon 중앙값 −0.02~0.01ms, p95 2.0~2.5ms, 최대 3.0ms로, 같거나 조금 늦게(보수적으로) 보고한다.

**UI 스레드 일 (`tools/baseline_probe.py stroke|save|open|cancel|memory|playback|export`):** 2.2.13은 창 스레드, 3.0은 `--thread render`. CPU는 `QueryThreadCycleTime` 차이 ÷ 보정 클럭(약 3.6GHz)이라 대기는 빠지고 그리기는 들어간다(2.2.13은 초당 약 4.8ms 쓰는 타이머의 바닥값이 있음). span은 입력부터 그 스레드가 처음 2ms 넘게 쉬기 전까지이며, 2ms 안에 붙는 다른 일도 합쳐 센다(18절). 3.0은 열자마자 재생하므로 `--no-play-key`. 도구는 앱을 정상 종료하므로 2.2.13 설정(마지막 도구)을 바꾸는 측정 뒤에는 되돌린다(채우기 클릭 측정이 뒤 측정을 오염시킨 적 있음). 3.0 `ReplaceFileW`의 교체 순간 경로가 잠깐 비는 것은 "아직 저장 중"으로 본다.

**격리:** 3.0은 `UGURUGU_SETTINGS_PATH`·`UGURUGU_RECOVERY_PATH`·`UGURUGU_LOG_PATH`로 시험마다 설정·복구·로그를 따로 둔다(`latency-probe`는 스스로 넣음). 2.2.13은 `UGURUGU_INSTANCE_LOCK_PATH`·`UGURUGU_RECOVERY_PATH`로 설치본과 나누고 PATH에 Qt `bin`과 `velopack_libc.dll` 폴더가 필요하다. 진단 키는 `UGURUGU_DIAGNOSTICS=1`, WARP 강제는 `UGURUGU_ADAPTER=warp`.

**작업자 수:** 앱 기본은 코어 수 − 1(이 PC 23, `apps/ugurugu/src/cache.rs`). 벤치마크는 더 작은 PC처럼 `UGU_WORKER_THREADS=8`(headless `ugu-doc render <file> 8`)을 기준으로 재고, 필요하면 기본값도 잰다.

**도구:** headless는 `tools/ugu-doc`(`fixture`, `many`, `bench`, `render <file> [threads [tile]]`, `layers`, `pen-only`, `reframe`, `sparse`, `moves`, `fills`, `digest`(모든 프레임 1/1·1/2·1/4 SHA-256), `compare`, `import`, `insert`, `strokes`, `gif`, `webp`)와 `tools/render-bench`. GUI는 `startup_probe.py`, `session_probe.py`, `kill_probe.py`, `ime_probe.py`, `display_scale.py`, `uia_probe.ps1`, `tools/sandbox/*.ps1`. 이름만 나오는 `selbench`·`membench`·`glancebench`·`tdr_test.py`·`up_probe.py`·`mem_probe.py`·`play_probe.py`와 3.0 재생·채우기 클릭 측정 도구는 scratchpad 도구라 저장소에 없다.

## 5. 프레임 순서와 창 전체 swapchain 하나

**질문:** 입력→present를 줄이려면 프레임을 어떤 순서로 돌려야 하나. 캔버스용 별도 swapchain이 필요한가.

**방법:** 약 2ms 간격 연속 이동에서 앱 지표(입력 → present 반환), 이어서 1절의 PresentMon 측정.

**결과:** 입력을 모은 뒤 swapchain 획득에서 vsync를 기다리는 순서는 Fifo·Fifo + latency 1·Mailbox 모두 p50 약 32ms였다(Immediate만 0.6ms, tearing이라 제품 설정 아님). 아래 순서로 바꾸자 약 6ms가 됐다.

Independent Flip 승격: 두 앱 모두 처음에는 Composed였다가 한 번 승격된 뒤 내려가지 않는다. 2.2.13은 시작 후 약 2.25초(재생 중이라 측정 전에 끝남), 3.0은 창 배치가 바뀐 뒤 약 80번 present하고 승격된다. 워밍업 150칸 뒤에는 기본·최대화·둥근 모서리 끔·자식 창 swapchain 모두 100% Independent Flip이고, 자식 창 swapchain(p50 5.82~6.39 / p95 8.43~9.12ms)은 창 전체 swapchain(p50 5.89~6.40 / p95 8.47~9.02ms, 같은 날 2.2.13 9.62~10.89 / 12.88~13.43ms)과 차이가 없다.

**결론과 코드** (`crates/ugu-render/src/present.rs`, `apps/ugurugu/src/render.rs`):

- 순서: 메시지 대기 → frame-latency waitable 신호 → 그동안 쌓인 입력 다시 수집 → egui 실행·tessellate → 획득(막히지 않음) → 렌더 → present. wgpu DX12 `Dx12UseFrameLatencyWaitableObject::DontWait`로 wgpu 내부 대기를 끄고 앱이 핸들을 직접 기다린다. 최대 frame latency 1. egui-wgpu `Painter`는 획득을 내부에서 하므로 쓰지 않는다.
- UI 스레드는 winit 루프와 포인터 subclass만, render 스레드가 GPU·egui·캔버스를 소유한다. instance·surface는 창 핸들을 꺼낼 수 있는 UI 스레드에서 만든다. DXGI가 swapchain 작업 중 창 스레드로 메시지를 보낼 수 있으므로 UI 스레드는 render 스레드를 막고 기다리지 않고 종료 통지(`EventLoopProxy`)를 받아 끝낸다.
- 표시 통계를 읽는 일만으로는 다시 그리지 않는다.
- **ADR:** 캔버스는 창 전체 swapchain 하나에 그리고 그 위에 egui를 그린다. 자식 창 swapchain은 지연 이득이 없고 egui 팝업이 가려지는 airspace 문제만 생긴다. 창 모서리도 그대로 둔다.
- 4K 최대화 창(3840×2059)도 입력→표시가 같다(p50 5.81~5.85 / p95 8.87~9.05ms). 캔버스는 바뀐 영역만 올린다.

## 8. 렌더러: Vello CPU, SSE4.2 고정, GPU 렌더 보류

**질문:** 문서 렌더러로 tiny-skia, Vello CPU, Vello GPU 중 무엇을 쓰나. CPU마다 픽셀이 달라지지 않나.

**방법:** `tools/render-bench`. 같은 결정적 문서(2048², 5레이어 Normal·Multiply·Screen·Overlay와 클리핑 그룹 1개, 2,000획 × 100점: 펜 50%, 필압 30%, 에어브러시 20%, 모두 반투명)를 같은 외곽선으로 그린다. 단계: 레이어 래스터화 30프레임, 합성, 선택 변형(12°·1.15배, bilinear) 10회, 실시간 획 한 칸 500회. 렌더러마다 프로세스 하나. 재현: `render-bench run --renderer tiny-skia|vello|vello-mt[=N]|vello-gpu [--simd ...]`, `render-bench diff`.

| 단계 p50 (교대 3회) | tiny-skia | Vello 1스레드 | Vello 8스레드 | Vello GPU |
|---|---|---|---|---|
| 래스터화 (5레이어, 프레임당) | 1,138.8~1,159.2 | 336.2~348.8 | 45.4~48.7 | 230.3~230.8 |
| 합성 | 85.6~85.7 | 55.0~56.1 | 8.0~8.2 | 1.51~1.55 |
| 선택 변형 | 39.3~41.2 | 24.7~25.5 | 2.7~2.9 | 0.45~0.52 |
| 실시간 획 한 칸 | 0.006~0.007 | 0.003 | 0.114~0.131 | 0.33~0.35 |
| peak working set (MiB) | 208.7 | 211.0~211.4 | 222.4~240.5 | 328~330 (private 779) |

정확성(2048²): tiny-skia 대 Vello 합성 평균 채널 차 0.85, 차 > 8 픽셀 2.9%. 차이는 획 가장자리 AA 방식과 반투명 반올림에만 있다. Vello 1·8스레드 결과는 바이트까지 같다. Vello GPU 대 CPU 합성은 평균 0.61, 최대 20.

**SIMD 수준:** SSE2와 SSE4.2는 모든 단계에서 바이트까지 같다. AVX2는 방사형 그라디언트의 `mul_add`가 FMA(반올림 1회)라 합성 20픽셀(±2) 등이 다르다. SSE 경로는 제조사마다 결과가 다른 근사 명령(`rcpps`·`rsqrtps`)을 쓰지 않는다. 속도(교대 3회 p50): SSE4.2는 AVX2보다 1스레드 래스터화가 약 3% 느리고(351~358 대 341~347ms) 합성은 25~35% 빠르다(1스레드 41.8~43.0 대 55.4~56.9, 8스레드 5.2~5.5 대 8.0~8.1ms).

**결론과 코드:**

- Vello CPU(`vello_cpu` =0.3.0, `u8_pipeline`). 1스레드에서도 tiny-skia보다 래스터화 3.3배, 8스레드에서 약 24배.
- 문서 렌더러는 SSE4.2로 고정한다(`crates/ugu-render/src/raster.rs` `document_level`, Windows 11 24H2부터 필수). 없으면 같은 결과를 내는 SSE2. 다른 제조사 CPU에서 직접 비교한 것은 아니다.
- Vello 다중 스레드 context는 작은 작업에 분배 비용(약 0.1ms)이 있어 실시간 획은 1스레드, 전체 다시 그리기는 다중 스레드로 나눈다.
- Vello GPU는 경로 전처리를 CPU 한 스레드에서 해 래스터화가 5배 느리고, 실시간 획은 제출·대기 비용으로 100배 느리다. 보류한다. 합성·변형을 GPU로 옮기는 것은 수 ms 단위라 필요하면 표시 경로(wgpu)에서 한다.

## 14. 작업자 수와 레이어 배분

**질문:** 레이어를 작업자에게 어떻게 나누나. 작업자가 많은데 왜 느렸나.

**방법:** headless `ugu-doc render <file> <threads>`, 2회째 이후 60프레임 p50.

**레이어 안을 나눌 가치 (② 8스레드):** 레이어 하나를 혼자 그린 시간 15.4~18.6ms, 합 약 240ms. 레이어 통째로 8스레드에 나누면 두 바퀴 34.2~35.0ms, 완벽한 하한 30.0~30.1ms. 레이어를 띠로 나누면 띠마다 경로 인코딩(레이어 시간의 약 40%)을 다시 해 실제 이득은 5ms보다 작다. 그래서 레이어 안은 나누지 않는다.

**작업자가 많을 때:** 앱 기본 23에서 ②가 8보다 느렸다(8스레드 42.1, 16스레드 53.4, 23스레드 56.9ms). 코어 종류가 아니다(② 1스레드 P코어 339.9 / E코어 333.4ms). 원인은 "레이어가 스레드보다 적으면 하나씩 모든 스레드로" 규칙이다. Vello는 레이어의 경로 인코딩을 한 스레드에서 하므로 그 시간이 레이어 수만큼 쌓인다.

레이어를 각자 한 스레드에서 한꺼번에(c=T) 그리면 ② / 23은 67.5 → 31.4ms로 좋아지지만 ③ / 23(28.7 → 36.1)과 ⑤ / 23(71.6 → 124.4)은 나빠진다. c개 레이어를 동시에 그리고 스레드를 T/c개씩 주면 c=4에서 ② / 23 32.8, ③ / 23 15.6, ⑤ / 23 59.5ms로 모두 좋아진다. 언제나 c=4이면 8스레드 ②가 7% 느려진다(레이어가 스레드보다 많으면 레이어마다 한 스레드가 가장 낫다).

|---|---|---|---|
| ② 14레이어 | 50.6/48.0 → 46.9/48.6 | 54.6/55.2 → 33.1/32.2 | 61.2/67.8 → 31.7/33.7 |

**결론과 코드** (`crates/ugu-render/src/document.rs` `draw_at_once`, `AT_ONCE`): 레이어가 스레드 이상이면 한 레이어에 한 스레드. 적으면 최대 4개를 동시에, 남는 스레드까지 고르게 나눠서(23이면 6·6·6·5). 실행이 끊기는 레이어(15절)는 그 앞에 모든 스레드로 그린다. 느려진 경우는 없고, `ugu-doc digest`가 1·3·8·23스레드 28조합에서 바꾸기 전과 같다(Vello는 스레드 수와 무관하게 같은 바이트).

## 15. 선택 이동이 쌓인 레이어

**질문:** 소수 픽셀 전체 선택 이동이 쌓인 레이어(긴 세션, 26절)가 왜 프레임마다 수 초인가.

**방법:** `ugu-doc moves <in> <out> N 48.19 32.13`(fixture ② 맨 위 레이어에 "불투명 획 3개 → 전체 선택 → smooth 이동" N번), headless 8스레드. N 0 / 25 / 50에서 51.0 / 623.8 / 1197.2ms, 이동 하나 약 23ms. 레이어마다 1스레드 context로 그리므로 이동 레이어가 한 스레드에서 혼자 돈다.

이동 하나의 단계(2048², 12회 p50, 1스레드 / 8스레드 context): 앞 결과를 바탕에 복사 3.70 / 1.03, 마스크 자리 잘라내기 3.46 / 0.79, 소수 이동 샘플링(`Medium`) 13.57 / 2.60, 정수 이동(`Low`) 3.38 / 1.04, 실행 전체 19.23 / 3.33ms. Vello 0.3의 u8 bilinear는 이미 SIMD 정수 산술이고 위치를 f32로 계산해 평행 이동이라도 가중치가 픽셀마다 같지 않으므로, 상수 가중치 구현은 바이트가 같을 수 없어 하지 않았다. 정수 이동은 이미 바탕 복사와 같은 비용이다.

| N (headless 8스레드, 교대) | 바꾸기 전 | 다중 스레드로 먼저 | + 덮는 이동 건너뛰기 |
|---|---|---|---|
| 0 | 41.9 | 41.4~41.9 | 41.5 |
| 177 | 4109.8~4134.2 | 546.5~601.3 | 397.8~421.2 |

앱(창 2560×1600, 이동 177개): 작업자 8에서 재생 프레임 3417 → 415ms, 첫 바퀴 30프레임 "30초에 8프레임" → 12.4초. 작업자 23에서는 레이어가 스레드보다 적어 이미 다중 스레드였으므로 건너뛰기만 들어 약 360 → 280ms. 그리는 동안 render 스레드 CPU는 그대로(이동 p50 1.71, pen-up 5.44ms). 처음 편집 분할 3578 → 588ms.

**결론과 코드** (`crates/ugu-render/src/document.rs` `draws_in_runs`):

1. 선택 이동·리샘플이 있는 레이어는 다중 스레드 context로 먼저 하나씩 그린다.
2. 원본을 남기지 않는 이동의 마스크가 한 직사각형이고 실행 영역 전체를 덮으면 바탕 복사와 잘라내기를 건너뛴다(시험 `a_move_that_cuts_away_everything_draws_as_one_that_does_not`).

`ugu-doc digest`가 이동 0·25·177개, 가장자리가 걸치는 작은 문서, `.ugu` 가져오기 fixture, ⑤, 리샘플, 채우기 22조합에서 바꾸기 전과 같다. 같은 구성의 2.2.13 정확 렌더(16307ms)의 약 1/40이다. 소수 이동을 이어 합치면 리샘플 횟수가 줄어 픽셀이 바뀌므로 하지 않는다. 편집 분할과 예산 초과 스트리밍 렌더는 이 순서를 쓰지 않고, 건너뛰기(2)는 모든 경로에 들어간다.

## 16. 픽셀 획

**질문:** 픽셀 연필(행 구간)의 렌더 비용이 잉크 펜과 비슷한가.

**방법:** 1024², 한 레이어 획 200개(400점, 약 980px 물결), 우글거림 2.0, 같은 점·굵기, 전체 렌더 10프레임 중앙값.

잉크 펜 → 픽셀 연필: 굵기 1 1스레드 32.6 → 23.7, 8스레드 7.1 → 6.0. 굵기 4 1스레드 33.8 → 28.5. 굵기 12 1스레드 24.8 → 38.2, 8스레드 5.1 → 7.5ms. 칸 계산은 굵기와 무관하게 약 12.7ms(구간 약 7.7만). 굵기 12의 차이는 Vello가 행마다 바뀌는 계단 경계를 채우는 비용이다. 칸마다 블록 행을 모두 구간으로 만든 처음 구현은 95ms였고, 행마다 마지막 구간을 늘리게 바꿔 38ms가 됐다. 위아래 같은 구간을 사각형으로 합쳐도 사각형이 0.1%만 줄었다.

그리는 중 픽셀 획은 새 점이 마지막 모서리 칸을 되돌릴 수 있어 매번 모든 점에서 칸을 다시 구한다. 3초 빠른 획 끝에서 약 1.5ms/프레임(잉크 펜의 10배 이상)이지만 프레임은 놓치지 않는다. 우글거리는 1px 획의 세 픽셀 뭉침은 무작위 획 300개에서 27/450 → 0/450(우글거림 없는 경로를 만든 뒤 칸마다 옮겨 다시 잇기).

**결론과 코드:** `crates/ugu-render/src/pixel.rs` 하나가 전체 렌더·확정 스탬프·진행 중 획의 칸을 만든다. 굵기 1·4는 잉크 펜 이하라 그대로 둔다.

## 17. 선택 영역 비트 행과 끄는 동안의 변형 (`Glance`)

**질문:** 4096² 선택 연산과 큰 선택을 끄는 동안의 갱신을 빠르게 할 수 있나.

**선택 영역 비트 행:** 캔버스 크기 작업 공간(`ugu_core::selection`의 `Canvas`)을 픽셀당 `bool`(4096²이면 16MiB)에서 `Mask`와 같은 행 단위 비트(2MiB)로 바꿨다. `selbench`, 4096², 1스레드, 15회 최솟값. 결과 비트의 SHA-256 12개가 모두 같다.

**Glance:** 4096² 전체 선택을 끌면 갱신마다 원본 해상도로 편집 레이어 고치기(11~14ms) + 레이어 6개 합성(19~20ms) + 64MB 업로드로 초당 23~27회였다.

## 18. pen-up 지연은 프레임 끝 시각으로 본다

**질문:** ① pen-up span p95가 9~10ms로 목표(8ms)를 넘는 것은 실제 지연인가.

**방법:** `baseline_probe.py stroke`(① 20획, `--thread render --no-play-key`)를 감싸 pen-up마다 render 스레드 일한 시각을 앱 로그(`ugurugu=debug`) 프레임 시각과 맞췄다. 2회.

pen-up CPU p95 4.0~4.4ms, span max 10.9~11.8ms, pen-up 프레임 끝은 입력 뒤 1.9~4.6ms. 예(10.9ms): pen-up 표시 1.4 → 업로드 3.9 → 프레임 끝 4.6 → 건너뛴 프레임 5.8·6.2 → 썸네일 도착 7.6 → 썸네일 프레임 끝 10.6ms. 건너뛴 프레임이 2ms 공백을 이어 썸네일 프레임까지 한 run이 됐다.

**결론:** 40회 모두 pen-up 프레임은 입력 뒤 4.6ms 안에 끝났다. 꼬리는 썸네일 갱신이라는 별개의 일이다. pen-up 지연은 span 대신 앱 로그의 프레임 끝 시각으로 본다. 진행 중 획의 문서 크기 coverage 버퍼는 캔버스가 보관해 다음 획에 넘긴다(`crates/ugu-render/src/live.rs` `into_spare`; ⑤p pen-up CPU 6.27~6.29 → 3.95~4.13ms).

## 19. 메모리 예산

**질문:** 렌더 캐시(재생 프레임 + 레이어 표면) 예산을 얼마로 잡나.

**방법:** 원본 ⑤ 펜 사본, 최대화, 160Hz, 작업자 8, 31.3GiB PC.

- 모든 프레임을 두려면 원본 ⑤ 100%는 약 2.24GiB(프레임 64MiB × 30 = 1.92 + 표면 0.32), 그 밖에 프로그램·표시·작업 메모리 약 500MiB.
- 이 PC는 사용 가능 메모리(14.8GiB)보다 커밋 여유(13.5GiB)가 작아, 다른 프로그램이 메모리를 쓰면 페이징보다 할당 실패가 먼저 온다.
- 2.2.13은 미리보기 캐시를 설치 메모리의 1/16(128MiB~2GiB)으로 잡는다.

| 문서·배율 | 고정 768MiB | PC 메모리 예산 |
|---|---|---|
| 원본 ⑤ 100% | 10.6fps, 266프레임 렌더, 1276MiB | 25.0fps, 30프레임, 2737MiB |
| 원본 ⑤ 화면 맞춤 | 25.0fps, 950MiB | 25.0fps, 949MiB |
| ⑤ 자르기·리사이즈(2688²) 68% | 19.8fps, 190프레임, 1108MiB | 25.0fps, 30프레임, 1312MiB |

다른 프로세스가 10GiB를 쥔 중(사용 가능 4.8, 커밋 여유 3.4GiB): 예산이 약 1.9GiB로 줄어 최대 2047MiB, 12.8fps. 45초 동안 페이지 입력 약 1.6MiB, 출력 약 13MiB, 사용 가능 최소 3080MB.

**결론과 코드** (`apps/ugurugu/src/budget.rs`, `crates/ugu-win/src/memory.rs`): 캐시 예산 = min(설치 메모리 / 4, (min(사용 가능 물리, 커밋 여유) + 캐시가 쥔 것) / 2), 최소 256MiB, Windows가 알려 주지 않으면 3GiB PC의 값. 레이어 표면은 그 절반. 1/4은 16GB급에서 ⑤ 100%가 들게 하는 상한이고(1/8이면 30장 중 26장), 여유의 절반은 다른 프로그램 몫이다. 예산은 재생을 계획할 때(쥔 프레임을 여유로 셈)와 분할을 요청할 때 정해 작업자에게 넘긴다. 작업자가 렌더마다 다시 계산하면 재생 도중 표면 예산이 줄어 단계별 렌더로 바뀔 수 있었다. 1GiB는 통과 기준이 아니다(사용자 결정).

## 21. 앱 재생 메모리: `MemoryHints::MemoryUsage`와 스테이징 버퍼

**질문:** 앱 재생 중 working set이 2.2.13의 1.1~3.1배인 내역과 줄일 수 있는 것.

**방법:** `baseline_probe.py memory --no-play-key --play-seconds 15`, 앱 로그에 재생 프레임·표면 보유량과 프로세스 힙(`HeapSummary`).

- 재생 프레임: 사이클의 30장을 화면 해상도 배수(2048² 또는 1024²)로 쥔다(②~⑤ 480MiB). 재생 중 증가분의 거의 전부이고, 첫 바퀴 뒤 다시 그리지 않는 성능 우선 설계라 둔다.

## 27. IME·글꼴·접근성·키보드

**질문:** 한국어·일본어 IME, 다른 배율, 화면 낭독기, 키보드만으로 쓸 수 있나.

**방법:** `python tools/ime_probe.py <ko|ja> <ugurugu.exe> <출력 폴더> [창 x,y]`가 실제 IME에 `SendInput` 키(한/영·한자 포함)를 보내고 앱 로그의 텍스트·단축키 횟수를 비교한다. 배율은 `python tools/display_scale.py <배율>`(설정 앱과 같은 DisplayConfig 경로). UIA는 `tools/uia_probe.ps1`(PowerShell 5.1 .NET UIA 클라이언트). 키보드는 `apps/ugurugu/src/ui/keyboard.rs`(창 전체를 GPU 없이 돌리고 AccessKit 트리에서 포커스를 읽는 시험).

결과: 한국어 조합 후 Enter "한글", 조합 중 Backspace "안녕하세요", 받침 이동 "값이", 한자 키 "韓". 일본어 "日本語", 문절 변환 "私は学生です", `kanji` 후보 확정("漢字"/"感じ"는 MS IME 학습으로 바뀌어 확정과 누출 없음으로 판정). 글자 칸의 Enter가 캔버스로 0번, 캔버스 클릭 뒤 Ctrl+Z는 캔버스로 1번. 125%·150%·200%, 100% 보조 모니터에서 같고 후보창이 같은 상대 위치에 뜬다. 최근 재시험(M5-15 뒤, 창 2400×2050)에서 문자 도구 '우슬'·'文字'도 적용됐다. 적용할 변형이 없으면 Enter는 캔버스 동작이 아니므로 캔버스 Enter는 0이다.

**고친 것과 규칙:**

- 캔버스 획이 시작되면 텍스트 포커스를 놓는다(`stop_text_input`, `apps/ugurugu/src/render.rs`). 포인터 라우터가 캔버스 입력을 egui에 보내지 않아 텍스트 칸이 포커스를 쥐고 Enter·Ctrl+Z를 가져갔다.
- 단축키는 키 이벤트 자신의 modifier로 판정한다. Ctrl·Z 누름·떼기가 한 프레임에 오면 프레임 끝 modifier는 이미 "없음"이다.
- 후보창 위치는 egui-winit이 넘기는 칸 전체(`ime.rect`) 대신 커서 영역(`ime.cursor_rect`)이다(`render.rs`).
- 글꼴: M0에서 시스템 fallback(맑은 고딕 + Yu Gothic)을 섞으면 epaint가 행 높이(line gap 포함) 차이의 절반만큼 세로를 맞춰 Yu Gothic 글자가 약 4.7pt 떴다. 제품은 한·일·한자를 모두 담은 글꼴 하나(`resources/fonts/PretendardJP-Medium.otf`, `apps/ugurugu/src/theme.rs`)를 번들해 섞지 않는다. 다른 글꼴을 fallback으로 더하면 기준선 차이를 재서 맞춰야 한다.
- 일본어 IME가 안 열린 첫 시도는 PC에 일본어 기본 입력 기능(`Language.Basic~~~ja-JP~0.0.1.0`, 시스템 사전)이 없었기 때문이다(`dism /online /add-capability`로 설치). probe는 창 스레드의 HKL로 전환을 확인하고 끝나면 원래 입력 언어로 되돌린다.

**UIA:** AccessKit 어댑터는 창을 소유한 UI 스레드에 두고, render 스레드 egui의 트리 갱신과 낭독기 요청을 전달한다. 어댑터는 창이 처음 보이기 전에 붙어야 해 창을 숨긴 채 만든다. 설치는 AccessKit → 포인터 subclass, 해제는 반대 순서. 이 변경 뒤 입력→표시는 교대 비교에서 차이 없음. 최근 결과: 요소 101개, 이름 없는 컨트롤 0, F2 이름 바꾸기, Add layer Invoke, F10·Alt 단독·Alt+E·설정 포커스 반환·도크 경계 통과. egui TextEdit는 `ValuePattern.SetValue`를 받지 않는다(egui 한계, 키보드 입력은 됨). Narrator 청취 검증은 범위 밖(사용자 결정).

**키보드:** Tab 순회 68곳 모두 이름 있음. 메뉴 F10·Alt+F·E·V·T·W·제목에서 ↓/Enter/Space, 열린 동안 ←·→. 메뉴 항목 실행 뒤 닫힘. 대화상자는 첫 컨트롤에 포커스, Esc 한 번에 닫히고 포커스는 연 메뉴 제목으로. 목록은 고르면 닫힘. 저장 확인 S·N·Esc·Enter(2.2.13과 같음). 도크 경계 ←·→ 16px. 색은 `#AARRGGBB` 칸(2.2.13 휠도 포인터 전용). 글자 칸의 Esc는 칸만 벗어난다. 캔버스에 그리기는 2.2.13처럼 포인터 입력이다.

## 28. 장치 손실·TDR·WARP·오프라인

**질문:** GPU 장치가 사라져도 문서와 화면이 살아나나. GPU가 없으면 어떻게 되나.

**방법:** `UGURUGU_DIAGNOSTICS=1`의 F9(`ID3D12Device5::RemoveDevice`, 앱 장치만 제거)와, 관리자 `dxcap -forcetdr`로 일으킨 실제 드라이버 리셋(②p 최대화, 유휴·획 도중·재생 중·PNG 내보내기 직후·저장, `tdr_test.py`).

**결과:** RemoveDevice 3회는 캔버스 화소 동일, 복구 0.4~0.9초. 실제 TDR 12회는 모두 복구했고, 장치 손실부터 마지막 교체까지 1.8~4.3초(새 장치 열기 약 1.5~2초). 유휴 화면은 썸네일까지 화소 동일, 누른 채 리셋해도 획이 이어지고(저장 연산 1680 → 1681), 재생이 이어지고, 내보내기·저장이 성공했다.

| WARP 입력→표시 (교대 2회, 100칸) | 표시 방식 | 입력→present | 입력→표시 p50 / p95 | 응답 없는 칸 |
|---|---|---|---|---|
| 2538×1549 | Composed Flip | 15.82~15.89 / 20.43~24.37 | 59.04~59.10 / 63.60~67.59 | 20~21 |
| 3840×2059 | Composed Flip | 17.63~20.39 / 25.35~25.54 | 73.28~75.89 / 81.05~81.18 | 32 |

WARP는 렌더가 입력 간격을 못 따라가 20~32%의 칸이 다음 프레임에 합쳐 보인다(입력은 잃지 않음).

**결론과 코드** (`crates/ugu-render/src/gpu.rs`, `apps/ugurugu/src/render.rs`):

- `Gpu`가 장치 손실 콜백과 `GetDeviceRemovedReason`으로 손실을 알아채고, render 스레드가 장치·swapchain·egui 렌더러·캔버스 텍스처를 새로 만든다. 새 장치에는 egui 글꼴 아틀라스 전체와 레이어 썸네일 텍스처를 다시 올린다.
- egui-wgpu 0.36.2는 제거된 장치에서 `Renderer::update_buffers`가 panic한다. 프레임의 GPU 부분을 `catch_unwind`로 감싸고 **장치가 손실된 경우에만** 흡수한다(그 프레임 자원은 모두 버림). 장치가 멀쩡한 panic은 다시 던진다.
- 옛 swapchain이 창을 쥐고 있으면 새 장치의 `ResizeBuffers`가 실패한다. 옛 장치·surface를 먼저 버리고 UI 스레드에 새 surface를 요청한다(교착 없음).
- 실제 TDR 뒤에는 이전 DXGI factory가 현재 것이 아니라 흰 창이 남았다. 복구마다 새 wgpu `Instance`와 surface를 만든다.
- 리셋 직후 만든 swapchain은 waitable이 다시 신호하지 않아 한 프레임 뒤 멈추는 경우가 있다(복구 전 5초 기다리면 없음). 복구 뒤 프레임 대기가 1초 넘게 안 풀리면 표시를 다시 만든다(최대 3번, 둘째 프레임이 지나가면 확인 끝). TDR 12회 중 9회에서 다시 만들었고 모두 한 번에 회복했다.
- WARP: `Gpu::is_software`. 하드웨어 어댑터가 창을 보이지 못할 때만 WARP로 열고 안내를 띄운다(`request_adapter`).
- 오프라인: 시작 경로에 네트워크가 없다. 업데이트 확인(Velopack)은 시작을 막지 않는 비동기 작업이고 실패는 안내만 한다(32절).

## 32. 설치·업데이트·제거 (Windows Sandbox)

**질문:** 깨끗한 Windows에서 설치·연결·업데이트·제거가 되나. 2.2.13과 함께 설치해도 서로 건드리지 않나.

**방법:** `tools/sandbox/prepare.ps1`이 같은 exe를 작업 공간 판 설치본과 다음 patch 판 로컬 피드로 묶고(`in\versions.json`, 2026-10-13 전에는 3.0.0·3.0.1로 고정이라 판을 올리면 첫 단계부터 실패했다)(`-Scenario alongside`, `-Only`로 단계 선택), `accept.ps1`·`alongside.ps1`이 게스트(10.0.26100, 네트워크 끔·vGPU 끔)에서 돈다. 시험 문서는 `ugu-doc fixture 1`. 실패 업데이트는 피드 사본의 nupkg 1바이트를 0xFF와 XOR한 것이다.

**깨끗한 설치 (최종 회차 9단계 모두 통과):** 설치(`%LOCALAPPDATA%\Ugurugu3`, 앱 목록 'Ugurugu 3', 바로 가기 둘) → 실행(RTX 5080, 원격 세션 `TerminalServerSession` True) → `UGURUGU_ADAPTER=warp` 실행(Microsoft Basic Render Driver) → 한글 경로에서 연결로 열기(`document opened ms=1.30`) → 다운로드 실패 업데이트(체크섬 불일치 안내, 제목 `*`·3.0.0 유지) → 저장 안 한 변경이 있을 때 3.0.1 업데이트(질문 → 취소 → 앱 유지 → 다시 질문 → 저장 안 함 → 3.0.1로 다시 시작) → 오프라인 확인(안내만) → 제거(남음: `Local\Ugurugu Data`, `Roaming\Ugurugu`) → 표준 사용자 계정으로 설치·실행·제거. Setup 매니페스트는 `asInvoker`.

**2.2.13과 함께 (8단계 모두 통과):** 2.2.13 설치 → 그 옆에 3.0 설치(2.2.13 41개 파일 그대로, 앱 목록 둘) → 3.0.1 업데이트 → 3.0에 복구할 작업 남김 → 그동안 2.2.13 실행 → 2.2.13 제거 → 2.2.13 다시 설치 → 3.0 제거. 3.0 복구 3·로그 4·설정이 끝까지 유지된다.

**결론과 코드:**

- 2.2.13의 Velopack 설치 루트가 `%LOCALAPPDATA%\Ugurugu`(`--packId Ugurugu`)이고 제거가 루트를 통째로 지워, 그 안에 있던 3.0 지역 데이터(복구·로그)가 사라졌다(첫 회차 FAIL). 3.0 지역 데이터는 `%LOCALAPPDATA%\Ugurugu Data\3`이다(`apps/ugurugu/src/logs.rs` `local_data`). 공백이 든 이름은 NuGet package id가 될 수 없어(`vpk pack`이 거부) 어느 Velopack 설치 루트도 될 수 없다.
- 이때는 업데이트 확인을 기록한 뒤 6시간 안의 시작은 자동 확인을 하지 않았다(2.2.13 `recordAutomaticCheck`와 같은 규칙). 3.3.2부터는 시작마다 확인한다(decisions.md 10절). 시험 단계마다 `UGURUGU_SETTINGS_PATH`로 설정을 따로 둔다.
- Sandbox는 `<VGpu>Disable</VGpu>`에도 호스트 GPU를 보여 준다. GPU가 정말 없을 때의 자연 WARP 경로는 CI smoke가 확인한다.
- 같은 PC에서 Sandbox는 하나만 뜬다. 앞 회차 Sandbox가 남아 있으면 시작되지 않는다.

## 35. main push의 CI 범위

**질문:** 문서만 바꾼 main push에 CI 12개 작업이 모두 도는 것(실행 38217225548, 19분 41초)을 줄일 수 있나. 릴리스가 검사되지 않은 코드를 내보내지 않게 하려면.

**사실:** `ci.yml`이 PR이 아닌 이벤트를 모두 돌게 둔 것은 의도된 설계였다. 릴리스 워크플로(`release-3.yml`)는 `wait-for-main-ci.sh`로 태그 커밋의 main CI 성공만 본다. main은 `cancel-in-progress`이므로, push 직전 커밋(`event.before`)과 비교하면 코드 push A 직후 문서 push B가 올 때 A가 취소되고 B는 문서만 보고 성공해 A의 코드가 검사 없이 릴리스될 수 있다.

**결정:** main push는 같은 브랜치에서 CI가 성공한 가장 새 조상 커밋(자기 제외)과 비교한다(Actions API, `actions: read`). 그런 커밋이 없거나 API가 실패하면 전부 돈다. `tools/sandbox/*`는 CI가 읽지 않으므로 문서와 같은 묶음이다.

| 가정한 push (로컬 시뮬레이션) | 찾은 기준 | 결과 |
|---|---|---|
| `70f9454` (문서) | `d04675f` | 작업 없음(static 외 건너뜀. 이 시뮬레이션 때 있던 translations 작업은 `4df2de2`에서 CI를 3.x Rust 앱만 보게 줄이며 없앴다) |
| `d04675f` (코드) | `cbc8dcd` | rust만 |
| 성공 기록 없는 브랜치 | 없음 | 전부 |

**실제 main push (2026-10-13):** 실행 38346647863(`3aa43f3`, 문서)은 자기와 취소된 `4ec1ad6`(실행 38346368886, workflow 변경)을 건너뛰고 `c192dce`를 기준으로 잡았다. 차이에 `4ec1ad6`의 `.github/workflows/*`가 들어 Rust 작업이 돌았다. 취소된 실행의 변경을 다시 검사하는 경우가 실제로 맞다.

**문서만 바뀐 main push (2026-10-16):** 실행 38848821927(`a8f9a3d`)은 마지막으로 성공한 main CI인 `49b7000`을 기준으로 잡았다(Detect changes 로그 "Last successful CI on main: 49b7000…"). 둘 사이의 차이는 `docs/rust/backlog.md`와 `docs/rust/evidence.md`뿐이라 `rust=false`가 되어 Rust Windows가 skipped이고, Format and release metadata·Detect changes·Quality gate는 success였다.

## 40. 파일을 주고 실행하면 떠 있는 창으로 (`5c18365`)

| 경우 | 결과 |
|---|---|
| 창 없이 4개를 함께 | 창 1개, 나머지 3개는 코드 0으로 끝남. 그 창 로그에 넘겨받음 3번, 문서 열기 4번 |
| 창이 떠 있을 때 이미 연 파일 | 32 ms에 코드 0으로 끝남, 창 1개 그대로 |
| 복구 경로가 다른 실행 | 넘기지 않고 제 창을 엶(창 2개) |

단일 실행으로 바꾼 뒤(2026-10-13, 호스트, 1회): 파일 없이 3개를 함께 실행하면 창 1개(2개는 끝남), 창이 있을 때 파일 없이 실행하면 20 ms에 코드 0으로 끝나고 창 1개, 로그 파일은 창의 것 하나뿐(넘기고 끝나는 실행은 로그를 만들지 않음).

단위 시험: `ugu_win::instance::tests`(같은 키에만 감, 파일 없는 실행도 감, 받는 쪽이 없으면 `false`, 뮤텍스 차례), `files::tests::a_document_asked_for_twice_while_read_opens_one_tab`(읽는 동안 같은 파일을 두 번 받으면 탭 하나, 둘 다 답할 때까지 바쁨).

**남은 것:** 창이 앞으로 나오는지(`AllowSetForegroundWindow`·`SetForegroundWindow`)와 최소화된 창 복원은 화면을 봐야 하므로 Sandbox에서 본다. 관리자 권한 창에는 UIPI로 넘기지 못하고 새 창이 뜬다(가설, 시험 안 함).

## 41. 탭 여러 개의 스레드·메모리·바꾸기 시간 (문서 탭 5단계)

**질문:** 탭마다 캐시 작업자가 생기는데, 탭 3개면 스레드·메모리가 얼마나 늘고 숨은 탭이 CPU를 쓰나. 큰 문서로 탭을 바꾸는 데(전체 업로드 `upload_all`) 얼마나 걸리나.

## 48. 캐시 작업자가 멈추거나 panic할 때의 내보내기 (2026-10-13)

**질문:** 렌더가 panic하거나 탭을 닫아 작업자가 끝나면 기다리던 내보내기는 어떻게 되나.

**방법:** `cache::tests`의 두 시험을 고치기 전 `cache.rs`에 넣어 돌림(내보내기를 다른 스레드에서 기다리고 10초 제한). panic은 `i32::MAX` 양쪽에 화소가 있는 mask로 일으킴(조작된 파일이 읽기를 통과하던 모양).

**결과:** 고치기 전에는 둘 다 10초 제한에 걸림(끝나지 않음). 고친 뒤 panic한 내보내기는 그림 없이 끝나고 다음 내보내기는 그림을 받는다(debug·release 모두). 끝난 작업자에 낸 요청은 바로 그림 없음으로 끝난다.

**결론:** 내보내는 탭을 닫았을 때 적어 둔 "실패로 끝남"은 실제로는 "끝나지 않음"이었다. 작업자가 job마다 `catch_unwind`한다. 그 뒤 탭을 닫아도 내보내기가 끝까지 그려지게 바꿨다(`cache::tests::a_closed_tabs_worker_draws_what_an_export_asks_then_ends`, decisions.md 7절).

## 52. 복사의 render 스레드 비용 (2026-10-14)

**질문:** 큰 선택을 복사할 때 render 스레드가 얼마나 멈추나.

**방법:** 외부 검토가 만든 시험 crate(앱 소스 `8195424` 복사본 + 공용 crate, 저장소에 두지 않음)의 `review_copy_cost_on_fixture4_with_and_without_split`을 release, `UGU_WORKER_THREADS=8`로 다시 돌림. fixture ④(2048², 레이어 1, 획 20,000) 전체 선택에서 `Canvas::copy` 진입부터 반환까지 10회씩. OS 클립보드 쓰기는 빼고, split 없음과 split을 받은 뒤를 비교.

**고친 뒤 (2026-10-14):** 복사는 render 스레드에서 연산 사본(`Session::copy`)과 문서 snapshot만 만들고, 다른 앱에 줄 그림(현재 레이어의 참조 렌더와 straight RGBA 변환)은 클립보드 스레드가 그 snapshot에서 새 `DocumentRenderer`(작업자와 같은 스레드 수)로 그린다(`CopiedPixels`). 앱 안의 시험 `copy_cost_on_a_large_document`(ignored)를 같은 fixture ④ 전체 선택, release, `UGU_WORKER_THREADS=8`로 바꾸기 전과 뒤에 두 번씩 돌렸다. 바꾸기 전 이 시험의 값은 split 없음 p50 56.6ms·최대 66.8ms, 있음 26.3·27.9ms로 위 표와 같은 크기다.

| 조건 | 바꾸기 전 p50 / 최대 | 바꾼 뒤 p50 / 최대 |
|---|---|---|
| render 스레드, split 없음 | 56.6 / 66.8ms | 3.4~3.6 / 4.5~5.0ms |
| render 스레드, split 있음 | 26.3 / 27.9ms | 3.4~3.5 / 5.4~6.9ms |
| 클립보드 스레드의 그림 | (render 스레드에 포함) | 59.2~59.6 / 60.3~62.9ms |

다른 앱이 그림을 받는 때는 split이 있던 경우 약 35ms 늦어진다(매번 새로 그리므로). 앱 안 붙여넣기는 연산 사본을 바로 쓰므로 영향이 없다. 남은 3.4ms는 연산 사본과 snapshot(문서 복제)으로 보이나 나눠 재지는 않았다(가설).

## 58. 도형 끌기의 프레임 비용 (이슈 #51, 2026-10-15)

**질문:** 도형 도구로 끌 때 미리보기가 마우스보다 늦고 몇 프레임씩 멈춘다(이슈 #51 영상: 40px쯤의 우글거리는 선, 미리보기와 브러시 원 커서가 OS 화살표보다 약 0.3초 뒤처짐).

**원인(코드):** 도형은 포인터 샘플마다 `LiveStroke`를 새로 만들고(외곽선 전체 재표본·우글거림·경계 상자 크기 래스터화) 옛 상자와 새 상자를 합성했다. 합성은 그리는 획이 있으면 한 스레드였다. render 스레드는 큐의 샘플을 하나씩 모두 적용한 뒤 프레임을 그리므로 샘플 하나가 샘플 간격보다 오래 걸리면 샘플이 밀린다.

**방법:** `canvas::tests::shape_drag_frame_cost`(ignored), release, `UGU_WORKER_THREADS=8`. 1920×1080 문서(기본 우글거림), 펜 40px, (100,100)에서 (1800,950)까지 타원을 120프레임에 걸쳐 끈다. 프레임마다 샘플 1개 또는 16개(1000Hz 마우스, 60Hz 화면)를 적용하고 `take_upload`까지 잰다. 같은 끌기를 펜으로 그린 값을 함께 본다. 24코어 PC, 합성 스레드는 최대 8.

**결과:** 바꾸기 전에 샘플 하나의 나눔은 큰 타원에서 획 다시 만들기 약 3.8ms, 합성 약 4.3ms였다(임시 계측).

| 경우 | 바꾸기 전 중앙값 / 최대 | 바꾼 뒤 중앙값 / 최대 |
|---|---|---|
| 도형, 샘플 1개/프레임 | 2.72 / 8.46ms | 1.92 / 5.10ms |
| 도형, 샘플 16개/프레임 | 49.50 / 179.87ms | 2.14 / 5.31ms |
| 펜, 샘플 1개/프레임 | 0.05 / 0.19ms | 0.04 / 0.11ms |
| 펜, 샘플 16개/프레임 | 0.57 / 1.06ms | 0.41 / 0.70ms |

**고침:** 도형 끌기는 세션의 점만 바꾸고, 미리보기는 프레임이 화면을 가져갈 때(`Canvas::take_upload`) 한 번 만든다(보이는 것은 마지막 끌기뿐). 그리는 획이 있는 합성도 없는 합성과 같은 기준(65,536화소 넘으면 최대 8스레드)으로 줄을 나눈다. 1개/프레임의 줄어듦은 합성을 나눈 몫이고, 16개/프레임은 샘플마다 하던 일을 프레임에 한 번으로 줄인 몫이다.

**남은 것:** 사용자 PC의 마우스 보고율과 CPU는 모른다. 영상의 0.3초가 샘플 밀림이라는 것은 이 측정과 맞는 가설이고 사용자 PC에서 재지 않았다.

**Windows Sandbox (2026-10-15):** `gui.ps1`의 "A dragged shape keeps up with the pointer"는 화면의 문서를 거의 가득 채우는 타원을 1500번(약 1ms 간격, 1000Hz 마우스처럼) 끈 뒤, 마지막 크기의 오른쪽 끝(12×12px)이 화면에 나올 때까지를 잰다. 3번 반복. 3.2.0(업데이트 피드의 `Ugurugu3-3.2.0-win-x64-full.nupkg`에서 꺼낸 실행 파일)은 281, 219, 1505ms, 고친 빌드(`9b6a9d9`)는 31, 32, 61ms. 같은 실행에서 "Shapes and the round pixel pencil"도 통과했다.

## 59. 둥근 픽셀 연필의 점과 확대율 (이슈 #24, 2026-10-15)

**질문:** 이슈 #24에서 다른 앱의 둥근 픽셀 브러시는 칸이 보이는데 Ugurugu의 둥근 픽셀 연필은 매끈한 원으로 보인다.

**결론:** 칠하는 칸은 같고, 보이는 차이는 확대율이다. 사용자 그림의 Ugurugu 쪽은 100% 아래로 본 것으로 보인다(가설, 사용자에게 확인하지 않음).

## 65. 최근 문서, 가려진 창, 읽기 퍼징과 ZIP 디렉터리 (2026-10-15)

**최근 문서(Jump List):** Windows Sandbox 수용 시험에 "Recent documents on the taskbar"를 더했다. 설치한 앱을 실행 인자로 연 `ugurugu-recent-probe.ugurugu`(셸을 거치지 않음)가 작업 표시줄 단추의 Jump List "최근 항목"에 보이는지 UI Automation과 화면으로 본다. 이 변경의 빌드는 항목이 보였다(앞 단계에서 탐색기로 연 "새 그림"과 함께). 고치기 전 빌드로는 돌리지 않았다. 셸이 실행 인자의 파일을 넣지 않는다는 것은 가설이다.

**가려진 창:** `gui.ps1` "CPU while the window is hidden": 획 하나가 우글거리는 동안 앱 프로세스의 CPU 시간을 5초씩 쟀다. 보일 때 31ms, 최소화 16ms, 최대화한 다른 창 아래 31ms. Sandbox는 vGPU가 꺼져 WARP의 그리기도 앱 CPU에 든다. 실제 GPU의 전력은 재지 않았다.

**ZIP 중앙 디렉터리:** `ugu-doc cd-only <entries>`로 내용 없이 중앙 디렉터리만 있는 ZIP64를 만들고 `ugu-doc readmem`으로 읽었다.

## 77. Sandbox의 UI Automation 시간 초과 (2026-10-16)

**질문:** 시험 스크립트의 `Wait-Until`은 UI Automation 시간 초과를 다시 묻는데, 왜 `FromHandle` 시간 초과 단계가 1초 안에 실패했나(B3-97).

**방법:** 이 PC에 남은 Sandbox 결과(`results.md`, 2026-10-13~16)에서 시간 초과로 실패한 단계를 모았다. Sandbox가 시험을 돌리는 Windows PowerShell 5.1에서 `Marshal.GetExceptionForHR(0x80131505)`의 형식을 보았다. `common.ps1`을 불러 가짜 조건(UI Automation처럼 `ThrowExceptionForHR(0x80131505)`를 두 번 던진 뒤 값을 냄)을 고치기 전과 뒤로 돌렸다.

**결과:** 결과 파일 14개에서 17단계가 모두 `Exception calling "FromHandle" ... "Operation timed out. (Exception from HRESULT: 0x80131505)"`로 실패했다. 그중 "Update that fails to download" 7회는 `Press` → `Find-Element`, 곧 `Wait-Until` 안에서 불렸다. .NET Framework는 0x80131505(COR_E_TIMEOUT)를 `System.Runtime.InteropServices.COMException`으로 바꾸고 메시지도 같은 꼴이다. `Wait-Until`은 가장 안쪽 예외가 `TimeoutException`일 때만 다시 물었으므로 곧바로 다시 던졌다. 가짜 조건은 고치기 전 곧바로 FAIL, 고친 뒤 "pass after retry"(무엇을 두 번 다시 물었는지 남김)였다. 잘못된 창 핸들의 `ElementNotAvailableException`(0x80040201)은 고친 뒤에도 곧바로 실패하고 결과에 형식과 HRESULT가 남는다.

**결론:** `Wait-Until`은 시간 초과를 형식이 아니라 HRESULT로 알아보고, 밖에 있던 `FromHandle` 호출(`Test-Named`, 저장 대화상자 이름, 양파 껍질 단추, `pointer.ps1`의 `Get-Value`·`Set-Toggle`)도 그 안에서 부른다. 다시 물어 통과한 단계는 "pass after retry"로 남아, 창이 시작 직후 답하지 않는 앱 쪽 원인(B3-97)을 가리지 않는다.

**Sandbox:** 고친 스크립트로 `gui.ps1 -Only`의 "Save dialog with another extension typed"와 "Key opacity, pivot and onion settings"를 돌려 둘 다 pass(다시 물음 없음)였다. 이번 실행에서는 시간 초과가 나지 않아 실제 "pass after retry"는 아직 보지 못했다.

## 79. 256보다 큰 픽셀 그림의 확대 GIF (이슈 #24, 2026-10-17)

**질문:** 이슈 #24 사용자는 캔버스가 256×256 이하일 때만 확대 GIF에 픽셀 블록이 보이고, 512×512 이상은 200·400·800%를 골라도 보이지 않는다고 했다. 앱이 큰 캔버스에서 블록이 아닌 GIF를 쓰는가.

**방법:** Windows Sandbox에서 `gui.ps1`의 "Enlarged pixel art GIFs of larger canvases"를 돌렸다. 설정의 `pixelExportScale`을 2와 4로 두고 앱을 켜, 512×512와 1000×1000 픽셀 모드 새 문서에 픽셀 연필로 한 획(30프레임 문서)을 긋고 움직이는 GIF로 내보냈다. 단계는 GIF 창의 크기 칸을 읽고, 파일 첫 프레임이 그 크기인지, 왼쪽 위부터 배율×배율 칸마다 한 색인지 센다. 호스트에서도 Pillow로 같은 파일을 따로 셌다. 3.3.2 코드(main 8627930)의 release 빌드, 기본 메모리 Sandbox와 `prepare.ps1 -MemoryInMB 16384` Sandbox에서 한 번씩.

**결과:**

| 캔버스 · 고른 배율 | GIF 크기 | 한 색이 아닌 칸 | 내보내기 시간(16GB Sandbox, ms) |
|---|---|---|---|
| 512 · 200% | 1024×1024 | 0 | 254 |
| 1000 · 200% | 2000×2000 | 0 | 624 |
| 512 · 400% | 2048×2048 | 0 | 679 |
| 1000 · 400% | 4000×4000 | 0 | 2,778 |

GIF는 모두 두 색(흰 바탕과 획)이었다. 기본 메모리 Sandbox에서는 1000·400%가 그 PC의 내보내기 예산을 넘어 창이 200%(2000×2000)로 열렸고(`files.rs` `export_animation`이 예산에 드는 다음 크기를 고름), 그 파일도 2×2 칸이 모두 한 색이었다. 나머지 셋은 16GB와 같았다.

**결론:** 512와 1000 캔버스에서도 앱은 고른 배율대로 한 픽셀을 블록으로 쓴다. 사용자가 블록을 보지 못한 것은 1024 이상인 GIF를 이미지 보기 프로그램이 창에 맞게 줄여 보였기 때문이라는 것이 **가설**이다(사용자가 쓴 프로그램은 확인하지 않음). 1000·2000 캔버스에는 800%가 없다(긴 변 4096 상한, `export.rs` `MOST_ENLARGED`).

**시험 스크립트:** 저장 대화상자에 친 이름은 앞 글자가 빠지기도 해서(경로를 치면 "경로가 없습니다", 이름만 치면 다른 이름으로 저장), 단계는 문서 폴더에 새로 생긴 GIF를 가져온다. 새 Sandbox의 첫 파일 대화상자는 20초 안에 뜨지 않은 적이 있어 90초 기다린다. 크기 목록은 UI Automation으로 펼쳐지지 않은 적이 있어 설정으로 배율을 정한다.

## 80. 1px 앨리어싱 선의 구멍과 새는 페인트통 (2026-10-17)

**질문:** 기본 우글거림에서 1px 앨리어싱 펜으로 그린 닫힌 상자를 페인트통으로 채우면 왜 상자 밖까지 채워지나(66절).

**방법:** 66절과 같은 320×200 상자(앱 `Canvas`, release, `UGU_WORKER_THREADS=8`)에서 페인트통이 읽은 그림 그대로 flood를 다시 돌려 상자 밖에 닿는지 보고, 닿으면 상자의 네 변을 따라 선 화소(alpha 128 이상)가 없는 열을 찾았다(임시 시험). 획의 seed는 세션마다 무작위라(`RandomState`) 실행마다 다른 선이다. 원인을 가른 뒤 `ugu-render`에서 우글거림 없이 너비 0.9·0.975·0.99·1.0의 앨리어싱 직선을 0~45°(각도마다 위치 8개)로 그려, 선 가까이에 화소가 없거나 다음 열과 8-이웃으로 닿지 않는 열을 셌다(임시 시험).

**결과:** 고치기 전 24번 중 10번 상자 밖으로 샜다. 샌 곳은 선이 한 행 아래로 넘어가는 열에서, 그 열의 두 화소가 모두 절반 미만으로 덮여 아무것도 그려지지 않은 한 화소짜리 구멍이었다(예: x=175, 왼쪽은 행 39, 오른쪽은 행 40). 직선의 구멍 열 수:

| 너비 | 0.9 | 0.975 | 0.99 | 1.0 |
|---|---|---|---|---|
| 구멍 열 | 2,297 | 387 | 166 | 0 |

1px 이상이면 어느 각도에서도 구멍이 없었다. 우글거림(classic)은 너비를 최대 2.5% 줄이고(`Mover::width`), 필압과 크기 반응도 줄인다. 그래서 1px 앨리어싱 선이 0.975px까지 가늘어져 구멍이 났다. 2.2.13도 너비 하한이 0.25px라 같은 조건이었다(가설: 2.2.13에서 재지 않음).

**고친 뒤:** 앨리어싱 선은 1px보다 가늘게 그리지 않는다(decisions.md 2절). 같은 상자에서 20번 모두 새지 않았다. 시험 `an_aliased_line_a_pixel_wide_has_a_pixel_in_every_column`(우글거림 1.6의 30프레임, 기울기 6가지와 필압 0.4의 선)은 고치기 전 프레임 0의 필압 선에서 실패했다. `a_bucket_fill_goes_behind_the_lines_on_every_wobbling_frame`에 1px 앨리어싱 상자를 더했다.

## 81. 채우기를 프레임마다 다시 하는 비용 (2026-10-17)

**질문:** 채우기 경계가 우글거리는 선을 따라가게 하는 가장 직접적인 방법은, 그 레이어를 프레임마다 그릴 때 채우기 단계에서 그때까지 그린 그 프레임의 선으로 flood와 `under_lines`를 다시 하는 것이다. 그 비용은 얼마인가.

**방법:** `selection::tests::measure_flood_per_frame`(`--ignored`, release, 1스레드, 호스트 Intel Core Ultra 7 270K Plus). 정사각 캔버스에 우글거린 고리(반지름 ±3%, 굵기 2~6px)를 불투명 선으로 두고, 가운데에서 `Selection::flood`(alpha 경계)와 `under_lines(…, 16)`을 15번씩 재어 중앙값을 냈다.

**결과(ms, 중앙값):**

| 캔버스 | 채운 넓이 | flood | under_lines | 합 |
|---|---|---|---|---|
| 320² | 약 2만 px | 0.04 | 0.07 | 0.11 |
| 1024² | 약 50만 px | 0.93 | 1.07 | 2.0 |
| 2048² | 약 254만 px | 4.32 | 5.18 | 9.5 |
| 4096² | 약 1,134만 px | 20.36 | 24.39 | 44.8 |

채운 넓이 100만 px마다 프레임마다 약 4ms다. 한 레이어의 채우기 넓이 합은 대개 캔버스를 넘지 않으므로, 2048²를 거의 다 칠한 레이어는 프레임마다 약 10ms, 4096²는 약 45ms가 더 든다(가설: 채우기가 겹치지 않을 때). 재생은 첫 바퀴에만 프레임을 그리므로 첫 바퀴와 편집 뒤 다시 그릴 때 늘고, 8스레드 ② 프레임이 이미 35~49ms다(13·14절).

**같이 드러난 위험:** 프레임마다 flood하면 어느 한 프레임의 선에 틈이 생길 때 그 프레임만 채우기가 밖으로 퍼진다. 지금은 클릭할 때 한 번만 샐 수 있다. 다시 flood하더라도 클릭 때의 영역을 최대 우글거림만큼 넓힌 범위 안으로 막아야 한다.

**결론과 코드:** 언어를 고른 직후 `theme::read_fonts_early`가 따로 스레드에서 읽기 시작한다(`main.rs` `run`). 창 스레드는 다 읽힌 것을 받거나 남은 만큼만 기다린다(`OnceLock`). 첫 프레임에서 YaHei 글리프를 만드는 약 5ms는 그대로다. 캐시에 없는(첫 부팅 뒤) 읽기는 재지 않았다: 더 오래 걸리겠지만 그만큼 창·GPU를 여는 시간과 겹친다(가설).

## 87. 예산 초과 편집 split의 화소 일치 (2026-10-18)

**질문:** 레이어 표면이 예산을 넘으면 편집 split이 캔버스와 내보내기의 화소 일치를 깼다(3.4.1까지). 왜이고, 같게 하면 얼마가 드나.

**원인:** `stream.rs` `reduce`는 편집 레이어 아래를 배경부터 순서대로 미리 합치고(전체 렌더와 같은 순서), 편집 레이어 위의 Normal 레이어 묶음은 투명한 면에 먼저 합쳐 한 장으로 얹었다. 8비트 반올림에서 `(X ⊕ A) ⊕ B`와 `X ⊕ (A ⊕ B)`는 다르다. 8×8 반투명 채우기 8장(불투명도 `0.53+0.05i`, 색 `[30+20i, 130-5i, 57+14i, 100+11i]`)의 첫 레이어를 예산 0에서 편집하면 1단계 달랐다(`compose::tests::over_the_budget_the_split_shows_the_bytes_of_a_full_render`, 고치기 전 실패). 위 레이어를 묶지 않게 임시로 바꾸자 바이트가 같아져 원인을 확인했다.

**고친 것:** 위 레이어는 저마다(그에 클리핑된 것과 함께) 두고 차례로 얹는다. 기존 예산 초과 시험(`over_the_budget_the_split_keeps_every_layer_editable`, blend·clip·그룹·키·셀 문서의 모든 레이어)은 오차 2 허용에서 바이트 같음으로, 같은 예산의 스트리밍 렌더도 바이트 같음으로 바꿨고 통과한다. 획을 찍은 뒤는 예산 안과 같은 1단계다.

**비용:** `ugu-doc render <fixture> 8`, `UGU_SURFACE_BUDGET_MIB=0`, 같은 release 빌드 둘(고치기 전·뒤). "pixels held"는 split이 쥔 화소(`Split::held_bytes`, 이번에 더함), 시간은 레이어마다 split(획 하나 뒤).

| fixture | 쥔 화소 p50 / max (전 → 뒤) | split p50 (전 → 뒤) | 최고 작업 집합 (전 → 뒤) |
|---|---|---|---|
| ② | 128 / 176 → 128 / 176 MiB | 131.8 → 123.3ms | 326 → 327 MiB |
| ③ | 48 / 48 → 64 / 80 MiB | 46.9 → 42.1ms | 245 → 249 MiB |
| ⑤ | 320 / 320 → 320 / 320 MiB | 204.4 → 206.9ms | 1066 → 1066 MiB |

예산 안(제한 없음)에서는 ② 224, ③ 64, ⑤ 320 MiB를 쥔다(같은 도구). 위 레이어가 많고 Normal인 문서일수록 예산을 넘었을 때 더 쥐며, 그 최대는 예산 안의 split과 같다. 시간 차는 실행 간 흔들림 안이다.

## 90. WARP에서 GPU 시험 프로세스가 죽던 것 (2026-10-21)

**질문:** CI의 "Rust Windows release tests"에서 `ugu_render` 시험 프로세스가 `STATUS_ACCESS_VIOLATION`(0xC0000005)으로 끝난 원인. 2026-10-16 main `10e2ad0`(실행 38874076967)과 2026-10-21 `4c98944`의 PR #119·main(실행 39599110586, 39601054566)에서 났고, job을 다시 돌리면 통과했다. 단언이 실패한 것이 아니라 프로세스가 죽었다. 세 번 모두 끝나지 않은 시험은 `view::tests`의 GPU 시험(CI 러너에는 GPU가 없어 WARP)과 `stroke::tests::the_outline_fills_what_the_circles_and_bands_fill`였다.

**방법:** 저장소 밖 복제본에서 `view::tests::device`가 `force_fallback_adapter: true`로 이 PC의 WARP(`d3d10warp.dll` 10.0.26100.9711)를 쓰게 하고, release로 만든 `ugu-render` 시험을 되풀이했다. 죽는 곳은 그 복제본에만 넣은 vectored exception handler로 모듈과 스택을 남겼다.

**결과:**

| 실행 | 비정상 종료 |
|---|---|
| `view::tests`만, 병렬 | 100번 중 5번 |
| 시험 전체, 병렬 | 30번 중 2번 |
| `view::tests`만, `--test-threads=1` | 100번 중 0번 |
| 고친 뒤 `view::tests`만, 병렬 | 200번 중 0번 |
| 고친 뒤 시험 전체, 병렬 | 60번 중 0번 |

죽은 곳은 `d3d10warp.dll` + 0xa7959의 읽기(주소 0x202345d2c9c)였고, 그 스레드는 시험 스레드가 아니라 Windows 스레드 풀의 작업자(`TpCallbackMayRunLong` → `d3d10warp.dll`)로 Rust 프레임이 없었다. 시험마다 따로 만든 장치가 다른 스레드에서 같은 때에 쓰일 때만 났다.

**결론:** WARP 안의 결함이고(풀린 메모리를 읽는다는 것은 가설), 한 프로세스에서 장치 여럿을 함께 쓰는 시험만 그 조건을 만든다. 앱은 프로세스마다 장치가 하나다. 그래서 GPU 시험이 앱처럼 장치를 하나씩 쓰게 했다: `view::tests::render_with`가 잠금을 쥔 채 장치를 만들고 버린다. 앱의 WARP 경로가 이 결함에 닿지 않는다는 것은 가설이다(Sandbox 수용의 "Run on WARP"와 한 스레드 100번은 죽지 않았다). CI 러너의 WARP 판은 확인하지 않았다.

## 92. 펜을 뗄 때 찍은 앨리어싱 선의 가장자리 (2026-10-22)

**질문:** `files::end_to_end::strokes_after_a_crop_or_a_resample_draw_on_the_new_canvas`가 가끔 "the canvas differs from a full render by 255"로 실패했다(2026-10-14 로컬 debug 전체 실행, 2026-10-15 main CI `c6a4e36` 실행 38691779083, 2026-10-21 PR #120 CI 실행 39608805791). 캔버스가 자르기 전이나 마지막 획 전의 split을 보였나, 시험의 기다림이 틀렸나.

**방법:** 그 시험 하나를 debug, `UGU_WORKER_THREADS=8`로 프로세스마다 돌렸다: 혼자 300번, 12개를 나란히. 임시 계측으로 실패한 확인(세 번 중 어느 것), 3 넘게 다른 화소와 값, 캔버스의 key·split key·요청, 작업자가 그린 순서를 찍고, 같은 문서를 0·8스레드 렌더러로 다시 그려 견줬다.

**결과:** 혼자 300번은 실패 0, 나란히 1,200번(계측한 바이너리)은 3, 계측하지 않은 바이너리로 나란히 4,800번은 11(모두 같은 메시지). 계측한 세 번 모두 두 번째 확인(390×300으로 리샘플하고 세 번째 획을 그린 뒤)에서 세 번째 획 가장자리의 화소 **하나**만 달랐다: (18, 224)와 (128, 212)는 캔버스가 검정·전체 렌더가 흰색, (71, 181)은 그 반대. 캔버스는 지금 판의 split(리샘플 뒤 split에 세 번째 획을 펜 뗄 때 찍은 것)을 보였고 기다리는 요청은 없었다. 다시 그린 0·8스레드 렌더는 서로, 그리고 전체 렌더와 같았다. 경합도 기다림도 아니고, 펜을 뗄 때 찍은 획이 전체 렌더와 달랐다.

**원인:** 펜을 뗄 때 `Stamp`은 선의 coverage를 획 경계의 모서리에서 시작하는 pixmap에 Vello로 그렸고, 전체 렌더는 레이어를 그 레이어가 닿는 타일의 왼쪽 위부터 그린다. Vello는 경로를 그리는 원점 기준 좌표로 바꿔 f32로 넘기고 4px 타일로 나누므로, 같은 윤곽도 원점이 다르면 가장자리 coverage가 조금 다르다. 안티앨리어싱 선은 1단계 안(받아들인 반올림)이지만, 앨리어싱 선(문턱 128, 새로 설치한 잉크 펜)은 문턱에 걸린 화소가 통째로 흑백이 바뀐다. 획의 seed가 세션마다 무작위라(`RandomState`) 우글거림으로 윤곽이 실행마다 달라서 걸리는 획이 실행마다 다르다. 부하와는 관계가 없다(혼자 0/300은 같은 비율과 맞는다).

`ugu-render` 임시 시험(release)으로 같은 펜(앨리어싱, 너비 6, classic 1.6)의 물결 획을 390×300 레이어에 찍고 전체 렌더와 견줬다:

| 레이어 | 획 | 찍은 레이어가 전체 렌더와 다름 | 같은 윤곽을 Vello로, 획 모서리에서 / 레이어 원점에서 |
|---|---|---|---|
| 빈 레이어(타일 원점 (0, 128)) | 10,000 | 14 | 14 / 0 |
| 캔버스를 덮은 레이어(원점 (0, 0)) | 6,000 | 9 | — |

레이어가 그려지는 원점은 레이어의 내용으로 정해져서, 뒤의 획이 왼쪽이나 위 타일에 닿으면 전체 렌더는 앞의 획도 새 원점에서 그린다. 600×400 레이어에 같은 획을 (200, 100) 옮겨 그리고(원점 (128, 256)) 왼쪽 위에 짧은 획을 더하면(원점 (0, 0)), 두 전체 렌더 사이에 앞 획의 화소가 10,000획 중 45획에서 달랐다.

레이어 원점부터 Vello로 그리면 원점에서 획까지를 다 그려야 해서, 오른쪽 아래 획 하나가 2048²에서 0.023 → 0.693ms, 4096²에서 0.024 → 4.020ms였다(release, 40번 p50).

**고친 것:** 펜을 뗄 때 선은 Vello CPU 렌더러의 strip 생성기(`vello_common::strip_generator`, 같은 0.3.0)를 전체 렌더가 그 레이어를 그리는 변환·뷰포트로 돌려 만들고, coarse 단계처럼 strip의 alpha와 그 사이의 채움을 깐다(`crates/ugu-render/src/compose.rs` `Stamp::line_coverage`). split은 편집 레이어가 닿는 타일을 `reach`와 같은 규칙으로 기억한다(`Split::reached`, `document.rs` `tiles_reached`). 찍은 획·채우기·적용한 이동이 그 왼쪽이나 위에 닿으면 앞 획이 다른 원점에서 그려지므로 split을 다시 그릴 것으로 둔다(`Split::redraw`). 캔버스는 그때 split을 다시 요청하고 올 때까지 찍은 것을 보이며 그 위에 계속 찍고(`canvas.rs` `sync`), 자동 선택·페인트통은 그동안 작업자가 그린 것을 읽는다.

**고친 뒤:** 같은 임시 시험에서 빈 레이어 0/10,000, 덮은 레이어 0/6,000(바이트 같음). 앱 시험은 나란히 4,800번에서 고치기 전 11, 뒤 0.

처음 고친 판은 ⑤의 첫 split(새 렌더러가 모든 레이어를 그림)이 번갈아 잰 8쌍 중앙값 169 → 185ms로 늘었고 ②·③과 나머지 split·프레임은 그대로였다. ⑤에만 있는 2048² PNG의 디코드가 21.6~21.9 → 36.6~37.4ms(20번 p50)였다. 디코드한 화소마다 부르는 `compose::premultiplied`에 `#[inline]`을 붙이자 20.9ms로 돌아왔다(가설: `compose.rs`가 커지자 release의 codegen unit 나눔이 바뀌어 `image::decode`에서 인라인되지 않았다. 기계어는 보지 않았다).

## 96. 내비게이터 그림의 축소 방식 (2026-10-26)

**질문:** 내비게이터가 캔버스 전체를 패널 크기(한 변 240~360 물리 픽셀)로 줄여 보일 때 어떤 방식이 그림을 제대로 보이고, 편집·재생 중에 얼마나 드나.

**방법:** 저장소 밖 복제본의 무시된 시험(`main` `585b384` 기준)이 세 그림을 같은 GPU 텍스처에서 줄였다: fixture ②(2048², `ugu-doc fixture 2`를 `DocumentRenderer` 8스레드로 그린 첫 프레임), ⑤(4096²), 4096² 흰 바탕에 왼쪽 반은 1px 대각선 4px 간격, 오른쪽 반은 1px 가로줄 3px 간격. 방식: (가) 캔버스가 100% 아래에서 쓰는 한 단계 텍스처 선형 표본, (나) 2×2 평균 mip 사슬 + 삼선형 표본(lod = log₂ 배율), (다) 그림 한 픽셀 아래의 캔버스 픽셀 면적 평균을 GPU 셰이더로. 기준은 같은 면적 평균을 CPU에서 f32로 한 것이다. 비교는 premultiplied RGBA 채널마다. 시간은 인코드·submit·완료 대기까지의 벽시계 중앙값(RTX 5080 30회, WARP 5회), CPU는 1스레드. "변화"는 문서 가운데 256² 사각형 위의 그림 픽셀만 다시 그린 것(scissor)이다.

**결과(360px, RTX 5080):**

| 그림(배율) | (가) PSNR·최대 차·16 넘게 다른 채널 | (나) | (다) |
|---|---|---|---|
| ② 2048²(5.69) | 25.29dB · 199 · 14.4% | 30.01dB · 80 · 6.6% | 65.93dB · 1 · 0% |
| ⑤ 4096²(11.38) | 24.67dB · 225 · 12.4% | 30.27dB · 79 · 6.5% | 66.05dB · 1 · 0% |
| 줄무늬 4096²(11.38) | 11.54dB · 185 · 68.1% | 33.80dB · 19 · 1.7% | 같음 · 0 · 0% |

240px도 같은 순서다((가) 11.6~23.0dB, (나) 28.6~35.6dB, (다) 65.4dB 이상). 그림으로 보면 (가)는 가는 선이 점선으로 끊기고, (나)는 선이 흐리다.

| ms(중앙값) | ② | ⑤ | 줄무늬 |
|---|---|---|---|
| (다) GPU 전체, RTX 5080 | 0.147 | 0.399 | 0.496 |
| (다) GPU 256² 변화, RTX 5080 | 0.094 | 0.139 | 0.230 |
| mip 사슬 전체 다시 만들기, RTX 5080 | 0.253 | 0.300 | 0.458 |
| (다) GPU 전체, WARP | 4.950 | 11.595 | 11.823 |
| (다) GPU 256² 변화, WARP | 0.523 | 0.531 | 0.481 |
| (다) CPU 1스레드 전체 | 4.215 | 11.735 | 11.718 |
| (다) CPU 1스레드 256² 변화 | 0.112 | 0.143 | 0.130 |

(다)를 GPU로 골랐다(`ugu_render::overview`, decisions.md 2절). 기준과 최대 1단계 차이이고, 전체를 다시 그려도 RTX 5080에서 0.5ms 아래다. CPU는 같은 값을 내지만 render 스레드에서 전체에 4~12ms가 들어, 프레임마다 그림 전체가 바뀌는 재생에서 그만큼 프레임을 쓴다. WARP는 GPU 전체가 5~12ms라 재생 중 내비게이터를 열어 두면 프레임마다 그만큼 더 쓸 것이다(가설: 재생 프레임은 줄여 그려 텍스처가 작으므로 더 적다, 재지 않음). 앱 안에서는 완료를 기다리지 않으므로 위 벽시계 시간은 render 스레드가 기다리는 시간이 아니다.

**확인:** `overview::tests`가 평균·체커보드·바뀐 곳만 다시 그림·줄인 일부·크기 바꿈을 GPU로 본다. Windows Sandbox에서 `gui.ps1` "Navigator" 단계(1600×1000 창, 영어): 우글거림 뒤의 탭을 열고 획을 그으면 그림의 픽셀 262~267개가 바뀌고, 400%로 확대한 뒤 그림 가운데 60px 왼쪽을 누르면 테두리 가운데가 -60.3~-60.4, 40px 오른쪽은 39.3~39.4, 테두리 안 50px 오른쪽을 눌러 20px까지 끌면 9.3이다(누른 자리로 뛰었다면 20). 첫 두 실행은 끌기 끝이 14.4로 5px 모자랐다: 누른 프레임에 포인터가 이미 움직였으면 egui가 누른 자리 대신 움직인 자리를 줘서 테두리 안에서 잡은 거리가 틀렸다. 누른 자리(`press_origin`)로 재게 고쳤고, 놓는 프레임에 함께 온 마지막 움직임도 반영하게 했다. 시험 `navigator::tests`의 두 끌기 시험은 고치기 전에 실패한다. 고친 뒤 두 번 연속 통과했고, 같은 빌드로 "Turn and flip the view", "Docks of a short window", "Splits and the menu bar of a small window", "Tab moves the keyboard focus through the controls"도 통과했다.

상태 표시줄의 포인터 위치(`x … y …`)는 UI Automation 트리에 없어 시험이 읽지 못했다(backlog B3-168). 그래서 단계는 그림 안 강조색 테두리의 가운데를 화면에서 잰다.

## 97. macOS에서의 빌드 상태와 ARM의 SIMD 수준 (2026-10-28)

**질문:** 지금 트리 중 무엇이 macOS(Apple Silicon)에서 빌드·시험되나. Vello CPU를 ARM에서 NEON으로 그리면 x86 SSE4.2와 바이트가 같나.

**방법:** Apple Silicon Mac(macOS, arm64). 환경 절의 Windows PC가 아니다, main `843b5a4`, 툴체인 1.99.0 `aarch64-apple-darwin`. 빌드는 패키지마다 `cargo check --locked -p <패키지> --all-targets`, 시험은 `cargo test --locked -p ugu-core -p ugu-io -p ugu-session -p ugu-text`(debug). SIMD는 저장소 밖 시험 프로그램(`vello_cpu` =0.3.0 `u8_pipeline`·`multithreading`, `fearless_simd` =0.7.0에 `force_support_fallback`)이 같은 장면을 수준마다 그려 RGBA8 결과를 바이트로 비교했다. 장면: 1024², Normal·Multiply·Screen·Overlay 레이어 4개(불투명도 0.8), 레이어마다 xorshift로 만든 2차 곡선 40조각 경로 1,500개(⅓ 채우기, ⅔ 굵기 1~13 선), 반투명 색(alpha 0.2~0.8), 7번째마다 두 점 방사형, 11번째마다 선형 그라디언트, 작은 회전 변환, 레이어마다 사각형 하나. x86은 같은 프로그램을 `x86_64-apple-darwin`으로 빌드해 Rosetta 2로 돌렸다. 시간은 그리기 호출부터 `render`까지 벽시계(인코드·래스터·합성), 3 round.

**결과(빌드):** `ugu-core`·`ugu-io`·`ugu-session`·`ugu-text`는 빌드된다. `ugu-render`·`ugu-win`·`ugurugu`·`ugu-doc`·`render-bench`는 `windows` crate(`windows-future`)가 컴파일되지 않아 실패한다. 시험은 core 123·io 68·session 102개 통과, `ugu-text` 4개 중 2개 실패(`letters_become_closed_contours_below_and_right_of_the_origin`의 크기, `each_line_starts_lower_and_empty_lines_count`의 줄 높이). `Fonts::new`의 대체 글꼴이 Windows 글꼴 이름(Malgun Gothic, Segoe UI, Yu Gothic UI, Microsoft YaHei)뿐이라 macOS에서는 `sans-serif`가 다른 글꼴로 풀린 것이 원인이다. 2026-10-28에 풀린 글꼴과 줄 높이를 찍어 확인했다(`platform/fonts` 브랜치, 시험에 임시 출력): "en"은 Helvetica로 풀려 64px에서 줄 높이가 64(줄 간격 0)라 `> 64`를 못 넘었고, "ko"는 가가 있는 줄은 Apple SD Gothic Neo(줄 높이 48), 빈 줄은 목록 첫 글꼴이 없어 Helvetica(40)로 잡혀 줄 간격이 어긋났다. OS마다 그 OS에 있는 글꼴을 목록 앞에 두자 macOS에서 네 시험이 모두 통과했다.

**결과(SIMD):** aarch64에서 `Level::baseline()`은 `Neon`이다(NEON이 대상 기본 기능이라). 그래서 `raster::document_level`은 ARM에서 이미 NEON이다. 스칼라는 `force_support_fallback`의 `Level::fallback()`으로만 고를 수 있다.

| 비교 (4,194,304바이트) | 다른 바이트 |
|---|---|
| ARM 스칼라 대 x86 SSE4.2(Rosetta) | 0 |
| ARM 스칼라 대 x86 스칼라(Rosetta) | 0 |
| ARM NEON 대 ARM 스칼라 | 34,901(0.83%, 최대 차 5) |
| ARM NEON 대 x86 SSE4.2 | 34,901 |
| ARM NEON 1스레드 대 8스레드 | 0 |

ARM 1스레드 시간: 스칼라 441.6·442.9·466.5ms, NEON 370.0·371.0·373.3ms(약 16% 짧다). NEON 8스레드 70.6~72.3ms. Rosetta의 x86 시간은 번역 비용이 섞여 비교하지 않는다.

**결론:** ARM에서 NEON은 x86과 바이트가 다르고 스칼라는 같다. 차이는 NEON의 `mul_add`가 FMA(`vfmaq_f32`, 반올림 1회)이고 SSE4.2·스칼라는 곱한 뒤 더하는 것(반올림 2회) 때문이라고 본다(**가설**: `fearless_simd` 0.7.0 `generated/neon.rs`·`sse4_2.rs`·`fallback.rs`를 읽은 것, 연산마다 나눠 재지 않았다). 같은 PC 안에서 캔버스와 내보내기가 같다는 약속은 어느 수준이든 지켜진다(1·8스레드 같음). 이 장면은 앱의 fixture가 아니므로, 앱 렌더러로 같은 비교(`ugu-doc digest`)를 다시 해야 한다. 고르는 일은 [plan-cross-platform.md](plan-cross-platform.md) 6절이다.

## 98. macOS에서 앱의 첫 실행 (2026-10-28)

**질문:** 1단계의 첫 변경(winit 입력, 트랙패드 제스처)으로 앱이 macOS에서 그리기·재생을 버티나. 사용자가 debug 빌드에서 큰 에어브러시와 우글거림 재생에 "렉이 엄청나다"고 했다.

**방법:** Apple M4 Mac, swap chain 3420×1902(`Bgra8Unorm`, Fifo), `platform/mac-window` 브랜치(커밋 전). 문서는 사용자가 그린 1024×768, 30프레임 재생. 사용자가 직접 조작했고, 수치는 앱 로그(`UGURUGU_LOG=debug`의 `frame ui_ms`·`rest_ms`, `playback frame rendered`·`shown`, 끝날 때의 `input to present-return latency`)에서 셌다. debug 실행은 `cargo run`(dev 프로필, 작업자 수 기본), release 실행은 `UGU_WORKER_THREADS=8`.

**결과:**

| 실행 | 프레임 | 프레임 시간(ui+rest) | 재생 프레임 렌더 | 입력→present 반환 p50·p95·최대 |
|---|---|---|---|---|
| debug, 그리기·재생 | 699 | 로그 수준이 info라 없음 | 없음 | 18.32·23.08·88.50ms |
| release, 그리기·재생 | 1,181 | 30ms 초과 1개(32.7ms), 보통 ui 0.3~0.5 + rest 0.5~0.8ms | 약 2ms | 1.92·17.77·293.61ms |
| release, 트랙패드 제스처·재생 | 1,085 | 20ms 초과 4개, 최대 31.7ms | 중앙값 2.1ms, 최대 16.5ms | 10.80·17.95·34.14ms |

release 첫 실행에서 재생 프레임이 보인 간격은 중앙값 40ms(25fps)였다. 270~950ms 간격 9번은 모두 재생 중에 획을 그은 동안이다(획이 끝나면 `pen-up shown` 뒤 `playback started`). 저장 확인 창이 떠 있는 동안 rest가 약 16ms인 것은 60Hz 화면의 vsync 대기다.

## 99. macOS에서의 장치 손실 복구 (2026-10-28)

**질문:** Windows의 장치 손실 복구(decisions.md 2절)가 macOS Metal에서도 화면을 되살리나. 복구 뒤 프레임 대기가 막히나(plan-cross-platform 3.2절의 **가설**).

**방법:** Apple M4 Mac, release 빌드, swap chain 3420×1902, `UGURUGU_DIAGNOSTICS=1 UGURUGU_LOG=debug UGU_WORKER_THREADS=8`. 사용자가 F9를 누르고 그렸다. Windows 밖의 F9는 wgpu `Device::destroy()` 뒤 한 번 poll해 장치 손실 콜백(`reason=Destroyed`)을 부른다. 드라이버가 일으킨 손실이 아니라 앱이 버린 장치다. 수치는 앱 로그의 `GPU device replaced`·`Missing texture`·`no swap chain buffer`·`frame abandoned`에서 셌다.

**결과:**

| 빌드 | 복구 | 복구 시간(`total_ms`) | 복구 뒤 건너뛴·버린 프레임 | egui `Missing texture` |
|---|---|---|---|---|
| 고치기 전 | 8번 | 16.5~25.1ms | 0 | 177번씩 5개(`Managed(1..5)`), 다음 시작까지 |
| 고친 뒤 | 2번 | 18.4~20.0ms | 0 | 0 |

고치기 전 마지막 복구 뒤에도 프레임 133개가 이어졌다. 사라진 텍스처는 브러시 미리보기였다: 복구가 레이어 썸네일만 비우고 브러시 미리보기와 정보 탭 아이콘의 캐시는 옛 장치의 텍스처를 가리킨 채 두었다. 이제 패널의 텍스처 캐시를 모두 비운다(`Panels::forget_textures`). 같은 코드라 Windows에서도 일어났을 것으로 본다(**가설**: Windows에서 확인하지 않았다).

**결론:** 앱이 버린 장치에서는 macOS 복구가 20ms 남짓에 끝나고 프레임 대기가 막히지 않는다. 드라이버가 일으킨 손실 뒤에 `nextDrawable`이 막히는지는 일으킬 방법이 없어 확인하지 못했다(Apple Silicon의 GPU는 떼어 낼 수 없다).

## 100. macOS에서 render 스레드의 창 호출 왕복 (2026-10-28)

**질문:** winit 0.30.13은 macOS에서 메인 스레드 밖의 창 호출을 모두 메인 큐에 넘기고 끝날 때까지 기다린다(`dispatch_sync`, plan-cross-platform 3.4절). render 스레드가 프레임마다 하는 창 호출이 지연을 늘리나.

**방법:** Apple M4 Mac, release 빌드, `UGU_WORKER_THREADS=8`. 커밋하지 않은 계측으로 프레임마다 세 시간을 기록했다: 프레임 처음의 `window.inner_size()` 한 번, egui-winit `take_egui_input`, `handle_platform_output`. 사용자가 약 1분 동안 그리기, 제목 막대 끌기, 가장자리로 크기 바꾸기, 창 안 메뉴를 열어 둔 채 움직이기를 차례로 했다. 프레임 9,234개.

**결과:**

| 시간 | p50 | p95 | p99 | 최대 |
|---|---|---|---|---|
| 창 호출 한 번 | 9µs | 43µs | 128µs | 6.9ms |
| `take_egui_input` | 25µs | 74µs | 109µs | 5.5ms |
| `handle_platform_output` | 0µs | 1µs | 2µs | 26µs |

창 호출 한 번이 1ms를 넘은 프레임은 25개, 0.5ms를 넘은 것은 36개였다. 대부분 사용자가 창을 끌고 크기를 바꾸던 약 25초 사이에 몰렸다(어느 조작인지는 나누어 기록하지 않았다). 같은 실행의 입력→present 반환은 p50 17.33ms, p95 26.69ms, 최대 35.37ms(프레임 464개). 창을 닫자 render 스레드가 끝나고 창이 닫혔다(서로 기다리지 않음).

**결론:** 왕복은 보통 수십 µs이고, 메인 스레드가 바쁠 때도 한 프레임(8~17ms) 안이다. egui-winit `State`는 render 스레드에 둔다. 메인 스레드가 render 스레드를 기다리는 곳은 macOS 앱 코드에 없다: 창 닫기는 render 스레드가 끝난 뒤 `join`하고, 메인 스레드가 기다리는 세션 끝은 Windows에만 있다.

## 101. macOS에서 fixture 렌더 시간과 ARM의 SIMD 판 비교 (2026-10-29)

**질문:** 앱 렌더러로 fixture ①~⑤를 그리면 Apple Silicon에서 얼마나 걸리나(plan-cross-platform 1단계 측정). 97절의 시험 장면처럼 NEON은 x86과 바이트가 다르고, 그 차이는 FMA 때문인가(6절의 A·B·C).

**방법:** Apple M4(성능 코어 4 + 효율 코어 6), 24GiB, macOS 27.2, release, `MACOSX_DEPLOYMENT_TARGET=14.0`, main `683a0b6`에서. fixture는 이 빌드의 `ugu-doc fixture <n>`으로 만든 파일 하나씩을 모든 판이 함께 쓴다. 판 넷: 지금의 NEON, B(스칼라: `fearless_simd`에 `force_support_fallback`을 켜고 `document_level`이 aarch64에서 `Level::fallback()`), C(FMA를 뺀 NEON: `fearless_simd` 0.7.0의 `generated/neon.rs`에서 `vfmaq`·`vfmsq` 네 곳을 곱한 뒤 더하기·빼기로 바꾼 사본을 `[patch.crates-io]`), x86(`x86_64-apple-darwin` 빌드를 Rosetta 2로, SSE4.2). ## 102. zip 9.0.5와 헤더 일치 검사의 열기 시간 (2026-10-29)

**질문:** ugu-io를 zip 8.6.0에서 9.0.5로 올리고 열 때 `validate_header_consistency`를 부르면(decisions.md 11절) 열기가 얼마나 느려지나.
