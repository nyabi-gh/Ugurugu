# M3 분해: 렌더·스케줄러 완성 (2026-10-07)

M3 종료 조건(계획 11절): 같은 render plan 규약, 표준 문서 목표·device loss 통과. 이를 다음 세 가지로 확인한다.

- 화면(편집 분할·진행 중 획·pen-up), 재생, 내보내기가 모두 한 `RenderPlan`을 평가한다. 품질 수준(배율)만 다를 수 있고 지우개·그룹·클리핑·합성 모드의 의미는 같다(계획 7.1절).
- 계획 10.2절의 표준 문서 목표를 측정해 통과하거나, 통과하지 못한 항목은 이유와 제품 판단을 기록한다. 각 항목은 2.2.13 측정값([m0-evidence.md](m0-evidence.md) 2·5절)보다 나쁘지 않아야 한다.
- 실제 드라이버 리셋(TDR)에서 문서와 편집 상태를 잃지 않고 표시가 돌아온다(scope.md 3.2절).

범위는 [scope.md](scope.md) 3절 기능표의 "레이어·그룹·클리핑·4개 합성 모드·불투명도 (M3 전체)"와 계획 7절, M2에서 넘긴 것([m2-plan.md](m2-plan.md) 9절), M0 위험표에서 M3로 넘긴 것([m0-close.md](m0-close.md): 타일 단위 취소, 창 모드 승격, TDR)이다.

## 1. 범위

| 넣는 것 | 빼는 것 (단계) |
|---|---|
| 그룹(중첩, 불투명도, 합성 모드), 클리핑, Normal·Multiply·Screen·Overlay | 채우기·이미지·선택·자르기·리사이즈 렌더 (M4) |
| `RenderPlan`: 문서 트리에서 한 번 만드는 평가 순서. 모든 경로가 이것만 평가 | 마커·에어브러시·스프레이 (M4) |
| 타일 단위 레이어 표면, 정적 레이어 캐시, 분할 캐시의 트리 일반화 | 썸네일 (M5, 레이어 패널 미리보기) |
| 작업 스케줄러: 우선순위, 오래된 요청 교체, 타일 단위 취소, 자원 예산 | 자동복구 (M5) |
| 미리보기 품질(표시 배율 렌더)로 재생, 4096² 재생 예산 | GIF·WebP 내보내기 (M5) |
| 레이어 패널의 그룹 조작: 그룹 만들기·풀기, 그룹 안팎 이동, 합성 모드·클리핑·불투명도 | 도킹 (M5) |
| 연산 상한 측정과 조정, 2560 창 승격 조사, 실제 TDR 시험, GPU 가속 판단 | 펜 장치 실증 (M6 전 gate) |

이번 빌드부터 그룹·클리핑·합성 모드가 든 `.ugu2`를 연다. M4 내용(채우기·이미지·선택·자르기·리사이즈, 펜 외 브러시)은 계속 열지 않고 안내한다.

## 2. 의미: 2.2.13을 따르는 것

C++ `src/render/engine/LayerHierarchyCompositor.hpp`, `src/render/LayerCompositionPlan.cpp`에서 확인했다. 3.0은 같은 의미를 `RenderPlan`으로 옮긴다.

| 항목 | 규칙 |
|---|---|
| 그룹 | 항상 격리: 투명한 표면에서 자식을 평가한 뒤 그룹의 합성 모드·불투명도로 부모 위에 그린다 (pass-through 없음) |
| 클리핑 | `clip_to_below` 레이어(또는 그룹)는 같은 부모 안에서 바로 아래의 클리핑이 아닌 형제(기준)의 alpha × 기준 불투명도로 잘린 뒤, 자기 합성 모드·불투명도로 그려진다. 연달아 있는 클리핑 레이어는 같은 기준을 쓴다 |
| 기준이 없을 때 | 기준이 숨김·불투명도 0·완전히 투명이거나 형제 맨 아래면 그 클리핑 레이어들은 그리지 않는다. 숨긴 클리핑 레이어는 기준을 바꾸지 않는다 |
| 합성 모드 | premultiplied RGBA8, sRGB 인코딩 값 기준(계획 7.1절). Multiply·Screen·Overlay는 W3C Compositing의 분리형 공식(Qt `CompositionMode_*`와 같은 정의) |
| 참조 레이어 | 화면에는 보이고 내보내기에서는 빠진다(M2와 같음). 그룹이 참조면 자식 전체가 빠진다 |

픽셀 단위 호환은 약속하지 않는다(계획 5.3절). 2.2.13과 같은 공식을 쓰되 반올림은 3.0 합성기의 규칙으로 고정한다.

사용자 결정 (2026-10-07): 레이어 표면이 메모리 예산을 넘는 문서도 느리게라도 동작해야 한다. 렌더러는 그때 내부 캐시로 일부를 미리 합칠 수 있지만, **문서의 레이어는 어떤 경우에도 합치지 않는다**(레이어 패널·저장 파일·편집 대상은 그대로).

사용자 결정 (2026-10-07, UI): 3.0의 UI/UX는 2.2.13(C++) 화면을 기준으로 삼는다. 배치(도구 막대·오른쪽 도크·애니메이션 바·상태 막대), 기능 위치, 용어·번역, 단축키, 다크 테마와 앰버 강조색, 흔들리는 절차적 아이콘은 이어 가고, 간격·글자 위계·행 모양·컨트롤 세부처럼 더 낫게 할 수 있는 곳은 현대적으로 다듬되 바꾼 점을 기록한다. 아직 없는 기능(M4·M5)의 메뉴·버튼은 숨기고 그 기능이 들어올 때 C++ 자리에 넣는다. 화면 문구는 C++와 같은 영어 원문을 쓰고, 번역은 Fluent(`apps/ugurugu/i18n/*.ftl`)로 둔다. 한국어·일본어 번역문은 `tools/ts_to_ftl.py`가 2.2.13의 `.ts` 카탈로그에서 가져와 지금부터 시스템 언어로 보인다. 레이어 썸네일도 지금 넣는다. 그래서 M3-9가 이 UI 기반 작업을 포함한다.

## 3. 구조

M2는 문서 전체를 Vello 장면 하나로 그렸고, 레이어 불투명도도 Vello의 `push_layer`로 합성했다. M3는 이를 두 층으로 나눈다.

1. **레이어 표면:** 페인트 레이어 하나의 연산(지우개·isolated section 포함)을 Vello CPU로 그린 premultiplied 표면. 레이어 안의 의미는 M2 그대로다.
2. **합성:** `RenderPlan`을 따라 레이어 표면을 그룹·클리핑·합성 모드·불투명도로 합치는 우리 코드. 사각형(타일) 단위로 평가하고 스레드로 나눈다.

이렇게 나누는 이유:

- 전체 렌더, 편집 분할, pen-up 증분, 재생, 내보내기가 같은 합성 코드를 쓰므로 "같은 render plan 규약"이 구조로 성립한다. M2의 분할 합성은 Vello와 다른 공식이라 전체 렌더와 2단계까지 달랐다.
- Normal이 아닌 합성 모드는 아래 결과에 따라 달라지므로, M2처럼 위쪽 레이어를 미리 합쳐 두는 방식이 성립하지 않는다. 바뀐 사각형만 계획을 다시 평가해야 한다.
- 정적 레이어 캐시, 타일, 취소가 모두 레이어 표면 단위로 붙는다.

이 결정은 M3-1 측정과 M3-3 결과로 확인한다. 합성 비용 때문에 전체 렌더가 M2보다 느려지면 원인을 측정해 고친다(타일로 빈 영역 건너뛰기, 스레드 분할).

### M3-7·M3-8 GUI 확인 (2026-10-07, release, 2400×1500 창, 문서를 연 뒤 10초)

`idle_probe.py`(scratchpad)가 앱을 `UGURUGU_LOG=ugurugu=trace`로 띄우고, 유휴 10초 → `P` 재생 15초 → 재생 중 최소화 10초 → 복원 5초 → 정지 → 유휴 10초 → 최소화 10초를 거치며 로그의 렌더(`canvas split rendered`, `playback frame rendered`)와 업로드(`canvas uploaded`)를 구간별로 세고, 0.5초마다 working set을 읽는다.

| 문서 | 유휴 / 재생 중 최소화 / 정지 뒤 유휴 / 정지 뒤 최소화 | 재생 렌더 | 최대 working set: 처음 → 분할 놓기 → Vello 놓기 → 표시 표면 넘기기 |
|---|---|---|---|
| ②p 2048², 표시 배율 그대로(프레임 16MiB) | 렌더·업로드 0 / 0 / 0 / 0 | 30프레임 각 1회 | 1279 → 1057 → — → 951MiB |
| ⑤p 4096², 1/2 축소(프레임 16MiB) | 0 / 0 / 0 / 0 | 30프레임 각 1회 | 1321 → 1088 → 1025 → 964MiB |

- **분할 놓기:** 재생은 분할을 쓰지 않고, 정지하면 멈춘 프레임의 분할을 새로 만든다. 그런데도 재생 내내 이전 분할이 레이어 표면(`Arc`)을 쥐어, 렌더러가 그 표면을 재생에 다시 쓰지 못하고 새로 할당했다. 재생을 시작할 때 놓는다.
- **Vello 놓기:** 할당량을 세는 임시 전역 할당자로 재 보니 ⑤p 분할 뒤 힙이 표면·표시 합계보다 약 170MiB 컸고, 렌더 뒤 컨텍스트를 새로 만들면 112MiB가 줄었다. Vello 컨텍스트(작업자용 1개와 스레드별 1개)가 가장 큰 레이어를 그린 작업 메모리를 계속 쥐는 것이다. 작업자가 할 일이 없어질 때 놓는다. 다음 렌더가 다시 할당하는 비용은 없었다(`UGU_RELEASE_SCRATCH`로 분할마다 놓아도 획 뒤 분할 ②p 18.1 → 18.2, ⑤p 52.7 → 50.0ms, 2회 교대).
- **표시 표면 넘기기:** 편집 표시 표면(⑤p 64MiB)을 재생의 첫 보이는 프레임으로 넘겨 다음 프레임이 보이면 놓인다. 정지하면 멈춘 프레임을 분할이 올 때까지 계속 보인다. 이전에는 정지 직후 분할이 올 때까지(⑤p 약 170ms) 재생을 시작한 프레임이 잠깐 보였다.
- 남은 메모리(⑤p 재생, 힙 약 600MiB): 프레임 30 × 16MiB = 480, 1/2 레이어 표면 64, 그 밖 약 60MiB. 힙 밖(GPU 드라이버·업로드 staging·코드)은 작은 문서 유휴 때 약 220MiB, 재생 중 약 300MiB다. 768MiB 예산(표면 + 프레임)을 다 쓰는 문서는 힙 밖을 더하면 1GiB를 넘을 수 있다. 표준 문서는 안에 든다.

**pen-up (앱):** ②p를 열어 현재 레이어에 `SendInput`으로 30획: `pen-up shown` p50 1.44 / p95 1.65 / 최대 1.79ms, 오류 0.

**바쁜 작업자 중 입력→표시:** M3에는 그리는 동안 작업자를 계속 바쁘게 하는 경로가 없다(재생 중에는 present가 계속되어 latency-probe로 잴 수 없고, PNG 내보내기는 한 프레임이다). 그래서 같은 렌더 코드를 작업자와 같은 8스레드로 도는 `ugu-doc render ⑤p 8`을 옆에서 반복해 CPU·메모리 대역 부하를 만들고 쟀다. PC는 24 논리 코어이고 작업자는 8스레드까지 쓴다. latency-probe `--window max --warmup 150`, M3 빌드와 대조 빌드(main `55df0e6`)를 번갈아 3회씩, 모두 misses 0, 대부분 Hardware Composed: Independent Flip.

| 조건 | M3 p50 / p95 (ms) | 대조 p50 / p95 (ms) |
|---|---|---|
| 부하 없음 | 11.40~12.27 / 18.60~19.05 | 10.83~11.87 / 18.25~18.40 |
| 렌더 부하 | 9.64~11.21 / 17.82~18.77 | 9.77~12.82 / 17.18~18.26 |

- 부하가 있어도 같은 수준이고, M3와 대조 빌드도 같다.
- 오늘은 두 빌드 모두 M2 때(p50 5.45~6.27 / p95 8.43~9.12ms)보다 한 프레임 가까이 느리다. 같은 대조 빌드가 함께 느려졌으므로 M3 변화가 아니라 표시 환경 차이다. 원인은 M3-11에서 PresentMon 기록으로 함께 본다.
