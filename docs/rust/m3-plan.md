# M3 분해: 렌더·스케줄러 완성 (2026-10-07)

M3 종료 조건(계획 11절): 같은 render plan 규약, 표준 문서 목표·device loss 통과. 이를 다음 세 가지로 확인한다.

- 화면(편집 분할·진행 중 획·pen-up), 재생, 내보내기가 모두 한 `RenderPlan`을 평가한다. 품질 수준(배율)만 다를 수 있고 지우개·그룹·클리핑·합성 모드의 의미는 같다(계획 7.1절).
- 계획 10.2절의 표준 문서 목표를 측정해 통과하거나, 통과하지 못한 항목은 이유와 제품 판단을 기록한다. 각 항목은 2.2.13 측정값([m0-evidence.md](m0-evidence.md) 2·5절)보다 나쁘지 않아야 한다.
- 실제 드라이버 리셋(TDR)에서 문서와 편집 상태를 잃지 않고 표시가 돌아온다(scope.md 3.2절).

범위는 [scope.md](scope.md) 3절 기능표의 "레이어·그룹·클리핑·4개 합성 모드·불투명도 (M3 전체)"와 계획 7절, M2에서 넘긴 것([m2-plan.md](m2-plan.md) 9절), M0 위험표에서 M3로 넘긴 것([m0-close.md](m0-close.md): 타일 단위 취소, 창 모드 승격, TDR)이다.

## 1. 범위

| 넣는 것 | 빼는 것 (단계) |
|---|---|
| 그룹(중첩, 불투명도, 합성 모드), 클리핑, Normal·Multiply·Screen·Overlay | 채우기·이미지·선택·자르기·리사이즈 렌더 (M4) |
| `RenderPlan`: 문서 트리에서 한 번 만드는 평가 순서. 모든 경로가 이것만 평가 | 마커·에어브러시·스프레이 (M4) |
| 타일 단위 레이어 표면, 정적 레이어 캐시, 분할 캐시의 트리 일반화 | 썸네일 (M5, 레이어 패널 미리보기) |
| 작업 스케줄러: 우선순위, 오래된 요청 교체, 타일 단위 취소, 자원 예산 | 자동복구 (M5) |
| 미리보기 품질(표시 배율 렌더)로 재생, 4096² 재생 예산 | GIF·WebP 내보내기 (M5) |
| 레이어 패널의 그룹 조작: 그룹 만들기·풀기, 그룹 안팎 이동, 합성 모드·클리핑·불투명도 | 도킹 (M5) |
| 연산 상한 측정과 조정, 2560 창 승격 조사, 실제 TDR 시험, GPU 가속 판단 | 펜 장치 실증 (M6 전 gate) |

이번 빌드부터 그룹·클리핑·합성 모드가 든 `.ugu2`를 연다. M4 내용(채우기·이미지·선택·자르기·리사이즈, 펜 외 브러시)은 계속 열지 않고 안내한다.

## 2. 의미: 2.2.13을 따르는 것

C++ `src/render/engine/LayerHierarchyCompositor.hpp`, `src/render/LayerCompositionPlan.cpp`에서 확인했다. 3.0은 같은 의미를 `RenderPlan`으로 옮긴다.

| 항목 | 규칙 |
|---|---|
| 그룹 | 항상 격리: 투명한 표면에서 자식을 평가한 뒤 그룹의 합성 모드·불투명도로 부모 위에 그린다 (pass-through 없음) |
| 클리핑 | `clip_to_below` 레이어(또는 그룹)는 같은 부모 안에서 바로 아래의 클리핑이 아닌 형제(기준)의 alpha × 기준 불투명도로 잘린 뒤, 자기 합성 모드·불투명도로 그려진다. 연달아 있는 클리핑 레이어는 같은 기준을 쓴다 |
| 기준이 없을 때 | 기준이 숨김·불투명도 0·완전히 투명이거나 형제 맨 아래면 그 클리핑 레이어들은 그리지 않는다. 숨긴 클리핑 레이어는 기준을 바꾸지 않는다 |
| 합성 모드 | premultiplied RGBA8, sRGB 인코딩 값 기준(계획 7.1절). Multiply·Screen·Overlay는 W3C Compositing의 분리형 공식(Qt `CompositionMode_*`와 같은 정의) |
| 참조 레이어 | 화면에는 보이고 내보내기에서는 빠진다(M2와 같음). 그룹이 참조면 자식 전체가 빠진다 |

픽셀 단위 호환은 약속하지 않는다(계획 5.3절). 2.2.13과 같은 공식을 쓰되 반올림은 3.0 합성기의 규칙으로 고정한다.

사용자 결정 (2026-10-07): 레이어 표면이 메모리 예산을 넘는 문서도 느리게라도 동작해야 한다. 렌더러는 그때 내부 캐시로 일부를 미리 합칠 수 있지만, **문서의 레이어는 어떤 경우에도 합치지 않는다**(레이어 패널·저장 파일·편집 대상은 그대로).

사용자 결정 (2026-10-07, 성능과 메모리): 메모리 상한을 빡빡하게 걸지 않는다. 성능이 우선이다(요즘 그림 도구는 메모리를 많이 쓴다). 다만 벤치마크는 처음처럼 작업자 8스레드로 재서, 코어가 적은 PC에서도 잘 되는지를 기준으로 판단한다. 앱은 코어 수 − 1 스레드를 쓰고, 측정할 때는 `UGU_WORKER_THREADS=8`로 고정한다.

사용자 결정 (2026-10-07, UI): 3.0의 UI/UX는 2.2.13(C++) 화면을 기준으로 삼는다. 배치(도구 막대·오른쪽 도크·애니메이션 바·상태 막대), 기능 위치, 용어·번역, 단축키, 다크 테마와 앰버 강조색, 흔들리는 절차적 아이콘은 이어 가고, 간격·글자 위계·행 모양·컨트롤 세부처럼 더 낫게 할 수 있는 곳은 현대적으로 다듬되 바꾼 점을 기록한다. 아직 없는 기능(M4·M5)의 메뉴·버튼은 숨기고 그 기능이 들어올 때 C++ 자리에 넣는다. 화면 문구는 C++와 같은 영어 원문을 쓰고, 번역은 Fluent(`apps/ugurugu/i18n/*.ftl`)로 둔다. 한국어·일본어 번역문은 `tools/ts_to_ftl.py`가 2.2.13의 `.ts` 카탈로그에서 가져와 지금부터 시스템 언어로 보인다. 레이어 썸네일도 지금 넣는다. 그래서 M3-9가 이 UI 기반 작업을 포함한다.

## 3. 구조

M2는 문서 전체를 Vello 장면 하나로 그렸고, 레이어 불투명도도 Vello의 `push_layer`로 합성했다. M3는 이를 두 층으로 나눈다.

1. **레이어 표면:** 페인트 레이어 하나의 연산(지우개·isolated section 포함)을 Vello CPU로 그린 premultiplied 표면. 레이어 안의 의미는 M2 그대로다.
2. **합성:** `RenderPlan`을 따라 레이어 표면을 그룹·클리핑·합성 모드·불투명도로 합치는 우리 코드. 사각형(타일) 단위로 평가하고 스레드로 나눈다.

이렇게 나누는 이유:

- 전체 렌더, 편집 분할, pen-up 증분, 재생, 내보내기가 같은 합성 코드를 쓰므로 "같은 render plan 규약"이 구조로 성립한다. M2의 분할 합성은 Vello와 다른 공식이라 전체 렌더와 2단계까지 달랐다.
- Normal이 아닌 합성 모드는 아래 결과에 따라 달라지므로, M2처럼 위쪽 레이어를 미리 합쳐 두는 방식이 성립하지 않는다. 바뀐 사각형만 계획을 다시 평가해야 한다.
- 정적 레이어 캐시, 타일, 취소가 모두 레이어 표면 단위로 붙는다.

이 결정은 M3-1 측정과 M3-3 결과로 확인한다. 합성 비용 때문에 전체 렌더가 M2보다 느려지면 원인을 측정해 고친다(타일로 빈 영역 건너뛰기, 스레드 분할).

### M3-7·M3-8 GUI 확인 (2026-10-07, release, 2400×1500 창, 문서를 연 뒤 10초)

`idle_probe.py`(scratchpad)가 앱을 `UGURUGU_LOG=ugurugu=trace`로 띄우고, 유휴 10초 → `P` 재생 15초 → 재생 중 최소화 10초 → 복원 5초 → 정지 → 유휴 10초 → 최소화 10초를 거치며 로그의 렌더(`canvas split rendered`, `playback frame rendered`)와 업로드(`canvas uploaded`)를 구간별로 세고, 0.5초마다 working set을 읽는다.

| 문서 | 유휴 / 재생 중 최소화 / 정지 뒤 유휴 / 정지 뒤 최소화 | 재생 렌더 | 최대 working set: 처음 → 분할 놓기 → Vello 놓기 → 표시 표면 넘기기 |
|---|---|---|---|
| ②p 2048², 표시 배율 그대로(프레임 16MiB) | 렌더·업로드 0 / 0 / 0 / 0 | 30프레임 각 1회 | 1279 → 1057 → — → 951MiB |
| ⑤p 4096², 1/2 축소(프레임 16MiB) | 0 / 0 / 0 / 0 | 30프레임 각 1회 | 1321 → 1088 → 1025 → 964MiB |

- **분할 놓기:** 재생은 분할을 쓰지 않고, 정지하면 멈춘 프레임의 분할을 새로 만든다. 그런데도 재생 내내 이전 분할이 레이어 표면(`Arc`)을 쥐어, 렌더러가 그 표면을 재생에 다시 쓰지 못하고 새로 할당했다. 재생을 시작할 때 놓는다.
- **Vello 놓기:** 할당량을 세는 임시 전역 할당자로 재 보니 ⑤p 분할 뒤 힙이 표면·표시 합계보다 약 170MiB 컸고, 렌더 뒤 컨텍스트를 새로 만들면 112MiB가 줄었다. Vello 컨텍스트(작업자용 1개와 스레드별 1개)가 가장 큰 레이어를 그린 작업 메모리를 계속 쥐는 것이다. 작업자가 할 일이 없어질 때 놓는다. 다음 렌더가 다시 할당하는 비용은 없었다(`UGU_RELEASE_SCRATCH`로 분할마다 놓아도 획 뒤 분할 ②p 18.1 → 18.2, ⑤p 52.7 → 50.0ms, 2회 교대).
- **표시 표면 넘기기:** 편집 표시 표면(⑤p 64MiB)을 재생의 첫 보이는 프레임으로 넘겨 다음 프레임이 보이면 놓인다. 정지하면 멈춘 프레임을 분할이 올 때까지 계속 보인다. 이전에는 정지 직후 분할이 올 때까지(⑤p 약 170ms) 재생을 시작한 프레임이 잠깐 보였다.
- 남은 메모리(⑤p 재생, 힙 약 600MiB): 프레임 30 × 16MiB = 480, 1/2 레이어 표면 64, 그 밖 약 60MiB. 힙 밖(GPU 드라이버·업로드 staging·코드)은 작은 문서 유휴 때 약 220MiB, 재생 중 약 300MiB다. 768MiB 예산(표면 + 프레임)을 다 쓰는 문서는 힙 밖을 더하면 1GiB를 넘을 수 있다. 표준 문서는 안에 든다.

**pen-up (앱):** ②p를 열어 현재 레이어에 `SendInput`으로 30획: `pen-up shown` p50 1.44 / p95 1.65 / 최대 1.79ms, 오류 0.

**바쁜 작업자 중 입력→표시:** M3에는 그리는 동안 작업자를 계속 바쁘게 하는 경로가 없다(재생 중에는 present가 계속되어 latency-probe로 잴 수 없고, PNG 내보내기는 한 프레임이다). 그래서 같은 렌더 코드를 작업자와 같은 8스레드로 도는 `ugu-doc render ⑤p 8`을 옆에서 반복해 CPU·메모리 대역 부하를 만들고 쟀다. ### M3-11 2560 창 승격과 느렸던 기준선 (2026-10-07, release, latency-probe `--warmup 150`, PresentMon `--no_track_input`)

**한 프레임 느렸던 기준선:** 모든 scratchpad의 PresentMon 기록을 다시 보면, M0·M2 측정(10-06~10-07 오전)은 화면 갱신 간격이 6.2ms의 배수(160Hz)였고 M3-7·M3-8 GUI 확인(10-07 오후)은 16.67ms의 배수(60Hz)였다. 표시 방식은 둘 다 Independent Flip이고 늘어난 것은 present → 표시(중앙값 5.2 → 9~10ms)뿐이다. 주 모니터(3840×2160, 23~160Hz)가 그 사이 60Hz로 바뀌어 있었다. 사용자가 160Hz로 되돌린 뒤 최대화 창에서 번갈아 3회씩 쟀다. 모두 misses 0, 100% Independent Flip:

| 창 | M3 p50 / p95 (ms) | 대조(main `55df0e6`) p50 / p95 (ms) |
|---|---|---|
| 최대화 | 5.96~6.08 / 8.51~8.53 | 5.53~5.93 / 8.12~8.37 |
| 2560×1600, 다른 앱이 계속 그릴 때 | 기록 없음(아래) | 기록 없음 |
| 2560×1600, 그 앱을 최소화 | 5.15~5.89 / 8.22~8.86 | 5.75~5.87 / 8.66~8.72 |

M2 기준(최대화 p50 5.45~6.27 / p95 8.43~9.12ms)과 같은 수준이다. M3-7의 "바쁜 작업자 중" 측정은 60Hz에서 두 빌드를 함께 잰 것이라 결론(부하·빌드 사이 차이 없음)은 그대로다.

**2560 창 승격:** 처음 2560 창 측정은 두 빌드 모두 PresentMon에 present가 1~6개만 남아 잴 수 없었다. 같은 배치에서 앱의 로그와 DXGI 통계를 보면 앱은 끄는 동안 계속 그리고 표시했다(2초에 80프레임). 시스템 전체를 5초 기록하니 뒤에 있던 Claude 데스크톱 창이 160fps로 계속 present하며 Hardware Composed: Independent Flip(하드웨어 오버레이 평면)을 쓰고 있었고, DWM은 5초에 8번만 합성했다. 그 창을 최소화하자(DWM만 5초에 14번) 2560 창이 100% Independent Flip으로 승격되고 PresentMon도 모든 프레임을 기록했다. 오버레이 평면은 수가 정해져 있어 다른 창이 쓰고 있으면 우리 창은 DWM 합성(Composed: Flip)으로 남고, 그 상태에서는 PresentMon이 우리 창의 합성 프레임을 마무리하지 못했다. 앱의 스왑체인 설정 문제가 아니므로 앱에서 고칠 것은 없다. 측정할 때는 계속 그리는 다른 창을 최소화하고, 시작 전에 시스템 전체를 5초 기록해 확인한다.

### M3-12 실제 TDR (2026-10-07, release, 최대화 창, ②p, 160Hz)

`tdr_test.py`(scratchpad)가 ②p 사본을 최대화 창으로 열고, 관리자 권한의 `dxcap -forcetdr`로 실제 드라이버 리셋을 일으킨다(화면 전체가 꺼졌다 켜지고 다른 GPU 앱도 장치를 잃는다). 순서: 유휴(전후 창 화면을 화소 단위로 비교) → 획을 긋는 도중(버튼을 누른 채 리셋, 복구 뒤 계속 그어 놓기) → 재생 중 → PNG 내보내기 대화 상자에서 Enter 직후 → Ctrl+S 저장. 입력 직전마다 맨 앞 창이 앱(또는 앱의 대화 상자)인지 확인한다.

처음 실행에서 드러난 것과 고친 것:

1. **복구 뒤 창이 흰색으로 남았다.** 앱은 새 장치로 그리고 재생 프레임도 진행했지만 화면에는 나오지 않았다. 복구가 처음 만든 wgpu `Instance`(그 DXGI factory)로 새 스왑체인을 만들고 있었다. 실제 드라이버 리셋 뒤에는 이전 factory가 더는 현재 것이 아니다(RemoveDevice는 앱 장치만 제거해 드러나지 않았다). 이제 복구할 때마다 UI 스레드가 새 `Instance`와 surface를 함께 만든다.
2. **레이어 썸네일이 사라졌다.** 새 장치에는 egui 글꼴 아틀라스만 다시 올리고, M3-9의 썸네일 텍스처(egui가 화소를 보관하지 않음)는 없었다(`Missing texture` 경고 16개). 복구 때 레이어 도크가 텍스처를 버리고 캔버스의 썸네일 화소로 다시 만든다.
3. **새 스왑체인이 한 프레임만 보이고 멈췄다.** 복구 직후 첫 프레임 뒤로 프레임 지연 waitable이 다시 신호하지 않아 프레임 대기가 계속 시간 초과됐다(6초에 57회). 그동안 키 입력·재생·대화 상자 결과가 처리되지 않았다. 복구 전에 5초 기다리면 생기지 않고 바로 만들면 절반쯤 생겨, 디스플레이가 아직 리셋 중일 때 만든 스왑체인으로 보인다. OS는 준비됐다는 신호를 주지 않으므로, 복구 뒤 프레임 대기가 1초 넘게 풀리지 않으면 표시(장치·스왑체인)를 다시 만든다(최대 3번, 두 번째 프레임이 지나가면 확인을 끝냄). 평소 동작에는 영향이 없다.

결과: 고친 빌드로 TDR 12회(짧은 시험 4회, 전체 시험 2회 × 4) 모두 복구했다. 멈춘 스왑체인을 다시 만든 것이 그중 9회이고, 모두 한 번에 회복했다(포기 0회).

| 상황 | 확인 |
|---|---|
| 유휴 | 복구 뒤 창 화면이 리셋 전과 화소 단위로 같다(썸네일 포함, 창 밖 테두리 11px 띠 제외) |
| 그리는 중 | 버튼을 누른 채 리셋해도 획이 이어지고, 놓은 뒤 pen-up 표시. 저장 파일의 연산이 1680 → 1681 |
| 재생 중 | 복구 뒤에도 프레임이 이어서 표시된다 |
| 내보내기 | 리셋 직후 PNG가 기록되고(1.66MB) 저장도 성공한다. 내보내기 렌더는 CPU라 리셋과 무관하다 |

장치 손실부터 마지막 교체까지(이후 처음 화면 갱신 직전): 1.8~4.3초. 그중 약 1.5~2초는 새 장치를 여는 시간이고, 다시 만들 때는 1초의 확인 시간과 약 0.5초가 더 든다. M0의 RemoveDevice(0.4~0.9초)보다 긴 것은 드라이버·DWM 자체의 리셋 때문이다. 리셋 직후 Windows가 GPU 오디오 장치를 다시 잡으며 알림을 띄운다(앱과 무관).

- 작업자 스레드를 8에서 코어 수 − 1로 늘렸다(사용자 결정: 성능 우선). 옆에서 23스레드 렌더 부하를 걸어도 입력→표시는 p50 5.22~5.31 / p95 8.11~8.14ms로 부하 없음(5.91~6.07 / 8.79~9.03ms)과 같다.

### M3-14 획 윤곽과 종료 측정 (2026-10-07, release)

**윤곽 (`ae46c14`):** 표본 원 하나는 대부분 양옆 띠 안에 있다. 그래서 두 띠 밖으로 나오는 부분만 그린다(꺾이는 바깥쪽 호, 양 끝 모자). 띠와 그 부분을 한 획 안에서 윤곽 하나로 잇는다(오른쪽 가장자리 → 끝 모자 → 왼쪽 가장자리 → 시작 모자). 반대 방향으로 지나는 현만 지웠으므로 모든 점의 감김수는 조각을 따로 그릴 때와 같다. 칠해지는 집합은 M2 결정대로 원과 띠의 합집합이다. 사용자 결정(2026-10-07): 결정 문구는 유지하고 그리는 방식만 바꾼다.
- 시험은 지그재그·되돌아오는 획·필압 급변·나선에 펜 1·12·40px와 흔들림 0·1.6·12를 쓴다. 경계에서 0.01px보다 먼 모든 화소 중심이 해석적으로 구한 합집합과 안팎이 같다.

- 진행 중 획은 조각 단위 그대로다. 꺾임을 판정하려면 다음 띠까지 보아야 해서, 표본을 확정하는 시점이 한 표본 늦다. 시험: 진행 중 표시가 전체 렌더와 같음(M3-6), 축소 렌더 허용 오차(M3-8).

## 9. M3 종료 조건 대비 (2026-10-07)

| 조건 | 상태 |
|---|---|
| 화면·재생·내보내기가 한 `RenderPlan`을 평가 | 충족. 편집 분할·진행 중 획·pen-up·재생·PNG가 같은 계획과 합성기를 쓴다. 다른 것은 배율(재생 축소, M3-8)과 재생 표본 간격(M3-13)뿐이다. 분할 화면은 전체 렌더와 바이트 단위로 같고, 예산 초과 축약 프로그램은 2단계 이내다(시험) |
| 표준 문서 목표 | 미달 1개를 빼고 충족(m0-evidence 11절). 미달은 ②p 30fps 처리 능력이다. 8스레드에서 원본 크기 프레임 p50 40ms로 25fps 수준이라, 25fps 문서는 첫 바퀴 뒤 유지하고 첫 바퀴는 1.35s(23스레드 1.67s)로 2.2.13(1초 뒤 25fps)보다 0.2~0.5초 늦다. 나머지 목표는 2.2.13보다 나쁘지 않다. RAM만 2.2.13의 2~3배이며 1GiB 예산 안이다(사용자 결정: 성능 우선). 사용자 결정(2026-10-07): 이 미달을 M3에서 받아들이고 M4의 첫 항목으로 넘긴다. 문서 fps는 유지되고, 원인(레이어 사이 일 분배)이 측정되어 있으며, 고치는 일이 측정부터 해야 하는 스케줄러 변경이기 때문이다 |

- **②p 30fps 처리 능력과 첫 바퀴:** 레이어를 레이어마다 1스레드로 그려서 14레이어가 8스레드에서 두 바퀴를 돈다. 남은 큰 비용은 래스터(스레드 합 88ms)다. 레이어 사이 일을 고르게 나누는 것(획 단위 윤곽을 모든 스레드로, 비싼 레이어부터)을 먼저 잰다.
- **render 스레드 점유:** pen-up 뒤 render 스레드가 처음 쉬기까지 ②p p95 10.5ms(8ms 초과). 다음 획 입력은 막지 않는다.
- **GUI 편집 측정 재확인:** batch·pen-up GUI 값은 새 윤곽 전 빌드(M3-13)의 것이다. 새 윤곽 뒤에는 headless로만 쟀다(pen-up p95 2.4ms 이하).
- **M4 연산:** 선택·채우기·자르기·리사이즈·이미지를 같은 계획 위에 올리고, `semantics.rs` 의미 시험을 같은 방식으로 늘린다.
