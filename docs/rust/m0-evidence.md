# M0 측정·실증 기록

환경은 [scope.md](scope.md) 1절(주 모니터 UHD 60Hz 150%, RTX 5080, 마우스만). 측정일 2026-10-06.

## 1. 입력→화면 표시 지연

도구: `tools/latency-probe` + PresentMon 2.6.0(Intel 서명 확인, 관리자 권한). 두 앱을 같은 도구, 같은 절차로 잰다.

1. 도구가 PresentMon(`--no_track_input`)을 먼저 시작한 뒤 앱을 실행한다.
2. 창을 2560×1600 외곽 크기(client 2538×1549)로 맞춘다.
3. 주 버튼을 누른 채 캔버스 중앙의 나선(반경 = client 짧은 변 × 0.12) 획을 `SendInput`으로 한 칸씩 늘린다. 칸 사이에는 15~40ms 무작위 간격을 두어 vsync 위상과 상관을 없앤다.
4. 칸마다 다음 입력 전의 첫 present를 응답으로 본다. 지연은 `SendInput` 직전 QPC에서 그 present의 `TimeInQPC + MsUntilDisplayed`까지다.

이 값은 scanout 시작까지이며 패널 응답 시간은 포함하지 않는다. "입력 뒤 첫 present = 응답"이 성립하려면 앱이 유휴 상태에서 present하지 않아야 한다. 두 앱 모두 유휴 5초 동안 present 0회였다. C++ 앱은 시작 시 우글거림 재생이 켜져 있으므로 `P`로 정지한 뒤 잰다(재생 중 대조군: 5초에 122회).

### 결과: 워밍업 후 (2026-10-07, 교대 3회 × 100칸, 누락 0)

DWM은 창을 옮기거나 크기를 바꾼 뒤 한동안 swapchain을 합성하고, 앱이 일정 시간 present한 뒤에야 Independent Flip으로 올린다(4절). 그래서 측정 전에 같은 획을 150칸 그려(`--warmup 150`, 통계 제외) 두 앱을 같은 상태로 맞췄다. C++는 `6c96784` 트리 Release, Rust는 `49b5809`(Vello CPU 캔버스 표시) 이후 빌드다.

| 앱 | 입력→present p50 / p95 (ms) | 입력→표시 p50 / p95 / max (ms) | 표시 방식 |
|---|---|---|---|
| C++ 2.2.13 | 3.90~5.15 / 7.11~7.56 | 9.62~10.89 / 12.88~13.43 / 13.96~14.24 | 100% Independent Flip |
| Rust | 2.02~2.09 / 3.46~3.69 | **5.89~6.40 / 8.47~9.02** / 9.82~10.32 | 100% Independent Flip |

**같은 표시 방식에서 Rust는 C++보다 입력→표시가 p50 약 4ms, p95 약 4.3ms 빠르다.** present까지가 빠르고(대기 → 최신 입력 → 렌더 순서), 표시까지도 짧다.

### 이전 결과: 워밍업 없음 (2026-10-06, 폐기)

아래 표는 창을 배치한 직후부터 쟀다. C++는 시작 시 재생이 켜져 있어 측정 전에 이미 승격됐고, 유휴 중 present하지 않는 Rust는 측정 대부분이 승격 전이었다. 그래서 "Rust가 약 1ms 느리다"는 결론은 측정 절차 때문이었다.


C++ 2.2.13은 `6c96784` 트리 Release(Qt 6.11.2), Rust는 presenter 구조(`ac95414` 이후) 빌드다.

| run | 앱 | 입력→present p50 / p95 (ms) | 입력→표시 p50 / p95 / max (ms) | 표시 방식 |
|---|---|---|---|---|
| 1 | C++ | 5.17 / 7.61 | 10.98 / 13.29 / 13.79 | Hardware Composed: Independent Flip |
| 1 | Rust | 2.25 / 4.29 | 11.72 / 15.23 / 16.07 (98/100 표시) | 대부분 Composed: Flip |
| 2 | C++ | 4.96 / 7.72 | 10.77 / 13.69 / 14.59 | Hardware Composed: Independent Flip |
| 2 | Rust | 2.35 / 4.14 | 12.16 / 14.87 / 16.86 | Composed: Flip |
| 3 | C++ | 4.40 / 8.16 | 10.12 / 13.96 / 15.51 | Hardware Composed: Independent Flip |
| 3 | Rust | 2.23 / 4.00 | 11.68 / 15.01 / 16.93 | Composed: Flip |

당시 결론(폐기): Rust 실증 앱은 C++보다 입력→표시가 p50 약 1ms, p95 약 1.3ms 느리다. Rust는 present까지는 더 빠르지만, DWM이 swapchain을 한 번 더 합성한다(Composed: Flip). C++ 캔버스는 MPO 오버레이로 바로 표시된다. 이 차이를 없애는 것이 다음 과제다(4절).

Rust의 개별 칸 지연은 egui Painter를 쓰던 이전 빌드(`bd3981e`)와 같다(p50 11.60 / p95 14.87ms, 60칸). presenter가 개선한 것은 연속 입력이다. 약 2ms 간격 연속 이동에서 입력→present 반환이 p50 약 32ms에서 약 6ms로 줄었다. 입력→표시는 p50 11.64~11.79ms, p95 13.06~13.29ms(앱 자체 통계, 4회, 입력 502~506개 무손실)다. C++의 연속 입력 지연은 이 도구 방식으로는 아직 재지 않았다.

### 앱 자체 계측(DXGI 통계)과 교차 검증

`ugu_render::present::Presenter`는 present 직후 `GetLastPresentCount`로 번호를 기억한다. 이후 `GetFrameStatistics`가 그 번호를 화면에 띄운 present로 보고하면, 그 `SyncQPCTime`을 표시 시각으로 쓴다. 통계를 읽기 전에 교체된 present는 시각을 추정하지 않고 버린다.

같은 실행을 PresentMon과 프레임 단위로 짝지어 보았다(present 시각 2ms 이내, 4회). 결과는 다음과 같다.

- 연속 입력: 227/227, 228/228 짝지음
- 칸 패턴: 101/102, 102/103 짝지음
- DXGI 표시 시각 − PresentMon 표시 시각: 중앙값 −0.02~0.01ms, p95 2.0~2.5ms, 최대 3.0ms. 77~88%가 1ms 이내다.

즉 DXGI 통계는 같은 프레임에 대해 같거나 최대 3ms 늦게 보고한다(보수적).

### 측정 함정과 정정

- **PresentMon 입력 추적(기본값)은 측정 대상의 지연을 늘린다.** 같은 Rust 실행에서 입력→표시 p50이 11.7ms에서 18.0ms로 늘었다. 이 상태로 잰 이전 C++ 기록(p50 24.7~26.1 / p95 32.6~33.3ms)은 폐기한다. 도구는 이제 `--no_track_input`으로 실행한다.
- **"PresentMon이 wgpu DX12 present를 놓친다"는 이전 결론은 근거가 부족했다.** 현재 빌드는 대부분의 실행에서 모든 present가 기록된다. 다만 같은 조건에서도 가끔 실행 전체의 기록이 1~3프레임뿐인 경우가 재현되며, 원인은 아직 확정하지 못했다. 도구는 칸마다 응답 present 유무(`misses`)를 보고하므로, `misses`가 0이 아닌 실행은 버린다. 위 표의 실행은 모두 0이다.
- **로그 I/O가 렌더 스레드를 막았다.** 측정 스크립트가 앱 stdout을 끝까지 읽지 않은 채 trace·debug 로그를 켜면, 꽉 찬 파이프 때문에 렌더 스레드가 멈춰 present가 21~24회로 줄었다(입력 505개는 모두 도착). 앱은 이제 비차단 writer(`tracing-appender`)로 로그를 쓰므로, 로그 출력이 막혀도 그리기는 멈추지 않는다.
- **Desktop Duplication 방식은 폐기했다.** duplication이 켜지면 앱의 표시 방식이 Composed Flip으로 바뀌고, `LastPresentTime`은 표시가 아니라 present 시각에 가깝다. 이 방식의 기록(C++ p50 28ms, Rust 3.5ms)은 쓰지 않는다.

## 3. 입력 경로에서 확인한 사실

1. **winit은 펜 pointer 메시지를 `Touch`로 바꾸고 history 항목마다 현재 필압을 넣는다**(winit 0.30.13 `event_loop.rs` WM_POINTER 처리). barrel·eraser·hover도 없다. 그래서 `ugu-win`이 창을 subclass해 `WM_POINTER*`를 직접 받는다. `WM_POINTERCAPTURECHANGED`는 send 메시지라 message hook으로는 받을 수 없다.
2. **마우스 pointer 프레임에는 coalesced history가 없다**(`historyCount`가 항상 1). 이벤트 루프가 present를 기다리는 동안의 이동은 메시지 하나로 합쳐진다. `SendInput` 이동 약 500회 중 97~107개만 도착했다. `GetMouseMovePointsEx`로 복원한 뒤에는 3회 모두 505/506/505개(버튼 이벤트 포함)가 도착했고 궤적이 입력과 일치했다.
3. **절대 좌표 입력은 이동 버퍼와 커서 위치를 1px 다르게 반올림한다.** 정확한 (x, y, time) 질의는 대부분 실패한다. 같은 시각의 ±1px 이웃까지 찾고, 그 오프셋으로 복원점을 커서 좌표계에 맞춘다. 펜 태블릿의 마우스 모드 같은 실제 절대 장치도 같은 경로를 탄다.
4. **같은 밀리초에 여러 이동이 들어온다.** 복원점 시각은 ms 단위라 펜 history용 (시간, frame) 중복 제거에 넣으면 지워진다. 마우스는 버퍼 순서로만 정렬한다.
5. **`SetCursorPos`는 pointer 프레임을 만들지 않는다.** 자동 시험은 실제 입력 스트림인 `SendInput`을 써야 한다.
6. **egui-winit은 `RedrawRequested`에도 `repaint: true`를 돌려준다.** 이를 따라 다시 redraw를 요청하면 vsync마다 끝없이 그린다. 수정 전 Rust 앱은 유휴 상태에서도 16.66ms마다 present했고, 수정 후에는 유휴 5초 동안 0회다.

## 4. 프레임 순서 결정 (presenter로 해결)

연속 이동(약 2ms 간격) 중 앱 내부 지표(입력 시각 → present 반환)는 p50 약 32ms였다. Fifo 기본값, Fifo + frame latency 1, Mailbox 모두 같았고 Immediate만 0.6ms였다(tearing 때문에 제품 설정이 아님).

원인은 순서다. 현재 루프는 입력을 모은 뒤 swapchain 획득에서 vsync를 기다리므로, 대기 동안의 입력이 다음 프레임으로 밀린다. 캔버스 표시 경로는 **획득(대기) → 최신 입력 수집 → 렌더 → present** 순서를 가져야 하고, 이벤트 스레드는 present를 기다리지 않아야 한다. egui-wgpu `Painter`는 획득을 내부에서 하므로 쓰지 않는다.

구현 (`crates/ugu-render/src/present.rs`, `apps/ugurugu/src/render.rs`):

- wgpu DX12 옵션 `Dx12UseFrameLatencyWaitableObject::DontWait`로 wgpu 내부 대기를 끈다. 앱이 `Surface::as_hal`의 frame-latency 핸들을 직접 기다린 뒤에 입력을 읽는다. 최대 frame latency는 1이다.
- UI 스레드는 winit 루프와 포인터 subclass만 맡고, 창·포인터 이벤트를 채널로 렌더 스레드에 보낸다. 렌더 스레드가 GPU, egui, 캔버스를 소유한다.
- 순서: 메시지 대기 → 대기 핸들 신호 → 그동안 쌓인 입력 다시 수집 → egui 실행과 tessellate → 획득(막히지 않음) → 렌더 → present.
- winit은 UI 스레드 밖에서 창 핸들을 꺼내지 못하므로, wgpu instance와 surface는 UI 스레드에서 만들어 넘긴다.
- DXGI는 swapchain 작업 중에 창 스레드로 메시지를 보낼 수 있다. 그래서 UI 스레드는 창이 살아 있는 동안 렌더 스레드를 막고 기다리지 않고, 렌더 스레드의 종료 통지(`EventLoopProxy`)를 받은 뒤에 끝낸다.
- 표시 통계를 읽는 일만으로는 다시 그리지 않는다. 그러지 않으면 측정이 present를 늘린다.

### Independent Flip 승격 (해결: 측정 절차 문제였음)

Rust 창 전체 swapchain이 Composed Flip으로 남는 것처럼 보여 아래를 차례로 시험했다. 모두 측정 직후 구간에서는 Composed였다.

- 2026-10-06: frame latency 1·2·3, 색 공간 `Auto`, `WS_EX_NOREDIRECTIONBITMAP`, OS 커서 숨김, hover 이동, wgpu `DxgiFromVisual`
- 2026-10-07: 둥근 모서리 끔(`DWMWCP_DONOTROUND`), 창 최대화, 캔버스만 자식 창 swapchain으로 분리. 셋 다 기본 구조와 같았다(Composed 72~79%). 모서리 가설은 기각했다.

PresentMon 기록을 present 순서대로 보면 원인이 드러난다. 두 앱 모두 처음에는 Composed였다가 한 번 Independent Flip으로 바뀐 뒤 다시 내려가지 않았다.

- C++: 시작 후 약 2.25초, 58~60번째 present에서 승격. 재생 중이라 측정 전에 끝난다.
- Rust: 앱이 뜬 직후 약 1.7초에 한 번 승격되지만, probe가 창 크기·위치를 바꾸면 내려간다. 그 뒤 약 80번 present하고(시작 후 약 5.9초) 다시 승격된다. 기본·최대화·모서리 끔·자식 창 모두 같다.

즉 DWM은 창 배치가 바뀐 뒤 앱이 한동안 present해야 다시 승격한다. 실제 사용에서는 창을 옮긴 직후 잠깐만 합성 경로다. 워밍업 150칸을 넣으면 세 조건 모두 100% Independent Flip이고, 자식 창 swapchain(p50 5.82~6.39 / p95 8.43~9.12ms)은 창 전체 swapchain(1절)과 차이가 없다.

**결정 (ADR):** 캔버스는 창 전체 swapchain 하나에 그리고, 그 위에 egui를 그린다. 자식 창 swapchain은 지연 이득이 없고 egui 팝업이 캔버스에 가려지는 airspace 문제만 생기므로 쓰지 않는다. 창 모서리도 그대로 둔다. 실험 장치(`UGURUGU_PRESENT`, `ugu_win::composition`)는 `81fe74f`에서 지웠다.

측정 도구에 남긴 것: `latency-probe --warmup N`(통계에서 빼는 앞 단계), `--window max`, swapchain별·표시 방식별 결과, 앱이 맨 앞에 있고 시작점 아래에 있을 때만 버튼을 누르는 안전장치.

### 입력 경로 버그 (화면 확인 중 발견, `b8341b1`에서 수정)

빠른 연속 입력에서 획 끝에 예전 커서 위치로 튀는 선이 그려졌다. 버튼을 뗀 프레임처럼 새 이동이 없는 프레임에서는 이동 버퍼의 첫 항목이 이전 프레임이 이미 전달한 항목인데, 건너뛴 이동을 찾는 검색이 두 번째 항목부터 시작해 그 항목을 지나쳤다. 그 결과 같은 밀리초의 이전 이동(이전 획의 끝, 새 획의 시작점)이 "건너뛴 이동"으로 다시 들어왔다. 검색을 첫 항목부터 하도록 고치고 회귀 테스트를 추가했다. 수정 후 기본·자식 창 각 3회에서 엉뚱한 구간은 0이었다.

## 5. 나머지 기준선 (C++ 2.2.13, 2026-10-07)

도구: `python tools/baseline_probe.py <stroke|save|open|cancel|memory> <Ugurugu.exe> <fixture> <출력 폴더>`. 2.2.13에는 내부 계측이 없으므로 모두 밖에서 잰다. 앱은 fixture 복사본으로 2560×1600 창에서 시작하고, 재생을 `P`로 멈춘 뒤 잰다. 측정 빌드는 1절과 같은 `6c96784` 트리 Release다. fixture ③은 `ugurugu_stress_document_generator 2048` 문서다.

- **UI 스레드 CPU**: 창 스레드의 `QueryThreadCycleTime` 차이를 같은 PC에서 보정한 클럭(약 3.6GHz)으로 나눈 값이다. 입력 하나부터 다음 입력까지 그 스레드가 실제로 실행한 시간이라, 그리기를 포함하고 대기는 뺀다. 재생을 멈춘 C++ 앱도 UI 스레드가 초당 약 4.8ms를 쓰는 타이머가 있어, 각 값에는 구간 길이만큼의 이 바닥값이 들어 있다(15~40ms 구간이면 0.1~0.2ms).
- **span**: 입력부터 UI 스레드가 처음 쉬기(2ms 넘는 공백) 전까지의 시간이다. 메인 스레드 점유 시간에 해당한다.

## 6. CPU 렌더러 비교 (10~11일차)

도구: `tools/render-bench`(`6b3468c`). 같은 결정적 문서를 tiny-skia 0.12.0과 Vello CPU 0.3.0(`u8_pipeline`, 단일 스레드와 `multithreading`)으로 그린다. 외곽선은 도구가 한 번 만들어 두 렌더러에 같은 경로를 넘기므로, 차이는 래스터화와 합성에서만 생긴다.

- 문서: 2048², 5레이어(Normal·Multiply·Screen·Overlay, Overlay 레이어를 바닥으로 하는 클리핑 그룹 1개), 2,000획 × 100점 = 200,000점. 획의 50%는 펜(일정 폭, 둥근 끝·이음), 30%는 필압(점마다 원 + 이웃 사이 사각형, non-zero 합집합), 20%는 에어브러시(방사형 그라디언트 dab). 모두 반투명이다.
- 단계: 레이어 래스터화 30프레임(프레임마다 점을 ±2px 흔듦), 흰 배경 위 합성, 레이어 하나의 선택 변형(12° 회전·1.15배, bilinear) 10회, 실시간 획 한 칸(dirty rect 안에서만 그림) 500회.
- 프로세스 하나에 렌더러 하나만 돌려 peak working set·private bytes를 렌더러별로 잰다. 각 단계 결과 이미지를 raw RGBA와 PNG로 남기고 `render-bench diff`로 비교한다.

재현: `render-bench run --renderer tiny-skia|vello|vello-mt[=N] --out DIR`, `render-bench diff DIR/tiny-skia-composite.rgba DIR/vello-composite.rgba DIR/heat.png`.

|---|---|---|---|---|
| 합성 | 0.39 | 99 | 9.3% | 1.4% |
| 선택 변형 | 0.27 | 130 | 4.1% | 0.8% |
| 실시간 획 | 0.29 | 142 | 4.4% | 1.0% |

Vello 단일 스레드와 다중 스레드 결과는 바이트 단위로 같다. tiny-skia와의 차이는 획 가장자리의 안티에일리어싱(tiny-skia는 scanline 수직 4배 supersampling, Vello는 면적 coverage)과 에어브러시 그라디언트 내부에 몰려 있고, 모양이 빠지거나 밀린 곳은 없다(차이 heatmap 확인). 어느 쪽이 C++ QPainter에 가까운지는 아직 비교하지 않았다. 2.2.13과의 비교는 같은 문서를 C++로 그리는 생성기가 있어야 한다.

정확성(2048², 1라운드): tiny-skia 대 Vello의 합성은 평균 채널 차 0.85, 최대 139, 차 > 2 픽셀 20.5%, 차 > 8 픽셀 2.9%다. 선택 변형은 0.59 / 127 / 10.1% / 1.7%, 실시간 획은 0.58 / 134 / 10.8% / 1.8%다. 512²보다 비율이 큰 것은 획이 더 촘촘하기 때문이다. heatmap에서 차이는 획 가장자리와 반투명 영역의 반올림에만 있고, 블렌드 결과가 면 단위로 다른 곳은 없다.

해석:

- Vello CPU는 1스레드에서도 래스터화 3.3~3.4배, 합성 1.5배, 변형 1.6배 빠르고, 8스레드에서는 tiny-skia 대비 래스터화 약 24배, 합성 약 10.5배다. 메모리는 비슷하다(다중 스레드 +10~25MiB).
- 실시간 획 한 칸은 두 렌더러 모두 수 µs로 입력 지연에 영향이 없다. 단 Vello 다중 스레드 context는 작은 작업에 분배 비용(약 0.1ms)이 더 크므로, 실시간 획은 1스레드 context로, 재생·전체 다시 그리기는 다중 스레드 context로 나눈다.
- 다른 문서라 직접 비교할 수는 없지만 참고로 C++ stress fixture ③(4레이어, 2,000획)은 프레임당 4.6s였다. 같은 규모에서 Vello 8스레드는 래스터화와 합성을 합쳐 약 55ms다.
- 남은 위험: `vello_cpu`는 0.x라 API가 바뀔 수 있다(이 비교는 0.3.0으로 고정). 어느 쪽이 C++ QPainter 결과에 가까운지는 아직 비교하지 않았다.

### SIMD 수준과 결정성

Vello CPU는 실행 시 CPU의 SIMD 수준을 골라 쓰므로, CPU가 다르면 픽셀이 달라질 수 있는지 확인했다(`render-bench --simd`, 이 PC가 가진 SSE2·SSE4.2·AVX2).

- SSE2와 SSE4.2는 모든 단계에서 바이트 단위로 같다(768², 400획).
- AVX2는 다르다. 2048²에서 합성 20픽셀(최대 ±2), 실시간 획 15픽셀, 선택 변형 25픽셀(±1)이며 알파는 같다. 원인은 방사형 그라디언트(`fine/common/gradient/radial.rs`)의 `mul_add`다. AVX2 경로는 이를 FMA 한 번(반올림 1회)으로, SSE 경로는 곱하기 뒤 더하기(반올림 2회)로 계산한다.
- SSE 경로는 Intel과 AMD에서 결과가 다른 근사 명령(`rcpps`·`rsqrtps`)을 쓰지 않는다. `sqrt`는 IEEE 규격상 정확히 반올림된다. 따라서 수준을 고정하면 CPU 제조사와 관계없이 같은 결과가 나온다.

속도(2048², 교대 3회, p50 ms):

| 단계 | SSE4.2 1스레드 | AVX2 1스레드 | SSE4.2 8스레드 | AVX2 8스레드 |
|---|---|---|---|---|
| 래스터화 | 351.0~357.8 | 341.1~346.7 | 48.3~51.9 | 48.0~49.6 |
| 합성 | 41.8~43.0 | 55.4~56.9 | 5.2~5.5 | 8.0~8.1 |
| 선택 변형 | 21.6~22.4 | 23.3~25.1 | 2.9~3.0 | 2.7~3.0 |

SSE4.2는 1스레드 래스터화가 약 3% 느리고 합성은 오히려 25~35% 빠르다. 그래서 문서 렌더러는 SSE4.2로 고정한다(`ugu_render::raster::document_level`, Windows 11 24H2부터 필수 명령어 집합). SSE4.2가 없으면 같은 결과를 내는 SSE2로 떨어진다. 다른 PC 사이의 일치는 이 PC 안에서 수준을 바꿔 확인한 것이고, 다른 제조사 CPU에서 직접 비교한 것은 아니다.

### Vello GPU (2026-10-07, 교대 3회, 2048², SSE4.2)

`render-bench --renderer vello-gpu`(Vello GPU 0.3.0, wgpu 30 DX12, RTX 5080)는 같은 문서와 단계를 GPU 텍스처 위에서 수행하고, 단계마다 GPU 완료까지 기다린 시간을 잰다. Vello CPU 8스레드와 번갈아 실행했다.

| 단계 p50 / p95 (ms) | Vello GPU | Vello CPU 8스레드 |
|---|---|---|
| 래스터화 (프레임당) | 230.3~230.8 / 233.0~234.1 | 45.2~46.0 / 55.3~56.5 |
| 합성 | 1.51~1.55 / 1.83~2.13 | 4.88~4.97 / 5.46~5.68 |
| 선택 변형 | 0.45~0.52 / 0.56~0.89 | 2.66~2.69 / 2.80~2.92 |
| 실시간 획 한 칸 | 0.33~0.35 / 0.50~0.56 | 0.10~0.11 (1스레드 0.003) |
| peak working set / private (MiB) | 328~330 / 779~780 | 231~244 / 245~253 |

- 래스터화는 GPU가 5배 느리다. Vello GPU는 경로를 strip으로 바꾸는 전처리를 CPU 한 스레드에서 하므로, 이 문서에서는 그 단계가 병목이다.
- 합성·변형은 GPU가 3~6배 빠르지만 원래 수 ms다. 실시간 획 한 칸은 제출·대기 비용 때문에 Vello CPU 1스레드보다 100배 느리다.
- 출력 차이(Vello CPU 대비, 2048² 합성): 평균 0.61, 최대 20, 차 > 8 픽셀 0.04%.

결론: 재생(전체 다시 그리기)에도 Vello CPU 다중 스레드가 빠르다. Vello GPU 보류 결정을 유지한다. 합성·변형을 GPU로 옮기는 것은 수 ms 단위 최적화이므로, 필요할 때 표시 경로(wgpu)에서 직접 한다.

## 7. IME 실증 (8~9일차, 한국어·일본어)

환경: 주 모니터 150%, Microsoft 한국어 IME와 Microsoft 일본어 IME(입력 언어 0411, 2026-10-07 추가). 앱의 IME probe(`apps/ugurugu/src/ime_probe.rs`)는 한 줄·여러 줄 TextEdit과, 텍스트를 편집하지 않을 때만 세는 캔버스 단축키(Enter, Ctrl+Z)를 둔다. CJK 글꼴은 M0에서만 시스템 글꼴(맑은 고딕, Yu Gothic)을 fallback으로 붙인다(제품은 글꼴을 번들한다).

재현: `python tools/ime_probe.py <ko|ja> <ugurugu.exe> <출력 폴더> [창 x,y]`. 창 위치로 모니터, 곧 배율을 고른다. 실제 IME에 `SendInput` 키 입력을 보내고(한/영·한자 키 포함), 앱이 로그로 남긴 텍스트와 단축키 횟수를 비교한다. 주 모니터(150%, RTX 5080)에서 2회 연속, 보조 모니터(100%, Intel iGPU 연결, 렌더는 RTX 5080)에서 1회 모두 같은 결과다. 보조 모니터로 옮기면 창이 배율에 맞게 다시 계산되고, 후보창은 두 배율 모두 같은 상대 위치에 뜬다.

| 시험 | 입력 | 결과 |
|---|---|---|
| 조합 후 Enter (한 줄) | `gksrmf` Enter | "한글", 캔버스 Enter 0 |
| 조합 중 지우기 | `dkssudgktpdy` Backspace `y` | "안녕하세요" (Backspace는 조합 중 "요"를 "ㅇ"으로 되돌림) |
| 받침 이동 | `rkqtdl` | 값 → 값ㅇ → "값이" |

조합 중 글자는 TextEdit 안에 강조 표시되고, 한글·한자는 fallback 글꼴로 그려진다.

### 발견해 고친 것

1. **캔버스를 눌러도 텍스트 칸이 포커스를 유지했다.** 포인터 라우터가 캔버스 입력을 egui에 보내지 않으므로 egui가 포커스를 놓을 기회가 없었다. 그래서 캔버스를 누른 뒤의 Enter는 텍스트에 줄바꿈을 넣고, Ctrl+Z는 TextEdit의 undo로 갔다. 캔버스 획이 시작되면 `stop_text_input`으로 포커스를 놓는다(`3d91d5e`).
2. **단축키는 키 이벤트 자신의 modifier로 판정해야 한다.** Ctrl 누름·Z 누름·떼기가 한 프레임에 함께 도착하면, 프레임 끝의 modifier 상태는 이미 "없음"이다. `InputState::consume_key`처럼 이벤트마다 modifier를 비교한다. M2 이후 단축키 체계도 이 규칙을 따른다.

후보 순서는 MS IME가 앞선 선택을 학습해 실행마다 바뀐다(두 번째 후보가 "漢字"와 "感じ" 사이에서 번갈았다). 그래서 이 항목은 특정 글자가 아니라 후보 확정과 Enter 누출 없음으로 판정한다.

**첫 시도가 실패한 원인은 시험 도구도 앱도 아니라 이 PC의 설치 상태였다.** 입력 언어 목록에 일본어만 추가되고 일본어 기본 입력 기능(`Language.Basic~~~ja-JP~0.0.1.0`)이 없어서 시스템 사전(`C:\Windows\IME\IMEJP\DICTS`의 `SDDS0411.DIC` 등)이 없었다. 이 상태에서는 창의 HKL이 0411로 바뀌어도 IME가 열리지 않는다. 앱 대신 표준 Win32 EDIT 창에 `VK_IME_ON`, Alt+\`, `VK_DBE_HIRAGANA`를 보내도, `IMC_SETOPENSTATUS`로 직접 열어도 로마자가 그대로 들어갔다. `dism /online /add-capability`로 기능을 설치하자 같은 키로 바로 열렸다. 이 PC는 앱별 입력 언어 전환이 꺼져 있어(`IsLegacySwitchingMode` False) 전환이 데스크톱 전체에 남는다. 그래서 probe는 창 스레드의 HKL로 전환을 확인하고, 끝나면 원래 입력 언어로 되돌린다.

### 125%·200% 배율 (2026-10-07)

`python tools/display_scale.py <배율>`로 주 모니터 배율을 바꿔(설정 앱과 같은 DisplayConfig 경로, 즉시 적용) 한국어·일본어 probe를 각 1회 돌린 뒤 150%로 되돌렸다. 두 배율 모두 위 표와 같은 결과다. 후보창은 150%와 같은 상대 위치(TextEdit 왼쪽 아래)에 뜨고, 글자와 후보창 모두 배율에 맞는 크기로 그려진다.

### 발견해 고친 것 (일본어)

3. **fallback 글꼴의 글자가 기준선 위로 떴다.** "私は学生です"에서 맑은 고딕에 없는 "学"만 Yu Gothic으로 그려지면서 약 4.7pt 위에 그려져, 칸 위쪽에 걸려 잘려 보였다. epaint는 다른 글꼴의 글리프를 섞을 때 행 높이 차이의 절반만큼 세로 가운데를 맞추는데, 행 높이에 line gap이 포함되므로 line gap이 큰 Yu Gothic은 위로 올라간다(glyph atlas의 비트맵은 정상이었다). 앱 시작 시 epaint의 배치로 기본 글꼴과 각 fallback 글꼴의 기준선 차이를 재서 `FontTweak::y_offset_factor`에 넣는다(Yu Gothic +0.279, 맑은 고딕 −0.066). 맑은 고딕의 한글도 그동안 약 0.9pt 아래로 처져 있었다. 제품이 글꼴을 번들해도 같은 방식으로 맞춘다.

### 접근성 (UI Automation, 2026-10-07)

Narrator 같은 화면 낭독기는 UI Automation(UIA)으로 앱을 읽는다. egui-winit의 AccessKit을 켜고, `tools/uia_probe.ps1`(Windows PowerShell 5.1의 .NET UIA 클라이언트)로 트리를 읽고 조작했다.

- 창, 텍스트, 텍스트 칸, 버튼이 이름과 함께 노출된다(`Edit "Line"`, `Button "Clear"` 등).
- UIA로 텍스트 칸에 포커스를 준 뒤 키보드로 입력하면 값이 들어가고, ValuePattern으로 읽힌다.
- 버튼은 InvokePattern으로 눌린다.
- **egui의 TextEdit는 ValuePattern.SetValue를 받지 않는다**(AccessKit 동작 중 Focus·SetTextSelection만 처리). 화면 낭독기 사용자는 키보드로 입력하므로 입력은 되지만, 값을 직접 넣는 보조 기술(음성 제어 등)은 쓸 수 없다. egui의 한계로 기록한다.
- 라벨을 연결하지 않은 칸은 이름이 비어 Narrator가 "편집"이라고만 읽는다. 제품 UI는 칸마다 `labelled_by`로 이름을 붙이고, 캔버스(지금은 이름 없는 Custom 요소)에도 이름을 붙인다.

구조: AccessKit의 Windows 어댑터는 창을 소유한 스레드에서만 쓸 수 있다. 그래서 어댑터는 UI 스레드에 두고, 렌더 스레드의 egui가 낸 트리 갱신과 낭독기의 동작 요청을 두 스레드 사이에 전달한다. 어댑터는 창이 처음 보이기 전에 붙어야 하므로 창을 숨긴 채 만든다. AccessKit은 창 프로시저를 직접 바꾸고(`SetWindowLongPtr`) 포인터 입력은 comctl32 서브클래스를 쓰므로, 설치는 AccessKit → 포인터 순서, 해제는 그 반대 순서로 한다. 이 변경 뒤에도 IME probe(한국어·일본어), 장치 손실 복구, 입력→표시 지연(최대화 창 p50 6.3 / p95 8.9ms, 변경 전 빌드와 교대 비교에서 차이 없음)이 그대로다.

### 남은 것

- Narrator를 실제로 켜고 듣는 시험은 사용자가 있을 때 한다.
- 후보창이 커서 바로 아래가 아니라 TextEdit 영역 아래에 붙는다. 사용에는 지장이 없지만 문자 도구(캔버스 위 입력)에서는 커서 위치에 맞춰야 한다.

## 8. 4K·장치 손실·WARP·오프라인 (13~14일차, 2026-10-07)

### 장치 손실

진단 모드(`UGURUGU_DIAGNOSTICS=1`)에서 F9를 누르면 `ID3D12Device5::RemoveDevice`로 앱 자신의 D3D12 장치를 "제거됨" 상태로 만든다. 드라이버 리셋과 같은 경로를 이 장치에만 일으키므로 다른 프로그램에는 영향이 없다. 시험은 획을 그리고, F9를 누르고, 캔버스를 화면에서 비교하고, 다시 그리는 순서다.

| 회차 | 캔버스 보존 | 복구 후 그리기 | 복구 시간 (ms) | 옛 장치 해제 (ms) |
|---|---|---|---|---|
| 1 | 화소 단위 동일 | 정상 | 931 | (계측 전) |
| 2 | 화소 단위 동일 | 정상 | 529 | 142 |
| 3 | 화소 단위 동일 | 정상 | 432 | 47 |

복구 시간의 나머지는 대부분 새 어댑터·장치를 여는 시간이다(surface 생성은 0.1ms).

#### 발견해 고친 것

1. **장치 손실 처리가 없었다.** wgpu의 기본 오류 처리기는 panic하고, 앱은 장치를 다시 열 수단이 없었다. 이제 `ugu_render::gpu::Gpu`가 장치 손실 콜백과 `GetDeviceRemovedReason`으로 손실을 알아채고, 렌더 스레드가 같은 장치로 만든 것(장치·스왑체인·egui 렌더러·캔버스 텍스처)을 모두 새로 만든다. egui는 글꼴 아틀라스의 변경분만 보내므로, 새 장치에는 아틀라스 전체를 한 번 올린다.
2. **egui-wgpu는 장치가 사라지면 오류 대신 panic한다.** 제거된 장치에서는 staging buffer를 만들 수 없는데, 이때 `Renderer::update_buffers`가 panic한다(egui-wgpu 0.36.2 `renderer.rs:984`). 장치는 프레임 중 아무 때나 사라질 수 있으므로, 프레임의 GPU 부분을 `catch_unwind`로 감싸고 **장치가 손실된 경우에만** panic을 흡수한다. 그 프레임의 자원은 모두 버리고 새로 만들기 때문에, 반쯤 갱신된 상태를 다시 쓰지 않는다. 장치가 멀쩡한데 난 panic은 다시 던진다. 상류에서 오류를 돌려주게 고쳐지면 이 처리를 뺄 수 있다.
3. **옛 surface를 새 장치에 다시 설정할 수 없다.** 옛 스왑체인이 창을 계속 쥐고 있어 `ResizeBuffers`가 실패하고 "window is in use"로 끝났다. 옛 장치·surface를 먼저 모두 버린 뒤, 창 핸들을 읽을 수 있는 UI 스레드에 새 surface를 요청한다. UI 스레드는 렌더 스레드를 기다리지 않으므로 교착이 없다.

### 4K와 WARP의 입력→표시

1절과 같은 방법(PresentMon `--no_track_input`, `latency-probe --warmup 150`, 100칸, 교대 2회)이다. 최대화한 창은 UHD 모니터에서 클라이언트 3840×2059다. WARP는 `UGURUGU_ADAPTER=warp`(Microsoft Basic Render Driver)로 강제했다.

| 어댑터 | 클라이언트 | 표시 방식 | 입력→present p50 / p95 (ms) | 입력→표시 p50 / p95 / max (ms) | 응답 없는 칸 |
|---|---|---|---|---|---|
| RTX 5080 | 2538×1549 | Independent Flip | 1.70 / 2.77 | 5.94 / 8.27 / 8.70 | 0 |
| RTX 5080 | 3840×2059 | Independent Flip | 2.08~2.14 / 3.60~3.61 | 5.81~5.85 / 8.87~9.05 / 10.03~10.21 | 0 |
| WARP | 2538×1549 | Composed Flip | 15.82~15.89 / 20.43~24.37 | 59.04~59.10 / 63.60~67.59 / 79.5~79.8 | 20~21 |
| WARP | 3840×2059 | Composed Flip | 17.63~20.39 / 25.35~25.54 | 73.28~75.89 / 81.05~81.18 / 93.2~102.8 | 32 |

RTX 5080 2538×1549 1회차는 워밍업 뒤에도 DWM이 합성(Composed Flip, p50 11.29ms)한 채 끝나 표에서 뺐다. 승격은 대부분 되지만 항상 되지는 않는다.

- **4K:** 최대화한 4K 창에서도 입력→표시가 2560 창과 같다. 캔버스는 바뀐 영역만 올리므로 화면 크기에 따른 손해가 없다.
- **WARP:** 표시는 되지만 입력→표시가 약 60~75ms다. 렌더가 입력 간격(15~40ms)을 따라가지 못해 20~32%의 칸은 다음 프레임에 합쳐 표시된다(입력은 잃지 않는다). 제품은 하드웨어 어댑터가 없을 때만 WARP로 열고 안내를 띄운다(scope.md 3.2절).

### 오프라인

Rust 앱의 의존 crate 196개에 네트워크 라이브러리(HTTP·TLS·소켓·updater)가 없다. 시작 경로가 네트워크에 닿지 않는다. 업데이트 확인(Velopack)은 M6에서 넣으며, 시작을 막지 않는 비동기 작업이어야 한다. 2.2.13도 업데이트 확인 실패를 경고로 남기고 계속 실행한다.

### 남은 것

- 실제 드라이버 리셋(TDR) 시험은 M3, 원격 세션(RDP)과 깨끗한 VM은 M6에서 한다(사용자 결정).
- WARP의 지연이 어디서 생기는지(렌더 시간인지, 합성 대기인지)는 나누어 재지 않았다.
