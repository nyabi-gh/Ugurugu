# M4 분해: 편집 기능 완성 (2026-10-07)

M4 종료 조건(계획 11절): 프레임별 선택 의미·merge/erase·pending edit가 회귀 fixture를 통과한다. 이를 다음 세 가지로 확인한다.

- [scope.md](scope.md) 3절의 M4 행(선택·자동 선택·채우기·변형, 이미지·문자, 스포이드·획 속성, 자르기·리사이즈, 마커·에어브러시·스프레이, 모션 전체)이 앱에서 동작하고, 모든 새 연산이 M3의 한 `RenderPlan`·합성기로 그려진다.
- [adr-operations-and-format.md](adr-operations-and-format.md) 2절의 의미(지우개는 앞선 결과에만, 선택 변형은 프레임마다 그 프레임의 결과를, 채우기 coverage 고정, 자르기와 리사이즈의 순서)가 참조 평가기와 실제 렌더러 모두에서 회귀 fixture로 고정된다.
- M3에서 넘긴 ②p 30fps 처리 능력을 충족하고, 이제 열 수 있는 원본 fixture ②·⑤(에어브러시·스프레이·이미지·마스크)를 2.2.13과 같은 내용으로 나란히 잰다.

범위는 scope.md 3절의 M4 행, M3에서 넘긴 것([m3-plan.md](m3-plan.md) 9절), 계획 5.2~5.4·6.2·7.2절이다. 2.2.13 동작은 C++ 소스에서 확인했다(각 행에 파일).

## 3. 구조

- **새 연산은 레이어 표면 안에서 평가한다.** M3에서 레이어 결과는 연산을 순서대로 적용한 표면이다. `Fill`·`ClearSelection`은 마스크 단위 화소 연산, `TransformSelection`·`PlaceImage`는 아핀 리샘플 후 source-over, `Crop`·`Resample`은 표면 자체를 바꾼다. 합성(그룹·클리핑·합성 모드)은 그대로다.
- **비국소 연산은 레이어 전체로 승격한다(계획 7.2절).** `TransformSelection`은 마스크 bounds 안의 모든 타일을, `Crop`·`Resample`은 레이어 전체를 입력으로 쓴다. 이런 연산이 있는 레이어의 pen-up 증분은 그 연산 뒤에 그린 획에만 쓰고, 연산 앞을 바꾸는 편집은 레이어를 다시 그린다. 승격 빈도를 센다.
- **선택은 세션 상태다(ADR 2절).** 마스크는 세션에 있고, 문서에는 그것을 쓰는 연산이 확정될 때만 들어간다. 자동 선택·채우기의 참조 이미지는 세션이 불변 snapshot으로 작업자에게 맡긴다.
- **대기 편집은 문서 사본에 덧붙인 연산이다.** 미리보기는 대기 연산을 덧붙인 계획을 같은 합성기로 평가하므로, 적용한 결과와 화면이 바이트 단위로 같다(2.2.13 `selectionMovePreviewMatchesCommittedPixelOperation`와 같은 성질).

### M4-14 스포이드·획 속성 편집 (2026-10-08)

2.2.13 동작은 C++ 소스에서 확인했다(`CanvasWidgetEvents`·`CanvasWidgetTools::pickColorAt`·`beginColorPick`, `MainWindow::editSelectedStrokeProperties`, `StrokePropertiesDialog`, `DocumentController::updateStrokeAttributes`, `CanvasWidgetSelection::applySelectionVisibility`).

**스포이드 (`canvas/picking.rs`, `Session::pick_color`):**
- 2.2.13과 같은 입력이다.
  - 스포이드 도구(I, 도구 막대·도구 메뉴, 아이콘은 2.2.13 글리프)는 누르면 고르고, 끄는 동안 계속 고른다.
  - 브러시·지우개·채우기 통에서는 Alt+클릭이 같다. 선택·자동 선택은 Alt가 빼기이므로 고르지 않는다(2.2.13과 같음).
  - 고른 색은 펜 색이 된다(지우개로 고를 때도). 완전히 투명한 화소는 무시한다. undo 단계가 없고 저장하지 않은 변경도 아니다.
- **2.2.13과 다른 점: 화면에 보이는 화소를 읽는다.** 2.2.13은 미리 그린 합성 참조 이미지를 읽었고, Alt로 시작하거나 변형 중이면 GUI 스레드에서 프레임 전체를 렌더했다(D14). 3.0은 이미 합성된 화면 이미지(대기 편집·배치한 글자 미리보기 포함)에서 화소 하나를 읽으므로 렌더가 없다. 재생 중이면 화면의 재생 프레임(축소된 것)을 읽는다.
- 화소는 premultiplied이므로 2.2.13 `qUnpremultiply`와 같은 반올림으로 되돌린다(`Rgba8::from_premultiplied`, 자동 선택의 색 비교와 같은 함수).
- 고를 수 있는 동안 캔버스 위 커서는 십자다.

**선 속성 편집 (`ugu_core::restyle`, `Session::touched`·`restyle_selected`):**
- 편집 메뉴와 선택 동작 막대(2.2.13 브러시 아이콘)의 "선택한 선 속성 편집…"이 대화상자를 연다. 대화상자는 2.2.13과 같다. 색상·굵기 체크와 값이 있고, 체크한 것만 바꾼다. 모두 같은 값이면 체크된 채로, 섞여 있으면 체크 없이(검정·6px) 시작한다. 값을 바꾸면 체크되고, 아무것도 체크하지 않으면 확인이 꺼진다.
- 색은 Paint 선과 채우기에, 굵기는 Paint·Erase 선에 적용한다(2.2.13). 굵기 범위는 0.25~512px다.
- **2.2.13과 다른 점: 대상이 선택에 닿는 선이다.**
  - 2.2.13은 선택 영역에 보이는 화소가 있으면 그 레이어의 모든 선을 바꿨다. 선 단위 선택을 화소 선택으로 바꾼 뒤 남은 동작이다.
  - 3.0은 계획대로 현재 레이어에서 선택에 닿는 선과 채우기만 바꾼다. 다른 그림 앱에서 영역으로 고른 것만 바뀌는 기대와 맞기 때문이다. 바꾸는 것은 선 전체이므로 선택 밖으로 나간 부분도 바뀐다.
- **닿음의 정의:**
  - 선은 움직이기 전 점들을 잇는 선에서 닿는 범위 안에 선택 화소의 중심이 있으면 닿은 것이다. 닿는 범위는 필압에 따른 반폭이고, 스프레이는 입자가 떨어지는 범위다.
  - 채우기는 덮는 화소와 선택이 겹치면 닿은 것이다.
  - 둘 다 자기 clip 안에서만 센다. 병합으로 생긴 구역 안도 찾는다.
  - 자르기·리샘플 앞에 그린 것은 그 연산이 옮긴 자리에서 찾는다. 선택을 그때의 캔버스로 되돌려 비교한다.
  - 흔들림은 넣지 않는다. 프레임과 관계없이 같은 결과를 내기 위해서다.
- **저장:** 바뀐 선은 새 id로 저장하고, 다른 레이어가 쓰지 않는 이전 선은 지운다. 같은 id 아래 내용이 바뀌면 id로 쥔 캐시가 틀릴 수 있기 때문이다. 시드는 그대로라 움직임이 같다.
- 리샘플 앞에 그린 선의 굵기는 저장된 값(그때 캔버스 기준)으로 보이고 바뀐다.
- **사용할 수 있을 때:** 선택이 있고 대기 편집·배치한 글자가 없을 때 메뉴·버튼이 켜진다. 대기 중에는 선택이 옮겨진 자리와 선이 있는 자리가 달라 대상을 정할 수 없다(2.2.13도 변형 중 비활성). 세션도 `FillError::Pending`으로 거부하고, 숨긴 레이어는 그리기와 같이 거부한다.
  - 2.2.13은 닿는 선이 없으면 메뉴를 껐다. 3.0은 판정을 매 프레임 하지 않고 열 때 한 번 하며, 없으면 "선택 영역에 편집할 선이나 채우기가 없습니다."를 띄운다.
- 적용하면 선택은 그대로 남는다.

**판정 비용 (release, 원본 ⑤ 4096², 레이어별 5회 중 중앙값):**

| 선택 | 판정 | 적용(판정 포함) |
|---|---|---|
| 전체 | 0.08~0.21ms | 0.16~0.30ms |

- 선택 마스크에 16px 타일의 누적 개수표를 붙였다. 이제 선 전체·선분·행이 빈 타일만 덮으면 바로 건너뛴다. 같은 조건에서 1.2ms, 선 가장자리 바로 바깥의 고리 선택은 1.7ms다. 표는 4096² 전체 선택에서 만드는 데 약 0.8ms다.

**시험:**

  - 기준점의 오프셋은 `(새 크기 − 지금 크기)`의 0·½·1배이고, ½은 0 쪽으로 버린다(2.2.13).
  - 크기를 바꾸면 기준점대로 오프셋을 다시 정한다. 오프셋을 직접 치면 그 값을 주는 기준점을 고르고, 없으면 해제한다.
  - 같은 크기에 오프셋만 있어도 적용한다.
- 이미지: 너비·높이, 균일 배율(%), 비율 유지.
  - 비율을 유지하면 다른 변은 반올림으로 따라온다.
  - 4096×1처럼 다른 크기로 비율을 지킬 수 없으면 비율 유지를 끄고 막는다.
  - 비율이 바뀌면 왜곡 안내를 띄운다. 계산식과 범위는 2.2.13과 같고, 2.2.13 `configuresCanvasSizeDialog`·`configuresImageSizeDialog`·`unlocksImageSizeDialogForExtremeAspectRatios`의 값을 그대로 시험한다.
- **2.2.13과 다른 점:**
  - **리샘플 방식 선택:** 부드럽게(기본)·픽셀 기반. 2.2.13은 늘 부드럽게였다. 렌더러가 둘 다 그리고(M4-5), 픽셀 그림을 정수배로 키울 때 계단이 그대로 남아야 하기 때문이다.
  - **설명 문구:** 2.2.13의 "그림과 브러시 크기를 조절"은 리샘플이 화소만 바꾸므로 맞지 않아, "그림을 새 픽셀 크기로 리샘플"로 바꿨다.
  - **확인 버튼과 Enter:** 확인·취소는 새 번역 키이고, Enter는 확인, Esc와 바깥 클릭은 취소다.

**세션:**
- 대기 편집이 있으면 다른 편집과 같이 먼저 적용한다(별도 undo 단계, `history_mut`). 2.2.13도 먼저 적용한다.
- 선택은 새 캔버스로 옮기거나(자르기) 최근접으로 리샘플한다(M4-8부터).
  - 2.2.13은 메뉴 경로에서 선택을 해제했지만, 3.0은 선택이 캔버스 변경을 따른다. 되돌리면 이전 선택이 돌아온다.
- 그리던 올가미는 버린다. 크기가 그대로면 undo 단계가 없다.
- 범위 밖 크기는 문서 검증이 거부하고 아무것도 바꾸지 않는다.
- 연산 상한 등으로 거부되면 먼저 적용한 대기 편집만 남는다. 2.2.13과 같고, 대화상자는 범위 밖 값을 만들지 않는다.

**선택 마스크 자르기·리샘플 (`Selection::cropped`·`resampled`):**
- 이전에는 캔버스 크기의 `bool` 배열로 펼쳤다가 다시 비트로 접었다(4096²이면 16M 칸).
- 이제 자르기는 비트 행을 밀어 복사한다. 새 캔버스 안에 다 들어가면 비트를 공유한다.
- 리샘플은 마스크가 닿는 목표 범위만 계산하고, 같은 원본 행은 앞 행을 복사한다. 그 뒤 경계를 좁힌다.
- 화소별 참조 구현과 같음을 모양 4개 × 자르기 5개·리샘플 6개로 시험한다(좁힌 경계 포함).

|---|---|---|
| 전체 선택 (3800²로 자름 / 3000²로) | 25.3 → 1.6ms | 25.4 → 7.0ms |
| 타원 | 22.5 → 0.0ms | 23.1 → 4.4ms |
| 별 모양 2000점 | 24.5 → 0.0ms | 25.4 → 6.6ms |

`Selection::transformed` 등 다른 연산도 같은 캔버스 크기 배열을 쓴다(4096² 전체 선택 변형 19.6ms). 이번 범위 밖이라 그대로 두었다.

**앱:**
- 캔버스 크기가 바뀌는 편집은 되돌리기를 포함해 화면을 맞춘다(최대 100%). 2.2.13은 되돌릴 때 이전 배율로 돌아갔다. 3.0에서는 크기가 바뀐 뒤의 이전 배치가 의미가 없으므로 맞춤으로 통일했다.

**시험:**
- 대화상자 모델 4개(2.2.13 UiShellTests 값).
- 세션 3개:
  - 대기 편집 중 자르기·리샘플: 연산 순서 그리기 → 변형 → 캔버스 변경, 옮긴 선택, undo 두 단계와 redo.
  - 변경 없음·거부·같은 크기 이동.
  - 올가미.
- 앱 1개: 미리보기가 떠 있는 대기 편집 중 자르기·리샘플 뒤와 undo 네 번마다, 화면이 전체 렌더와 2단계 이내.

### M4-11 클립보드·이미지 가져오기 (2026-10-08)

2.2.13 동작은 C++ 소스에서 확인했다(`SelectionClipboardCodec::makeCopy`, `DocumentController::pasteLayer`·`insertImage`, `MainWindow::pasteFromClipboard`·`chooseInsertImage`).

**복사 (`ugu_core::clip`):**
- 현재 레이어의 연산을 그대로 복사하고, 선택 밖을 지우는 `ClearSelection`을 끝에 하나 붙인다. 2.2.13도 이렇게 하며, 이미 순서 있는 화소 연산이 있는 레이어에서도 맞고 붙여넣은 획이 계속 흔들린다.

**붙여넣기:**
- 현재 레이어 바로 위에 새 레이어를 만들고, 선택을 잡은 뒤 대기 편집으로 들어간다. 레이어 추가와 선택이 undo 한 단계이고, 2.2.13의 "복사 후 바로 이동"과 같은 흐름이다(계획 2절 2).

**시스템 클립보드 (`ugu_win::clipboard`, 앱 `clipboard.rs`):**

### M4-10 대기 편집 (2026-10-08)

**사용자 결정(2026-10-08):** 이동·크기·회전은 2.2.13의 이동 토글과 배율·각도 대화상자 대신 **캔버스 변형 상자**로 한다. 안쪽 끌기는 이동, 모서리·변 핸들은 크기(Shift로 비율 고정), 상자 바깥은 회전(Shift로 15° 단위)이고, 동작 막대에 뒤집기·적용·취소·복제·삭제·해제를 둔다.

2.2.13 동작은 C++ 소스에서 확인했다(`CanvasWidgetSelection.cpp`의 변형 세션, `CanvasWidget.cpp`의 `scaleSelection`·`rotateSelection`·`applySelectionTransform`·`deleteSelection`·`handleEscape`, `MainWindowActions.cpp`의 동작 막대, `SelectionOperation.cpp`의 `transformedSelectionSupport`).

**core·세션:**
- **아핀 (`ops::Affine`):** 합성(`then`), 역변환(평면을 납작하게 하거나 유한하지 않으면 없음), 점 변환, 중심 기준 크기·회전(화면에서 시계 방향).
- **변형 뒤 선택 (`Selection::transformed`):** 옮긴 화소 사각형이 조금이라도 덮는 캔버스 화소다. 3.0 렌더러는 옮긴 내용을 `T(마스크)` 경로로 잘라 앤티에일리어싱으로 그리므로 회전·확대 뒤 가장자리 화소에 내용이 일부 들어간다. 화소 중심 규칙이면 그 화소가 선택 밖이 되어 이어서 칠하거나 지우거나 다시 옮길 때 가장자리가 남는다. 정수 이동이면 두 규칙이 같다(2.2.13 `transformedSelectionSupport`도 같은 결과). 처음에는 대상 화소마다 역변환해 겹침을 검사했는데 4096² 전체 선택 회전이 322ms였다. 원본의 같은 행 구간을 사각형으로 묶어, 그 평행사변형이 대상 각 행과 겹치는 x 범위를 채우게 바꿔 19.6ms(타원 3000² 회전 30.7ms, 정수 이동 13~20ms)가 됐다. 90° 회전처럼 정수에 떨어지는 꼭짓점은 부동소수 오차를 정수로 맞춘다.
- **명령:** `command::transform_selection`(연산을 레이어 맨 위에), `clear_selection`. `draw`·`fill`과 위치 계산을 공유한다.
- **세션 (`ugu_session::transforming`):** `Pending`(레이어, 시작할 때의 선택, 변환, 원본 남김=복제). `begin_transform`(선택과 그릴 수 있는 레이어 필요), `set_transform`(평면을 납작하게 하거나 좌표 한계 32767을 넘으면 거절), `set_keep_source`, `apply_transform`(마스크·`TransformSelection`·옮긴 선택을 한 undo 단계, 변환이 항등이면 아무것도 안 함), `cancel_transform`, `delete_selected`(대기 편집이 있으면 먼저 적용하고 옮긴 자리를 지움). 표본 방식 `transform_sampling`(기본 Smooth). 대기 편집은 저장하지 않은 변경으로 센다(`is_dirty`).
- **정책 (2.2.13과 다름):** 2.2.13은 대기 중 다른 편집을 하면 대기 편집을 취소한다. 3.0은 먼저 적용한다. 세션의 문서·선택 변경은 모두 `history_mut`을 거치며 그때 대기 편집을 적용하고, 레이어·프레임을 바꿀 때도 적용한다. 해 둔 변형이 보이지 않게 사라지지 않고, 다른 그림 앱이 도구를 바꿀 때 적용하는 것과 같다. Undo·Redo·Esc는 계획 2절대로 취소다.
- 시험: 아핀(시계 방향 회전, 합성·역변환 왕복, 납작한 변환 거절), 변형 뒤 선택(정수 이동, 캔버스 밖, 90° 회전, 반 화소, 30° 회전에서 8×8 표본이 닿는 화소는 모두 포함하고 먼 화소는 없음), 세션(선택 없으면 거절, 문서에 넣기 전 그대로, 적용 한 단계와 undo, 옮긴 선택, 항등은 변화 없음, Undo는 취소만, 다른 획·프레임·레이어 추가가 먼저 적용, 복제 플래그, 삭제가 옮긴 자리를 지움).

**미리보기 (`ugu_render::moving`, `Split::begin_move`·`show_move`·`end_move`):**
- 대기 편집을 시작하면 Split이 쥔 현재 레이어 표면을 원본으로 잡는다. 이 원본 위에 옮긴 부분을 렌더러의 `TransformSelection`과 같은 단계(원본 남김이 아니면 마스크를 지우고, `T(마스크)`로 잘라 원본을 옮겨 그림)로 그린다. 그리는 범위는 지난번과 이번에 바뀐 범위뿐이다.
- 옮긴 색과 클립 커버리지는 따로 그린 뒤 한 번에 섞는다. Vello가 클립 가장자리를 `dst·(1 − a·c) + s·c` 한 번으로 섞기 때문이다. 처음에는 클립한 결과를 그린 뒤 src_over로 얹었는데, 반올림이 두 번 일어나 2단계까지 달랐다.
- 시험(레이어 4개 × 변환 6개 × 원본 남김 2가지, 연달아): 레이어 표면은 전체 렌더와 1단계 이내(48건 가운데 20건은 바이트 단위로 같음), 화면은 2단계 이내다. 항등 변환과 취소는 바이트 단위로 원래대로 돌아간다. 남는 1단계는 Vello가 완전히 덮인 구간에만 plain src_over를 쓰는 데서 오고, 어느 구간인지는 타일 배치에 따라 다르다(획 `Stamp`와 같은 계약).
- 적용하면 그 표면을 그대로 두고 Split 키만 적용 뒤 상태로 옮기므로, 다시 그리지 않는다. 취소하면 원본 표면을 되돌린다.
- **마스크 경로를 윤곽으로 바꿈(근본 원인):** `Runs::path`는 행마다 1px 높이 사각형을 하나씩 만들었다. 회전하면 길이 4096짜리 얇은 평행사변형 4096개가 되어 Vello가 타일을 수백만 번 지난다. 이제 경계 윤곽(`Mask::outline`, `Selection`에서 옮김)을 그린다. 넓이는 같고, 원본 크기에서는 화소 경계에 맞아 커버리지가 0/255 그대로다(기존 렌더 시험 88개 통과). 같은 원인이 실제 적용 렌더에도 있었다. 4096² 30° 회전 기준: 적용 렌더 전체 선택 339 → 69ms, 타원 168 → 64ms. 미리보기 커버리지 140 → 2ms.
- 4096² 벤치(8스레드, 레이어 하나):

  | | 시작 | 이동 p50 | 회전 p50 | 크기 p50 |
  |---|---|---|---|---|
  | 전체 선택 | 3.7ms | 15ms | 18ms | 12ms |
  | 타원 | 3.1ms | 8.3ms | 12ms | 6.6ms |

  여기까지 오는 동안 고친 것:
  - 처음 측정에서 1회 갱신이 177~242ms였다(대부분 위의 경로 문제).
  - 합성 루프를 행 단위로 병렬화했다(22 → 5ms).
  - 영역 크기가 바뀔 때마다 64MB 버퍼를 새로 할당하던 것을 재사용하게 했다(이동 41 → 15ms).
  - 회전 각도가 커질 때마다 표본 원본을 다시 복사하던 것을, 늘릴 때 선택 크기의 절반만큼 미리 넓혀 두게 했다.
  - `Runs::from_mask`와 비트 채우기를 바이트 단위로 바꿨다(시작 18 → 3.7ms).
- **개미선:** uniform에 아핀(2×3)과 윤곽을 따라 늘어나는 비율(√|det|)을 넣어, 선택 윤곽을 다시 올리지 않고 옮겨 그린다. 회전·균일 크기·뒤집기에서는 대시 간격이 정확하고, 한쪽으로만 늘이면 평균 비율을 쓴다.

**앱 (`canvas/transform.rs`, `ui`):**
- Ctrl+T, 동작 막대, 편집 메뉴로 대기 편집을 시작하면 변형 상자를 보인다.

  - 바깥: 상자 중심 회전. Shift는 상자의 각도를 15° 단위로 맞춘다.

**정책:**
- Esc는 대기 편집 취소를 선택 해제보다 먼저 한다. 전에는 `deselect`가 `history_mut`을 거쳐 대기 편집을 **적용**했다.

**2.2.13과 다른 점(사용자 결정 외):**

### M4-9 자동 선택·채우기 (2026-10-08)

2.2.13 동작은 C++ 소스에서 확인했다(`FloodFillMask.cpp`, `FrozenFillMask.cpp`, `CanvasWidgetSelection.cpp`의 `computeWandSelection`·`applyBucketFill`·`fillSelection`·`commitFrozenFill`, `CanvasWidgetTools.cpp`의 `toolReferenceDocument`·`prepareToolReference`, `SelectionOutline.cpp`).

- **flood (`Selection::flood`):** 2.2.13과 같은 4-이웃 scanline이다. alpha 경계는 alpha 128 이상에서 멈추고, 색은 Qt `qUnpremultiply`와 같은 반올림으로 straight RGBA를 만들어 채널마다 허용치와 비교한다(허용치 0은 alpha 경계). 클릭한 화소가 막혀 있으면 아무것도 없다. 2.2.13 C++를 같은 참조 이미지(원본 ②·⑤의 레이어마다, 두 방식, 38건)에 돌려 화소 수가 모두 같았다.
- **참조 이미지 (`RenderPlan::reference`, `Split::reference`):** 범위 3종은 2.2.13과 같다. 현재 레이어는 숨김·불투명도·합성 모드·클리핑·그룹을 떼고 그 레이어만, 참조 레이어는 표시된 참조 표시 레이어만, 보이는 레이어는 전부이고, 셋 다 배경 없이 투명 위에 그린다(`Purpose::Reference`). 2.2.13은 도구를 고르거나 프레임이 바뀔 때 작업자가 참조 이미지를 미리 그렸다. 3.0은 화면용 Split이 이미 레이어 표면을 프레임마다 쥐고 있으므로, 클릭할 때 그 표면을 같은 계획으로 합성만 한다(아래 비용). 그래서 유휴 때 그리는 일이 없다. Split이 그 레이어를 따로 쥐지 않으면(숨긴 현재 레이어, 예산 초과로 미리 합친 경우, Split이 아직 오지 않은 경우) 작업자가 같은 계획을 그린다. 두 경로가 바이트 단위로 같음을 시험한다.
- **세션 (`ugu_session::filling`):** 도구 `Wand`·`Fill`, 채우기 설정(참조 범위, 색 비교, 허용치, 앤티에일리어싱, 2.2.13 기본값). 자동 선택은 선택 도구처럼 Shift 더하기·Alt 빼기이고, 바꾸기에서 영역을 찾지 못하면 선택을 해제하고 이유를 알린다. 채우기 통은 선택이 있으면 그 안을 클릭해야 하고 결과를 선택으로 자른다. 선택 채우기는 덮개와 clip이 같은 저장 마스크 하나다(2.2.13처럼 앤티에일리어싱 가장자리가 개미선 밖으로 나가지 않음). 올가미 칠하기는 선택 도구의 모드이고 모양을 채운 뒤 선택은 그대로다. 채우기는 모두 마스크와 `Fill` 연산을 한 undo 단계로 넣는다(`command::fill`).
- **채우기 표시 (`Split::stamp_fill`):** 확정한 채우기를 Split의 현재 레이어 표면에 바로 찍는다. 원본 크기에서 렌더러가 하는 것과 같다: 덮은 화소는 채우기 색으로 바꾸고, 가장자리(4-이웃)는 뒤에 깐다. 덮개·가장자리 계산은 렌더러와 같은 `Runs::fill`이다. 이전 구조라면 다시 그린 Split이 올 때까지 보이지 않았다(②p 57ms, ⑤p 188ms).
- **윤곽 (`Selection::outline`):** 경계 사각형의 화소마다 `contains`를 두 번 부르고 HashMap으로 변을 잇던 것을, 행 바이트 XOR로 가로 변을 찾고 그 자리에서 화소 2×2를 보며 따라가게 바꿨다. 꼭짓점에서는 오른쪽으로 먼저 돌아 꼭짓점만 닿은 화소를 다른 고리로 둔다. 무작위 마스크로 모든 경계 변을 한 번씩 지나는지 시험한다.
- **개미선 (`ugu_render::ants`):** 자동 선택은 스프레이 입자마다 구멍이 생겨 고리가 수천 개다. egui로 그리면 프레임마다 테셀레이션이 10~21ms(고리 1117개, 정점 42만~78만)이고, 획을 그리는 동안에는 매 프레임 render 스레드가 이 일을 했다. 이제 선택이 바뀔 때 직선 구간(문서 좌표와 고리를 따른 길이)을 한 번 정점 버퍼로 올리고, 캔버스를 그린 뒤 egui 앞에 인스턴스 사각형으로 그린다. 프레임마다 바뀌는 것은 uniform 32바이트(배치와 점선 위상)뿐이다. 모양은 2.2.13과 같다: 흰 1.8pt 선 위 어두운 1pt 4/4 점선, 120ms마다 한 칸. 끌고 있는 모양은 egui 그대로다.
- **앱:** 도구 레일·Tools 메뉴에 자동 선택(W)·채우기 통(G)(2.2.13 아이콘), Edit 메뉴에 선택 채우기(Alt+Delete). 도구 설정은 2.2.13 패널을 따르되, 자동 선택에도 비교 방식·허용치를 보인다(2.2.13은 채우기 통 패널에만 있었지만 자동 선택도 그 값을 쓴다). 영역 선택 패널에 모드(선택·그리기)와 그리기일 때 가장자리 앤티에일리어싱. 번역은 2.2.13 en·ko·ja. "이 레이어에서 채울 영역을 선택하세요"는 3.0 선택이 레이어에 묶이지 않으므로 "채울 영역을 선택하세요"로 바꿨다.
- 시험: flood(alpha 경계 링, 색 허용치 채널별, 허용치 0, 막힌 클릭·캔버스 밖), Qt 반올림, 윤곽 변 집합(무작위 마스크 3종), 참조 계획(범위 3종 × 프레임 2 × Split 합성 = 그린 것, 숨긴 레이어는 그리기로, 배경 없음, 표시 없으면 빈 계획), 채우기 찍기(모든 레이어 × 앤티에일리어싱·clip, 레이어 표면 1단계·화면 2단계), 개미선 GPU(가장자리에 밝은 선과 점선, 안팎은 그대로, 위상에 따라 움직임), 세션(자동 선택 바꾸기·더하기·빼기·해제·이유·색 허용치, 채우기 통 한 단계·undo·선택 밖 거절·clip·숨김, 선택 채우기 마스크 하나·전체 선택은 clip 없음, 올가미 칠하기와 클릭), 앱(채우기 통 클릭이 다시 그리지 않고 전체 렌더와 2단계 이내, Split 없이도 같은 자동 선택).

### M4-8 선택 세션 (2026-10-08)

2.2.13 동작은 C++ 소스에서 확인했다(`CanvasWidgetSelection.cpp`, `DocumentController::pushSelectionStateCommand`, `HistoryEffects::SelectionStateTransition`, `UiSelectionTests.cpp`).

- **선택의 자리 (`ugu_core::history`):** 선택은 문서가 아니다(ADR 2절). 2.2.13처럼 선택 변경마다 같은 undo 스택에 합쳐지지 않는 항목을 넣는다. 선택만 바꾼 항목은 문서 상태 id와 렌더 revision을 바꾸지 않으므로 저장한 문서가 dirty가 되지 않고 다시 그릴 것도 없다. 획을 되돌려도 선택은 그대로다(2.2.13과 같음). `Group::select`로 문서 편집과 선택 변경을 한 단계에 담는다. 자르기·리사이즈는 선택을 같은 변환(자르기 offset, 최근접 화소 중심)으로 옮기고, 남는 화소가 없으면 해제한다. 되돌리면 둘 다 함께 돌아간다.
- **모양 (`ugu_core::selection`):** 2.2.13은 Grayscale8 QImage에 앤티에일리어싱 없는 `QPainter`로 칠한다. 3.0도 같은 규칙이다: 화소 중심이 안에 드는 화소, 자유형은 even-odd이고 처음 점으로 닫는다. 사각·타원은 가로세로 1px 이상, 자유형은 점 3개 이상이고 점은 1px 이상 떨어질 때 더한다(캔버스로 자름). 저장은 캔버스 크기와 선택 화소의 경계로 자른 1비트 `Mask`로 한다.
- **세션 (`ugu_session::selecting`):** 도구 `Select`와 모양(자유·사각·타원). Shift는 더하기, Alt는 빼기, 둘 다면 바꾸기다. 바꾸기에서 선택할 화소가 없는 모양(클릭)은 "Deselect" 단계이고, 더하기·빼기에서는 아무 일도 하지 않는다. 전체(Ctrl+A), 반전(Ctrl+Shift+I, 선택이 없으면 무시, 전체를 반전하면 해제), 해제(Ctrl+D)를 둔다. Esc는 끌고 있는 모양 → 진행 중 획·이동 → 선택 순으로 취소한다(2.2.13 `handleEscape`의 해당 부분).
- **2.2.13과 다르게 한 것:** 2.2.13은 선택을 만든 레이어에 묶고 현재 레이어가 바뀌면 지운다. 3.0은 선택을 문서 전체에 두고 레이어를 바꿔도 유지한다. 다른 그림 앱(Photoshop·Krita·Clip Studio)의 관례이고, 레이어를 옮겨 다니며 같은 영역에 그리는 흐름과 M4-9 참조 레이어 자동 선택에 맞는다.
- **선택 안의 획:** 획을 시작할 때 선택(캔버스 전체가 아니면)을 붙이고, 확정할 때 같은 화소를 가진 저장 마스크가 있으면 그 id를 다시 쓰고 없으면 넣는다(2.2.13의 공유 QImage와 같은 효과). 지우개도 같다. 진행 중 획(`LiveStroke::with_clip`)과 pen-up 증분(`Stamp::apply_stroke`의 clip)이 마스크 밖 화소를 건너뛴다. 렌더러가 원본 크기에서 마스크를 비트 그대로 자르므로 같고, 이전에는 clip이 있는 획이 pen-up 때 새 분할로 넘어갔다.
- **개미선 (`ui::selection_overlay`):** 2.2.13처럼 흰 1.8pt 선 위에 어두운 1pt 4/4 점선을 120ms마다 한 칸씩 움직인다. 윤곽은 화소 경계를 이은 고리이고(`Selection::outline`, 선택이 바뀔 때 한 번 만듦), egui가 캔버스 위에 그리므로 문서 렌더·캔버스 업로드가 없다. 최소화 중에는 render 스레드가 다시 그리기를 예약하지 않는다. 바꾸기로 끄는 동안은 기존 선택을 숨긴다(2.2.13은 누를 때 지움).
- **앱:** 도구 레일·Tools 메뉴에 영역 선택(L, 2.2.13 올가미 아이콘), 도구 설정에 2.2.13 `LassoPopoverPanel`의 모양 세 가지(이름과 설명), Edit 메뉴에 전체 선택·선택 반전·선택 해제(번역은 2.2.13 en·ko·ja). 올가미 칠하기(MODE Paint)는 M4-9에서 넣는다.
- 시험: 모양 래스터(화소 중심, 방향 무관, 1px 미만 거부, 캔버스 밖 자름, 타원, even-odd 자기 교차, 일직선 거부), 더하기·빼기·바꾸기와 빈 모양, 전체·반전(바이트 경계 아닌 폭), 자르기·리사이즈 이동, 윤곽 고리(방향, 구멍, 꼭짓점으로 닿는 화소). ### M4-7 모션 (2026-10-08)

- **설정 (`ugu-core`):** `Motion`이 2.2.13 `MotionSettings`의 필드를 모두 갖는다: 스타일, 포즈 수, 디테일, 연결, 무작위성, 끊어진 선, 끊김 정도, 끊김 범위(기본값도 같음). `Wobble`은 흔들림 양과 `Motion`이고, 레이어·병합 구간이 둘을 함께 덮어쓴다(2.2.13 `setLayerWobbleOverride`가 둘을 함께 받는 것과 같음). 검증 범위도 2.2.13과 같고, 범위 밖은 새 오류 `Motion`이다. `.ugurugu` 스키마 1의 `wobble`에 필드를 더했다(M4-6 빌드 파일은 열지 않음).
- **포즈 수:** 2.2.13은 프레임 수를 줄이면 문서·레이어의 포즈 수를 잘라 저장값을 바꾼다. 3.0은 1~60을 저장하고 평가할 때 min(포즈 수, 프레임 수)를 쓴다. 렌더 결과는 같고, 프레임 수를 다시 늘리면 원래 포즈 수가 돌아오며, 병합 구간의 모션을 고쳐 쓸 일이 없다.
- **수식 (`ugu_core::motion`):** `MotionTimeModel`(Smooth 포즈 보간·Stepped 포즈), `StrokeMotionModel`(포즈·연결 시드 사이 보간, 디테일 파장, 무작위 채널, 굵기), `BrokenLineModel`(움직인 표본의 호 길이를 끊김 범위로 나눈 칸마다 보임 판정, 판정 포즈는 첫 포즈)을 그대로 옮겼다. 2.2.13 C++ 소스를 MSVC `/fp:precise`로 빌드해 뽑은 값(`crates/ugu-core/testdata/motion.txt`: 포즈 표본, Stepped, 굵기 72, 변위 288, 보임 포즈, 끊어진 구간 24)과 비트 단위로 같다. 목표(1e-6)보다 강하게 두려고 시험 입력은 f32로 정확히 표현되는 값을 썼다.
- **렌더:** `Pen`이 `Mover`(모션과 프레임 수)를 갖는다. 끊어진 선은 움직인 표본에서 보이는 구간을 정하고, 선은 보이는 구간마다 따로 합집합 윤곽을 만들어 한 경로로 채운다(반투명이 겹쳐 진해지지 않음). 사각 끝도 같고, dab·입자는 보이는 구간에 닿은 표본만 그린다(2.2.13 `pointVisible`, 입자 번호는 표본 번호 그대로). 진행 중 획은 더 움직이지 않는 표본까지의 호 길이를 이어 가고 꼬리만 다시 센다. dab은 끊어진 선이면 한 표본 더 기다려 확정한다.

**전용 dab 래스터 (`dab::Painter`):**
- 화소 규칙: 앨리어싱 원·사각형은 화소 중심이 안에 드는 화소를 칠한다. 앤티에일리어싱 원은 가장자리 화소를 중심이 반지름 ± 0.5 안 어디에 있는지로 덮고(1px보다 작은 dab은 제 넓이까지), 사각형은 화소와 겹친 넓이로 덮는다. 부드러운 dab은 획마다 경도에 대한 감쇠 표(거리² 4096칸)를 한 번 만들어 쓴다. 겹치는 dab은 premultiplied source-over로 쌓는다(반올림 a·b/255).
- 렌더러: 획 버퍼는 Raster가 재사용하고, Vello 이미지(최근접)로 정수 위치에 얹는다. 지우개는 DestOut, 선택 안에서 그린 획은 clip이 걸린 레이어 하나로 얹는다. 그룹이 없으므로 획마다 연 레이어 비용이 없다.
- 미리 칠하기: dab 획을 만나면 다음 자르기·선택 변형 전까지의 dab 획을 모아 Raster의 스레드 수만큼 나눠 칠한다. 처음 구현은 그리는 자리에서 하나씩 칠했는데, 레이어가 스레드보다 적은 문서(⑤, 레이어 5개)는 Vello가 레이어 하나를 8스레드로 래스터하므로 dab만 1스레드가 되어 106 → 139ms로 느려졌다.

**진행 중 획과 pen-up 증분의 dab:**
- 진행 중: 표본의 변위는 양옆 표본에 기대므로, 다음 표본이 정규 표본이 되면 그 표본의 dab은 더 움직이지 않는다. 그런 dab은 문서 크기 획 버퍼에 한 번 칠하고, 나머지(꼬리)는 그 영역 복사본 위에 갱신마다 다시 칠한다. 획 버퍼는 선 획의 덮개 버퍼를 그대로 다시 쓴다. 화면에는 레이어 화소에 `src_over`(지우개는 `dest_out`)로 얹는다.
- pen-up: 획 전체의 dab을 렌더러와 같은 표본으로 칠해 레이어 표면에 같은 식으로 얹는다.
- 고친 것: pen-up 증분과 진행 중 획의 선 색이 불투명도 압력(첫 점 압력)을 빼먹어, 불투명도 압력이 있는 펜은 pen-up 뒤 다음 분할에서 진하기가 바뀌었다. 렌더러와 같은 `line_alpha`를 쓰고, 진행 중 획은 첫 점이 오면 정한다. `LiveStroke::new`는 이제 획 자신의 색을 받는다.
- 시험: 진행 중 dab을 점 하나씩 그린 것이 획 전체를 한 번에 칠한 것과 바이트 단위로 같음(부드러운 에어브러시, 스프레이 둘, 부드러운 지우개), pen-up 증분 시험을 불투명도 압력 펜·부드러운 에어브러시·스프레이로 넓혀 그리기·지우기 모두 레이어 표면 1단계, 화면 2단계 이내.
- 진행 중 획은 표본 수 상한(5만)을 모르고 그린다. 상한을 넘는 긴 획은 확정 뒤 간격이 넓어진 모양으로 바뀐다.

### M4-5b 메모리 예산을 PC에 맞춤 (2026-10-08)

**잰 것 (원본 ⑤를 펜으로 바꾼 사본, 최대화 창, 160Hz, 작업자 8스레드, 31.3GiB PC):**

- 레이어 표면 추정치는 원본 ⑤ 320MiB(1/2 80, 1/4 20), ②p 224MiB이고, 모든 fixture가 512MiB 안이다. 원본 ⑤가 단계별 렌더로 떨어지지는 않았다. 모자란 것은 재생 프레임이다.
- 화면 맞춤(1/2 축소)은 프레임 16MiB × 30이 768MiB 안이라 25fps, 949~960MiB다. 100%에서는 프레임 하나가 64MiB라 768MiB에 7장만 들어, 25초에 266프레임을 다시 그리며 10.6fps였다. 렌더 예산 8GiB 측정용 빌드는 30장을 한 번 그리고 25.0fps, 최대 2734MiB였다. 모든 프레임을 두려면 예산이 약 2.24GiB(프레임 1.92 + 표면 0.32)이고, 그 밖에 프로그램·표시·작업 메모리가 약 500MiB다.
- 2.2.13은 미리보기 캐시를 설치 메모리의 1/16(128MiB~2GiB)으로 정하고, ⑤ 재생 중 최대 working set이 325MiB였다(m0-evidence 5절). 3.0은 화면 맞춤에서 2.9배, 100%에서 8.4배다.
- 이 PC는 사용 가능 메모리(14.8GiB)보다 커밋 여유(13.5GiB, 페이지 파일 9.5GiB)가 작다. 다른 프로그램이 메모리를 쓰면 페이징보다 할당 실패가 먼저 온다. 설치 메모리만 기준으로 하면(1/4 = 7.8GiB) 다른 프로세스가 10GiB를 쓰는 중 원본 ⑤ 100%가 2.7GiB를 잡아 커밋 여유가 0.7GiB만 남는다. 다른 앱이 위험해서 이 경우는 돌리지 않았다.

**정한 것 (`apps/ugurugu/src/budget.rs`, `ugu_win::memory`):** 캐시 예산 = min(설치 메모리 / 4, (min(사용 가능 물리, 커밋 여유) + 캐시가 쥔 것) / 2)이고, 최소 256MiB, Windows가 알려 주지 않으면 768MiB다. 레이어 표면은 그 절반이다.

- 설치 메모리 비율은 PC 크기에 따른 상한이다. 16GB급이면 4GiB라 원본 ⑤ 100%(2.24GiB)와 4096² 60프레임의 1/2 축소(1.04GiB)가 든다. 1/8이면 16GB급에서 ⑤ 100%가 30장 중 26장만 든다.
- 여유의 절반은 다른 프로그램 몫을 남기고 할당 실패를 피하기 위한 것이다.
- 재생을 계획할 때(쥔 프레임을 먼저 놓아 여유로 셈)와 분할을 요청할 때(작업자가 알린 표면 크기를 쥔 것으로 셈) 정한다. 작업자는 받은 표면 예산을 렌더마다 쓴다. 처음에는 작업자가 렌더마다 다시 계산했는데, 재생 프레임이 쌓여 여유가 줄면 재생 도중 표면 예산이 줄어 단계별 렌더로 바뀔 수 있어 옮겼다.
- 시험: 16·32GiB 여유 충분(4·8GiB), 다른 프로그램이 대부분을 씀, 커밋 여유가 작음, 쥔 것을 셈, 최소값, 알 수 없음.

### M4-5 자르기·리사이즈 렌더 (2026-10-08)

- **의미:** 2.2.13 `applyReframeOperation`과 같다. 자르기는 캔버스를 바꾸고 내용은 화소 그대로 offset만큼 옮긴다(앞 캔버스 밖은 버림). 리사이즈는 그때까지의 화소를 `ImageResampler` 규칙으로 리샘플한다: 최근접은 화소 중심 `((2x+1)·원본)/(2·목표)`, Smooth는 가장자리를 늘인 이중선형(축소에도 면적 평균 없음). 뒤의 연산은 새 캔버스 좌표다. 참조 평가기의 최근접도 화소 중심으로 고쳤다(이전 `x·원본/목표`는 2.2.13과 반 화소 달랐다).
- **자르기 = 옮겨 그리기:** 리사이즈 사이(또는 끝까지)의 자르기들은 끊지 않는다. 각 구간을 뒤 자르기들의 offset 합만큼 옮겨 마지막 캔버스에 그리고, 앞 캔버스를 옮긴 사각형이 마지막 캔버스를 다 덮지 못할 때(넓히는 자르기)만 그 사각형으로 클립한다. 클립은 뒤 자르기가 바깥, 앞 자르기가 안쪽인 중첩 레이어라서 뒤 구간의 지우개가 앞 구간 내용에 닿는다. 선택 변형으로 끊을 때는 열린 클립을 닫았다가 다음 구간에서 다시 연다(앞 결과는 이미 그 클립 안이다). 마스크·이미지·선택 변형도 그 구간의 이동을 따른다.
- **리사이즈 = 끊어 그리기:** 앞 구간은 그 캔버스 전체(축소 재생이면 1/shrink)를 버퍼에 그리고, 다음 구간이 그것을 새 캔버스로 늘이거나 줄여 깐다(Vello 이미지, 최근접 Low·Smooth Medium). 리사이즈 바로 뒤의 선택 변형은 깐 결과를 옮겨야 하므로 한 번 더 끊는다. 아무것도 그리기 전의 리사이즈는 건너뛴다.
- **타일·예산:** 각 연산의 bounds를 앞 캔버스로 자르고 캔버스 변경을 따라 옮긴다(리사이즈는 이웃 화소 하나만큼 넓힘). 예산 계산(`op_bounds`)도 같다.
- **앱:** 캔버스 크기가 바뀌는 편집(되돌리기 포함)은 이전 캔버스의 분할을 버린다. 새 분할이 오기 전에 그리기 시작하면 새 크기의 진행 중 획을 이전 크기 화면에 합성해 범위를 넘던 것을 시험으로 잡았다(수정 없으면 패닉). 대화상자(M4-12)가 쓸 세션 명령 `crop_canvas`·`resample_image`를 더했다.
- 시험(렌더러): 자르기 하나·둘(좁혔다 넓힘)이 2.2.13 자르기와 바이트 단위로 같고 뒤 획이 새 캔버스에 그려짐, 최근접 2/3 리사이즈가 2.2.13과 바이트 단위로 같고 Smooth 확대·축소가 2단계 이내(Vello·2.2.13 모두 8비트 가중치, 잰 최대 1.8), 자르기 직후 선택 변형, 자르기 둘·리사이즈 둘·채우기·선택 변형·지우개가 든 문서가 스레드 수 무관 바이트 동일·타일 16·64·4096에서 1단계 이내·예산 초과 경로와 같음, 1/2·1/4 축소(자르기만 3단계, 리사이즈 포함 10단계 미만: 아래). compose 시험 문서를 자르고 그린 뒤 리사이즈한 것으로도 분할·pen-up 증분·예산 초과 시험을 돌린다. pen-up 증분은 레이어 표면에서 1단계 이내이고, Multiply 0.6 레이어를 거친 합성에서는 몇 화소가 2단계가 되어 합성 기준을 2로 했다. 앱: 자르기 직후·리사이즈 뒤 그리기와 되돌리기(end-to-end), 재생 중 캔버스 변경을 축소 프레임이 따라감.
- `ugu-doc pen-only`·`render`는 자르기·리사이즈를 더 이상 빼지 않는다. `ugu-doc reframe <in> <out> <crop|resample|both>`는 레이어마다 연산 중간에 7/8 자르기(가운데 기준), 3/4 Smooth 리사이즈, 또는 둘 다를 넣는다.

**축소 재생의 오차 (1/2 / 1/4, 원본 크기를 상자 평균한 것과 평균 차이):** 처음 구현은 자르기도 끊어 그렸는데, offset이 shrink의 배수가 아니면 최근접으로 반 화소 어긋나 4.24 / 4.34단계였다(2.2.13 표시 축소도 같은 방식). 옮겨 그리기로 0.13 / 0.18이 되었다. 리사이즈는 작게 그린 것을 리샘플하므로 원본을 리샘플한 뒤 줄인 것과 다르다: Smooth 1.4~3.4, 최근접 2.3~4.5(2.2.13도 같다).

### M4-4 선택 변형과 이미지 렌더 (2026-10-08)

- **이미지:** `ugu_render::image::decode`가 저장된 PNG를 8비트 RGBA로만 받아 기록된 크기와 같은지 확인하고 premultiplied로 바꾼다. 렌더러가 자산 id로 캐시하고 두 렌더 동안 쓰이지 않으면 버린다. 그리기는 Vello 이미지 paint(최근접 Low, 이중선형 Medium)로 같은 장면 안에서 한다.
- **선택 변형:** 연산 순서상 그때까지의 결과가 필요하므로 레이어 그리기를 그 자리에서 끊는다. 다음 구간은 앞 구간 결과를 원본 배율 최근접 이미지로 깔고(끊지 않은 것과 바이트 단위로 같음, 시험), `keep_source`가 아니면 마스크를 DestOut으로 지운 뒤, T(마스크) 클립 안에 앞 결과를 T로 옮긴 이미지를 덮는다. 선택 변형이 든 병합 구간은 따로 그린 뒤 그 불투명도로 얹는다(구간은 격리되므로 의미가 같다, 같은 내용을 별도 레이어로 그린 것과 1단계 이내, 시험).
- **표본:** Nearest는 최근접. Smooth는 이중선형이되 90° 단위 회전·뒤집기와 정수 이동이면 최근접(2.2.13 `SelectionOperation`과 같은 규칙, 화소 중심이 화소 중심으로 가므로 정확하다).
- **타일:** 옮겨진 마스크·이미지의 bounds가 닿는 타일을 더한다. 레이어 표면이 연산 결과 전체이므로 분할·pen-up 증분은 그대로 맞다(compose 시험 문서에 선택 변형·이미지를 넣어 확인).
- 시험(렌더러): 프레임마다 그 프레임의 결과를 옮김(정수 이동·남기기·90° 회전, 기대값과 1단계 이내), 이미지가 정수 위치에서 디코드한 화소 그대로 덮임, 병합 구간, 스레드 수 무관 바이트 동일, 타일 16·64·4096에서 1단계 이내(옮긴 내용이 원래 타일 밖으로 나가는 경우 포함), 1/2·1/4 축소 평균 3단계 미만. 참조 평가기에 `PlaceImage`와 시험(이미지는 움직이지 않고 앞뒤 순서를 지킴)을 더했다.
- `check`는 이제 자르기·리사이즈(M4-5)와 에어브러시·스프레이(M4-6)만 거절한다. `ugu-doc pen-only`·`render`는 자르기·리사이즈만 뺀다.

**끊어 그리기의 비용 (원본 ⑤, 브러시는 펜으로, headless 8스레드, 프레임 p50):** 처음 구현은 끊을 때마다 4096² 결과(64MiB)를 복제해 102.3ms였고, 선택 변형을 빼면 73.3ms였다(이미지를 빼면 87.6ms). 복제 대신 버퍼 두 개를 번갈아 쓰게 해(앞 구간 버퍼를 다음 구간의 바탕으로, 남는 하나는 렌더러가 보관) 82.6ms가 됐다. 선택 변형이 있는 4096² 레이어를 그리는 동안 버퍼가 둘 더 필요해 전체 프레임 뒤 최대 working set이 505 → 622MiB다. 이미지만 든 레이어는 움직이지 않아 앱에서는 첫 프레임에만 그린다(headless `render`는 revision 없이 매 프레임 다시 그린다).

### M4-3 마스크 연산 렌더 (2026-10-08)

- `ugu_render::mask::Runs`: 1비트 마스크를 행별 구간으로 읽고, 교집합·4-이웃 가장자리·경로(구간마다 화소 경계의 사각형)를 만든다. 원본 크기에서 이 경로의 coverage는 화소마다 0 또는 1이라 클립이 비트 그대로다.
- 획 + clip은 클립 레이어 안에, 지우개 + clip은 클립이 있는 DestOut 레이어로, `ClearSelection`은 DestOut으로 그린다. `Fill`은 (coverage ∩ clip)을 DestOut으로 지운 뒤 색을 칠해 대체하고, 가장자리 ∩ clip은 DestOver 레이어로 칠한다. Vello는 클립 레이어를 넣는 순간의 aliasing 설정을 클립에 쓰므로, 안티에일리어싱 없는 펜도 클립을 먼저 넣어 클립이 정확하다. 클립 레이어를 겹치면 격리 그룹이 되어 DestOut이 아래 내용에 닿지 않으므로, 마스크끼리의 교집합은 비트에서 미리 구한다.
- 참조 평가기(`semantics.rs`)의 채우기를 2.2.13 규칙(대체 + 가장자리)으로 바꾸고 반투명 채우기 시험을 더했다. 이전 시험은 불투명 색만 써서 위에 덮기와 대체가 구별되지 않았다.
- 시험(렌더러): 클립된 획·지우개·지우기가 마스크 안 화소만 바꾸고 그 값이 클립 없는 결과와 바이트 단위로 같음(안티에일리어싱 켬·끔), 채우기 대체·가장자리, 흔들려도 채우기는 프레임마다 같음, 스레드 수 무관 바이트 동일, 타일 16·64·4096에서 1단계 이내, 1/2·1/4 축소가 원본 상자 평균과 평균 3단계 미만. compose 시험 문서에 클립된 채우기와 지우기를 넣어 분할·pen-up 증분·예산 초과 경로도 같은 시험을 통과한다.
- pen-up 증분(`last_stroke`)은 clip이 없는 획만 찍는다. 클립된 획은 새 분할이 그린다(세션이 선택 안에 그리는 것은 M4-8).
- `ugu-doc pen-only`·`render`는 이제 채우기·지우기·clip을 남기고 이미지·선택 변형만 뺀다. `ugu-doc fills`는 레이어마다 큰 채우기를 더한 측정 문서를 만든다.

**비용 (②p에 레이어마다 화면 1/3 원형 채우기(줄무늬 clip, 안티에일리어싱)와 지우기 하나, headless, 8스레드, 프레임 p50 / 획 뒤 분할 p50):**

| 문서 | 마스크 경로를 프레임마다 만듦 | 렌더러가 캐시 |
|---|---|---|
| ②p (채우기 없음) | 35.4 / 17.7ms | 35.5 / 16.6ms |
| ②p + 채우기 14개 | 153.4 / 205.5ms | 47.5 / 26.3ms |

처음 구현은 프레임마다(예산 계산에서 한 번 더) 2048² 마스크 비트를 훑어 경로를 만들었다. 마스크는 저장된 뒤 바뀌지 않으므로 렌더러가 비트 주소(그 `Arc`를 쥐어 다른 마스크가 같은 주소를 받지 못함)로 경로를 캐시하고, 두 렌더 동안 쓰이지 않은 것은 버린다. 예산 계산은 비트를 읽지 않고 마스크 bounds로 범위만 잡는다. 남은 +12ms는 채우기 경로의 인코딩·래스터(스레드 합 +40 / +31ms)로, 큰 채우기 하나에 프레임당 약 0.85ms다. 움직이지 않는 레이어는 레이어 캐시가 다시 그리지 않는다. 구간을 위아래로 합쳐 경로 요소를 줄이는 것은 원본 ⑤로 필요한지 M4-5에서 본다.

**앱 확인 (②p + 채우기 14개, 최대화 창, 160Hz, 작업자 8스레드):** 화면에서 채우기가 줄무늬 클립으로 잘리고 레이어 합성 모드대로 섞이며, 썸네일에도 나온다. 재생은 첫 프레임 85ms, 30프레임이 모두 보이기까지 1.56s, 이후 25.0fps(60ms 넘는 간격 0). 획 20개: 칸당 CPU p50 1.68 / p95 1.91ms, pen-up CPU 5.25 / 5.71ms. 재생 중 최대 working set 1029MiB로 1GiB 참고값을 조금 넘는다(마스크 캐시와 채우기 경로만큼). ### M4-1 ②p 프레임의 원인 (2026-10-07, release, headless, 8스레드)

`ugu-doc layers <file> <threads>`는 레이어마다 그 레이어만 남긴 문서(다른 페인트 레이어의 연산을 비우고 클리핑을 끔, 계획 구조는 그대로)를 1스레드로 그려 단계별 p50을 내고, 그 비용으로 스레드 배정을 계산한다.

- **배정 순서는 원인이 아니다.** ②p의 레이어 14개가 모두 12~14ms(합 183~186ms, 칠해진 화소 약 15%)다. 8스레드에서 문서 순서 27.2ms, 비싼 것부터 26.1~26.6ms, 고르게 나눈 하한 22.8~23.3ms다. 14개를 8스레드로 그리면 두 바퀴다.
- **코어 종류도 아니다.** 프로세스를 P코어 8개(0xc03c03)로 묶으면 p50 43.8~46.8ms, E코어 8개 50.2~50.8ms, 제한 없음 44.4~47.8ms(같은 시각에 잰 값).
- **합성(약 10ms)은 계산에 묶여 있다.** 1·2·4·8스레드에서 70 / 36 / 21 / 10ms로 정비례한다. 모드 분기를 루프 밖으로 빼면 64ms(오차 수준), 투명 화소를 건너뛰지 않는 분기 없는 루프는 167ms로 느렸다(레이어의 85%가 투명). 둘 다 넣지 않았다.
- **동시 실행에서 윤곽이 부풀었다**(혼자 29 → 동시 41~46ms, 스레드 합). 한 프레임의 윤곽 경로는 요소 약 100만 개(약 56MB)이고 획 하나가 약 34KB라, 매 프레임 할당·재할당·해제하면 Windows 힙이 페이지를 OS에 돌려주고 다시 받는다. mimalloc은 해제한 메모리를 붙잡아 같은 이득을 냈지만(`MIMALLOC_PURGE_DELAY=0~10`으로 바로 돌려주면 이득이 사라짐), 경로를 다시 쓰면 할당자와 무관하게 없어진다. Windows segment heap(manifest `heapType`)은 39 → 45ms로 느렸다.

3회 교대(프레임 p50 / p95, 첫 프레임, 최대 working set: 전체 프레임 뒤 / 분할까지 끝):

| 빌드 | 프레임 (ms) | 첫 프레임 (ms) | working set (MiB) |

경로 재사용만으로 mimalloc과 같은 프레임 이득이 나와 C 의존성(또는 순수 Rust 재구현 `rusty_alloc`, 1.0이 2026-08이고 0.3.2 이하에 use-after-free 3건)은 들이지 않는다. 래스터가 붙잡는 경로는 작업자가 쉴 때 `release_scratch`로 함께 놓는다.

남은 것(35.5ms = 그리기 약 25.5 + 합성 약 10): 스레드 합은 윤곽 21.6 / 인코딩 약 70 / 래스터 약 88 / 합성 약 80(8스레드)이다. 모두 완벽히 나눠도 (180 + 80) / 8 ≈ 32.5ms라, 배정만으로는 여유가 거의 없고 일 자체를 줄여야 한다. 더 해 본 것:

- 합성에서 8화소가 모두 투명하면 한 번에 건너뛰기: 9.6 → 11.1ms로 느려 넣지 않았다(가장자리 안티에일리어싱 때문에 투명 화소가 흩어져 있다).
- 획 표본 캐시: 표본은 프레임과 무관하지만 모든 획을 다시 표본화하는 데 1스레드 5.1~5.4ms라 8스레드에서 최대 0.7ms다. 넣지 않았다.
