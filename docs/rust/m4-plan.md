# M4 분해: 편집 기능 완성 (2026-10-07)

M4 종료 조건(계획 11절): 프레임별 선택 의미·merge/erase·pending edit가 회귀 fixture를 통과한다. 이를 다음 세 가지로 확인한다.

- [scope.md](scope.md) 3절의 M4 행(선택·자동 선택·채우기·변형, 이미지·문자, 스포이드·획 속성, 자르기·리사이즈, 마커·에어브러시·스프레이, 모션 전체)이 앱에서 동작하고, 모든 새 연산이 M3의 한 `RenderPlan`·합성기로 그려진다.
- [adr-operations-and-format.md](adr-operations-and-format.md) 2절의 의미(지우개는 앞선 결과에만, 선택 변형은 프레임마다 그 프레임의 결과를, 채우기 coverage 고정, 자르기와 리사이즈의 순서)가 참조 평가기와 실제 렌더러 모두에서 회귀 fixture로 고정된다.
- M3에서 넘긴 ②p 30fps 처리 능력을 충족하고, 이제 열 수 있는 원본 fixture ②·⑤(에어브러시·스프레이·이미지·마스크)를 2.2.13과 같은 내용으로 나란히 잰다.

범위는 scope.md 3절의 M4 행, M3에서 넘긴 것([m3-plan.md](m3-plan.md) 9절), 계획 5.2~5.4·6.2·7.2절이다. 2.2.13 동작은 C++ 소스에서 확인했다(각 행에 파일).

## 3. 구조

- **새 연산은 레이어 표면 안에서 평가한다.** M3에서 레이어 결과는 연산을 순서대로 적용한 표면이다. `Fill`·`ClearSelection`은 마스크 단위 화소 연산, `TransformSelection`·`PlaceImage`는 아핀 리샘플 후 source-over, `Crop`·`Resample`은 표면 자체를 바꾼다. 합성(그룹·클리핑·합성 모드)은 그대로다.
- **비국소 연산은 레이어 전체로 승격한다(계획 7.2절).** `TransformSelection`은 마스크 bounds 안의 모든 타일을, `Crop`·`Resample`은 레이어 전체를 입력으로 쓴다. 이런 연산이 있는 레이어의 pen-up 증분은 그 연산 뒤에 그린 획에만 쓰고, 연산 앞을 바꾸는 편집은 레이어를 다시 그린다. 승격 빈도를 센다.
- **선택은 세션 상태다(ADR 2절).** 마스크는 세션에 있고, 문서에는 그것을 쓰는 연산이 확정될 때만 들어간다. 자동 선택·채우기의 참조 이미지는 세션이 불변 snapshot으로 작업자에게 맡긴다.
- **대기 편집은 문서 사본에 덧붙인 연산이다.** 미리보기는 대기 연산을 덧붙인 계획을 같은 합성기로 평가하므로, 적용한 결과와 화면이 바이트 단위로 같다(2.2.13 `selectionMovePreviewMatchesCommittedPixelOperation`와 같은 성질).

### M4-2 GUI batch·pen-up 재측정 (2026-10-07, release, 2560×1600 창, 160Hz, 작업자 8스레드)

`baseline_probe.py stroke --thread render --no-play-key`(M3-13과 같은 방법). 획 하나 = 40칸 이동 + 놓기. 값은 render 스레드의 p50 / p95(ms).

| fixture | 칸당 CPU | 칸당 점유 | pen-up CPU | pen-up 점유 |
|---|---|---|---|---|
| ① (20획) | 1.33 / 1.54 | 2.26 / 3.18 | 2.85 / 3.30 | 2.02 / 3.26 |
| ②p (20획) | 1.66 / 1.89 | 2.66 / 3.77 | 4.86 / 5.24 | 5.06 / 9.06 |
| ③ (20획) | 1.48 / 1.68 | 2.43 / 3.66 | 4.30 / 4.98 | 2.81 / 4.00 |
| ⑤p (20획 × 2) | 1.48~1.50 / 1.71~1.74 | 2.42~2.45 / 3.57~3.71 | 3.95~4.13 / 4.45~4.72 | 3.54~3.78 / 6.78~9.04 |

칸당 CPU는 모두 목표(p95 4ms)와 2.2.13(2.2~3.8ms) 안이다.

**pen-up 점유 p95가 8ms를 넘는 것은 측정 방식 때문이다.** 프레임 단계 시간을 임시로 로그에 남겨(②p 30획) 보면, pen-up 뒤 render 스레드의 일은 셋으로 나뉜다: `end_stroke` p50 2.71 / p95 4.03ms, 바로 이어지는 프레임 1.72 / 2.33ms, 작업자가 썸네일을 보낸 뒤 다음 화면 주기의 프레임(썸네일 텍스처 업로드) 1.92 / 3.40ms. 앞의 둘 사이에는 공백이 없고, 뒤 프레임과는 화면 주기를 기다리는 공백(p50 3.9ms)이 있다. probe는 스레드가 2ms 넘게 멈출 때 한 덩어리가 끝났다고 보는데, 썸네일이 도착할 때 render 스레드가 잠깐 깨어나 이 공백을 이으면 두 프레임을 한 덩어리로 센다. 한 번에 이어지는 일은 p95 약 6.4ms(②p)다. 2.2.13의 pen-up 점유는 p95 30.3ms였다.

**고친 것:** ⑤p의 `end_stroke`가 3.6~6.0ms로 ②p의 1.5배였다. 세션 커밋은 0.1ms였고, 대부분이 진행 중 획의 문서 크기 coverage 버퍼(4096²이면 64MiB)를 획마다 할당하고 pen-up에서 해제하는 비용이었다(②p 0.8ms, ⑤p 3.0ms, 면적에 비례). 버퍼를 캔버스가 보관해 다음 획에 넘기고, 쓴 사각형만 지운다(`LiveStroke::into_spare`, 재사용한 버퍼의 결과가 새 버퍼와 같다는 시험). 재생을 시작하거나 문서를 바꾸면 놓는다. M3 빌드와 교대로 잰 pen-up CPU: ⑤p 6.27~6.29 → 3.95~4.13ms, ②p 5.58 → 4.86ms(p50).

### M4-1 ②p 프레임의 원인 (2026-10-07, release, headless, 8스레드)

`ugu-doc layers <file> <threads>`는 레이어마다 그 레이어만 남긴 문서(다른 페인트 레이어의 연산을 비우고 클리핑을 끔, 계획 구조는 그대로)를 1스레드로 그려 단계별 p50을 내고, 그 비용으로 스레드 배정을 계산한다.

- **배정 순서는 원인이 아니다.** ②p의 레이어 14개가 모두 12~14ms(합 183~186ms, 칠해진 화소 약 15%)다. 8스레드에서 문서 순서 27.2ms, 비싼 것부터 26.1~26.6ms, 고르게 나눈 하한 22.8~23.3ms다. 14개를 8스레드로 그리면 두 바퀴다.
- **코어 종류도 아니다.** 프로세스를 P코어 8개(0xc03c03)로 묶으면 p50 43.8~46.8ms, E코어 8개 50.2~50.8ms, 제한 없음 44.4~47.8ms(같은 시각에 잰 값).
- **합성(약 10ms)은 계산에 묶여 있다.** 1·2·4·8스레드에서 70 / 36 / 21 / 10ms로 정비례한다. 모드 분기를 루프 밖으로 빼면 64ms(오차 수준), 투명 화소를 건너뛰지 않는 분기 없는 루프는 167ms로 느렸다(레이어의 85%가 투명). 둘 다 넣지 않았다.
- **동시 실행에서 윤곽이 부풀었다**(혼자 29 → 동시 41~46ms, 스레드 합). 한 프레임의 윤곽 경로는 요소 약 100만 개(약 56MB)이고 획 하나가 약 34KB라, 매 프레임 할당·재할당·해제하면 Windows 힙이 페이지를 OS에 돌려주고 다시 받는다. mimalloc은 해제한 메모리를 붙잡아 같은 이득을 냈지만(`MIMALLOC_PURGE_DELAY=0~10`으로 바로 돌려주면 이득이 사라짐), 경로를 다시 쓰면 할당자와 무관하게 없어진다. Windows segment heap(manifest `heapType`)은 39 → 45ms로 느렸다.

3회 교대(프레임 p50 / p95, 첫 프레임, 최대 working set: 전체 프레임 뒤 / 분할까지 끝):

| 빌드 | 프레임 (ms) | 첫 프레임 (ms) | working set (MiB) |
|---|---|---|---|
| 이전 | 38.8~39.5 / 44.8~46.3 | 71~73 | 338~341 / 571~589 |
| 경로 재사용 | 35.4~35.6 / 37.2~38.8 | 53~55 | 346~348 / 657~661 |
| mimalloc | 35.5~35.7 / 39.1~40.6 | 47~48 | 387~396 / 663~703 |
| 경로 재사용 + mimalloc | 35.0 / 37.5~38.5 | 45~47 | 343~350 / 655~660 |

경로 재사용만으로 mimalloc과 같은 프레임 이득이 나와 C 의존성(또는 순수 Rust 재구현 `rusty_alloc`, 1.0이 2026-08이고 0.3.2 이하에 use-after-free 3건)은 들이지 않는다. 래스터가 붙잡는 경로는 작업자가 쉴 때 `release_scratch`로 함께 놓는다.

남은 것(35.5ms = 그리기 약 25.5 + 합성 약 10): 스레드 합은 윤곽 21.6 / 인코딩 약 70 / 래스터 약 88 / 합성 약 80(8스레드)이다. 모두 완벽히 나눠도 (180 + 80) / 8 ≈ 32.5ms라, 배정만으로는 여유가 거의 없고 일 자체를 줄여야 한다. 더 해 본 것:

- 합성에서 8화소가 모두 투명하면 한 번에 건너뛰기: 9.6 → 11.1ms로 느려 넣지 않았다(가장자리 안티에일리어싱 때문에 투명 화소가 흩어져 있다).
- 획 표본 캐시: 표본은 프레임과 무관하지만 모든 획을 다시 표본화하는 데 1스레드 5.1~5.4ms라 8스레드에서 최대 0.7ms다. 넣지 않았다.
