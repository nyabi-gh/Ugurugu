# Ugurugu 3.0 Rust 종합 검토 보고서

Ugurugu 3.0은 핵심 편집 모델과 렌더 정확성의 기반이 탄탄하지만, **현재 상태로 정식 출시하기에는 문서 전환과 저장 완료 처리의 데이터 보존 문제가 남아 있다.** 우선순위는 새 기능이나 대규모 엔진 재작성보다 저장·열기·종료·복구의 상태 관리 수정이다. 기본 패널 배치가 일반적인 크기의 창에서도 주요 조작부를 화면 밖으로 밀어내는 문제도 출시 전에 해결해야 한다.

기존 Rust 테스트는 **485건 통과, 3건 제외**였고, Release 빌드·형식 검사·Clippy·의존성 정책 검사도 통과했다. 추가한 검토용 시험에서는 **데이터 보존 결함 5건, 업데이트 재시도 결함 1건, 작은 창의 배치 결함 1건, 여러 창의 설정 덮어쓰기 1건**을 실행으로 확인했다. 테스트 통과와 사용자 작업 전체의 안전성 사이에 공백이 있다.

### 유지해야 할 강점

1. **레이어를 순서 있는 연산으로 표현한다.** `Paint`, `Erase`, `Fill`, 선택 변형, `Crop`, `Resample`, `Isolated`를 구분해 잘못된 필드 조합을 줄였다. 병합 시 지우개가 다른 레이어에 영향을 주는 문제를 연산 의미 차원에서 다룬다.
2. **변경을 원자적으로 확정한다.** `commit`과 `History::group`은 적용 중 실패하면 되돌린다. 저장한 `StateId`로 되돌아왔을 때 수정 표시가 없어지는 모델도 올바르다. 문제는 이 기반 밖에 있는 앱의 비동기 완료 처리다.
3. **큰 자료는 공유한다.** 획 점·마스크·이미지의 `Arc` 공유와 snapshot은 저장·이력·렌더가 같은 큰 버퍼를 불필요하게 복사하지 않게 한다.
4. **정확성을 실행 가능한 규칙으로 고정했다.** 참조 평가기, 렌더 fixture, 병합 전후 비교, 선택 이동의 프레임별 의미, SIMD·스레드 수 관련 시험이 있다. 이미지 해시만 갱신하면 잘못된 그림도 통과하는 방식에 머물지 않는다.
5. **저장 파일을 교체하기 전까지 이전 파일을 유지한다.** 같은 디렉터리의 임시 파일, 동기화, Windows 파일 교체를 사용하며 디스크 부족과 교체 실패 시험도 있다.
6. **입력 파일의 실제 압축 해제량을 제한한다.** 새 포맷은 항목별·전체 출력 상한, 이름·중복·압축 방식·내용 검증을 갖춘다. 구형 `.ugu`도 입력 크기 제한을 사용한다.
7. **관측 도구가 제품과 함께 있다.** `ugu-doc`의 fixture·render·digest·bench·stop, 입력 지연 도구, 로그·크래시 기록은 이후 성능 수정의 판단 비용을 낮춘다.

## 5 데이터 보존과 편집 정확성

### U3 01 저장 후 종료가 추가 편집을 잃음

**P1 · 실행 확인.** 닫기 확인 창에서 저장을 선택하면 `after_save = Close`가 된다. 저장은 snapshot으로 실행되고 편집은 계속 가능하지만, 저장 성공 처리에서는 현재 세션이 다시 변경됐는지 검사하지 않고 `proceed(Close)`를 호출한다.

재현에서는 레이어가 2개인 상태를 저장한 뒤 완료 이벤트를 처리하기 전에 레이어를 하나 더 추가했다. 결과는 `disk_layers=2`, `live_layers=3`, `dirty=true`, `close=true`였다. 저장 자체는 올바르지만 종료 판단이 현재 내용을 보호하지 못한다. 정상 종료 경로는 복구 폴더도 정리한다.

**개선:** 후속 종료·새 문서·열기·업데이트를 실행하기 직전에 저장 대상의 문서 ID와 현재 상태를 다시 비교한다. 달라졌다면 다시 저장 여부를 묻거나 사용자가 중단할 수 있는 재저장 흐름으로 돌아간다. 종료를 기다리는 저장 동안에는 편집을 제한하는 방식도 가능하지만, 일반 저장과 구분해야 한다.

**완료 기준:** 저장 후 종료·열기·새 문서·업데이트 각각에서 저장 중 추가 편집을 넣어도 새 편집이 사라지지 않는다.

### U3 02 비동기 열기의 완료가 새 편집을 덮음

**P1 · 실행 확인.** 파일을 고른 직후 `busy_dialog`가 해제된다. 실제 읽기를 수행하는 `open_path`는 읽기 상태나 요청의 문서 버전을 기록하지 않으며, `Opened`는 도착 시점의 캔버스를 바로 교체한다.

### U3 04 연속 저장의 완료가 새 문서에 이전 경로를 붙임

**P1 · 실행 확인.** `save()`와 `start_save()`는 이미 저장 중이어도 추가 저장을 큐에 넣을 수 있다. 상태는 `saving: bool` 하나이므로 첫 번째 응답을 받으면 아직 두 번째 응답이 남아 있어도 `saving=false`가 된다. 이후 새 문서로 이동하면 늦게 도착한 `Saved`가 새 문서에 이전 파일 경로와 저장 상태를 적용한다.

**완료 기준:** 연속 저장·다른 이름으로 저장·문서 교체를 섞어도 문서와 파일 경로가 뒤섞이지 않는다. 중복 완료와 오래된 완료도 안전하게 무시한다.

### U3 05 적용에 실패한 임시 변형을 버림

**P1 · 실행 확인.** `apply_transform()`은 `pending.take()`로 임시 변형을 먼저 제거한 뒤 문서에 확정한다. 한도를 넘으면 코어 변경은 안전하게 롤백되지만 임시 변형은 복원되지 않는다. `settle()`과 복구용 `settled_document()`는 적용 오류를 무시한다. “좌표를 검증했으므로 변형은 실패하지 않는다”는 주석은 문서 연산 수·자료 용량 제한을 고려하지 못한다.

유효한 문서에 연산 20,000개를 넣고 선택을 1픽셀 옮겼다. 확정 결과는 `TooManyOperations(20001)`였지만 `pending=false`, `dirty=false`로 바뀌었다. 도구를 변경하는 자동 확정 경로에서도 원래 문서로 되돌아갔다. 복구용 snapshot도 변형이 없는 문서를 반환했다.

**개선:** 성공 후에만 임시 상태를 제거한다. `settle`과 `apply_pending`은 `Result`를 반환하고, 실패 시 후속 저장·내보내기·도구 변경을 중단하거나 사용자가 명시적으로 취소하도록 한다. 한도에 가까워지면 구체적인 이유와 해결 행동을 안내한다.

### U3 08 확장자를 바꾼 최종 저장 경로의 확인이 없음

**P1 · 정적 확인, 네이티브 재현 필요.** 대화상자는 `FOS_OVERWRITEPROMPT`로 사용자가 선택한 경로의 덮어쓰기를 확인한다. 그러나 `Show`와 `GetResult`가 끝난 뒤 `with_extension_of`가 경로에 확장자를 추가할 수 있다. 변경된 최종 경로에 대한 존재 확인·재확인 없이 저장한다.

예를 들어 대화상자 결과가 `drawing.txt`이고 선택 형식이 `.ugurugu`라면 실제 저장 대상은 `drawing.txt.ugurugu`다. 이 두 번째 파일이 이미 존재하면 대화상자가 확인한 경로와 교체 대상이 다를 수 있다. 보통의 확장자 없는 입력은 `SetDefaultExtension`이 처리하므로 이 위험을 모든 저장에 일반화해서는 안 된다.

Microsoft 문서는 `FOS_OVERWRITEPROMPT`를 같은 이름의 기존 파일에 대한 확인으로, `FOS_STRICTFILETYPES`를 지정한 확장자로 제한하는 별도 옵션으로 정의한다. 현재 코드는 후자를 명시적으로 설정하지 않는다. [공식 옵션 문서](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/ne-shobjidl_core-_fileopendialogoptions), [기본 확장자 문서](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifiledialog-setdefaultextension).

**개선:** 최종 경로를 대화상자 안에서 확정하게 하거나, 반환 후 경로가 바뀌었고 최종 대상이 존재하면 그 정확한 경로에 대해 다시 확인한다. 문서·프리셋·이미지 내보내기에 공통으로 적용한다.

**완료 기준:** 다른 확장자 직접 입력, 따옴표 입력, 형식 선택 변경, 이미 존재하는 보정 후 파일을 실제 Windows 대화상자로 시험한다. 취소하면 기존 파일의 바이트가 그대로여야 한다.

### 국제화와 접근성

Fluent 키의 언어별 일치 검사, 아이콘 버튼의 이름, 키보드 메뉴 이동, 도킹의 키보드 조작, 포커스 복귀를 갖춘 점은 좋다. 반면 번역 파일이 완전하다는 시험은 소스에 남은 영어 문구를 찾지 못한다. `Untitled`, `Saving ...`, `Saved ...`, `Not saved: ...`, 변형·텍스트 적용 오류, WARP 안내는 대표적인 잔여 경로다. 코어 오류를 그대로 붙이면 한국어 UI에서도 이유가 영어로 출력된다.

저장·실패 문구부터 Fluent로 옮기고, 사용자가 해야 할 행동을 함께 표현하는 것이 좋다. 예를 들어 내부 오류 문자열만 보이기보다 “저장하지 못했습니다. 다른 폴더를 선택하세요.”와 세부 정보를 분리한다. 언어 키 검사와 별도로 사용자에게 보이는 문자열의 직접 삽입을 검사할 필요가 있다.

### U3 06 다운로드된 업데이트를 다시 적용할 경로가 사라짐

**P2 · 실행 확인.** 다운로드 완료 시 `ready`를 설정하고 한 번만 `Next::Install`을 보낸다. 이 순간 저장 중이거나 파일 대화상자가 열려 있으면 `Files::request`가 요청을 버린다. 미저장 확인에서 사용자가 취소하는 경우도 있다. 이후 수동 업데이트 확인은 `ready.is_some()` 때문에 바로 반환하며, `ask()`는 `offer`와 `notice`만 표시한다.

## 9 코드 품질과 보안 경계

### 상태 관리가 파일 길이보다 먼저다

`document.rs` 3,871줄, `files.rs` 2,053줄, `canvas.rs` 1,963줄, `ui/mod.rs` 1,576줄처럼 큰 파일이 있다. 테스트가 포함된 파일은 길이만으로 제품 코드가 과도하다고 판단하면 안 된다. 그러나 파일 서비스가 대화상자·저장·열기·복구·내보내기·업데이트를 모두 조정하면서 여러 boolean을 조합하는 것은 이번 재현 결함들과 직접 연결된다.

먼저 다음 상태를 명시적으로 표현하는 편이 좋다.

- 문서 세대와 현재 편집 상태
- 파일 작업의 ID·종류·대상 경로·요청 문서
- 저장 후 실행할 동작과 그 전제 조건
- 복구본 인계 중 보존해야 할 이전 세대
- 적용을 기다리는 업데이트

그다음 파일 서비스의 순수 상태 전이 부분을 UI·작업자 코드에서 분리하면 이벤트 순서를 테스트하기 쉽다. 같은 저장소의 `cache::Version { document, revision }`가 이미 좋은 선례다. 렌더러는 연산 replay, 레이어 캐시, 래스터 준비, 테스트를 경계로 점진적으로 나눌 수 있다. 동작을 바꾸지 않는 파일 이동보다 지금은 실패 처리 수정의 가치가 크다.

### 오류 전파와 불변 조건

프로덕션의 `expect`가 모두 문제는 아니다. “직전에 생성한 값” 같은 불변 조건과 실제로 실패할 수 있는 외부 작업을 구분해야 한다. 특히 스레드 생성, 채널 전송, 작업자 종료, 임시 편집 확정처럼 실패가 가능한 경로의 `expect`·`let _ =`는 별도 검토가 필요하다.

`settle()`이 확정 실패를 버리는 문제는 이미 실행으로 확인했다. 파일·설정 작업자의 채널 전송 실패를 무시하는 경로도 있어, 작업자 panic 시 UI가 완료를 기다리는 상태로 남을 수 있는지 후속 시험이 필요하다. 이 항목은 이번에 worker panic으로 재현하지 않았으므로 별도 개선 후보로 둔다.

### U3 10 사용자 텍스트가 기본 로그에 기록됨

**P2 · 정적 확인.** `Canvas::apply_text`는 성공 시 `tracing::info!`에 `session.text_content` 전체를 넣는다. 기본 로그 필터는 `info`이고 파일 로그가 켜져 있다. 따라서 사용자가 작품에 입력한 문구가 진단 로그에 그대로 남는다. 도움말은 문제 신고 시 로그 폴더를 첨부하도록 안내한다.

자동 업로드가 없다는 점은 유지할 장점이지만, 사용자가 로그에 작품 본문이 들어간다는 것을 예상하기는 어렵다. 성능 측정에 필요한 값은 적용 시간·문자 수·윤곽 수로 충분한 경우가 많다.

**개선:** 기본 로그에서 원문을 제거하고 길이·처리 시간·오류 분류만 남긴다. IME 진단처럼 원문이 필요한 경우는 명시적으로 활성화한 진단 모드로 한정하고 기록 범위를 안내한다.

**완료 기준:** 임의의 식별용 문구를 입력·확정해도 기본 정보 로그와 진단 요약에 그 문구가 남지 않는다.

### 입력과 네이티브 코드 경계

`ugu-core`와 `ugu-session`의 얇은 의존성은 유지할 가치가 크다. `unsafe`는 Windows FFI·GPU 연동·WebP 출력 같은 경계에 주로 모여 있고 안전 조건 주석이 있다. 앱의 `EguiState`에는 수동 `Send` 구현이 있으므로 egui-winit을 갱신할 때 “AccessKit 필드가 비어 있으면 나머지는 옮겨도 된다”는 가정을 다시 확인해야 한다. 현재 버전에서 문제를 재현한 것은 아니다.

U3-09의 이미지 입력 예산을 보완하고, 새 포맷·구형 가져오기·프리셋에 대한 자원 제한 시험을 강화한다. M6의 실제 설치·연결 프로그램·업데이트·2.x 공존·합성 입력 수용 표를 채운다. 실제 펜·터치의 검증 범위는 확보된 장치와 결과에 맞춰 출시 안내에 표시한다.

### 네 번째 단계 유지보수와 선택적 성능 개선

기능이 안정된 뒤 파일 상태 전이, 렌더 replay·캐시, UI 섹션을 점진적으로 분리한다. 성능은 큰 문서·선택 이동 누적·대량 텍스트·동시 내보내기의 사용자 반응을 먼저 측정하고 그 결과로 우선순위를 정한다. 파일 길이나 새로운 GPU 백엔드의 존재만으로 재설계를 결정하지 않는다.

**현재 권고는 정식 출시 보류다.** 이유는 기능 부족이 아니라 실행으로 확인한 데이터 보존 결함과 기본 UI의 접근 문제다. 핵심 구조와 기존 회귀 시험을 유지한 채 이 경계들을 수정하면, 이미 구현된 기능과 렌더 성능을 활용해 출시 준비를 이어갈 수 있다.
