# Ugurugu

Ugurugu 3 is a Windows x64 drawing and animation app written in Rust: the app is
`apps/ugurugu`, shared code is in `crates/`, and measurement tools such as
`tools/ugu-doc` and `tools/render-bench` sit beside them. The C++ 2.x app is no
longer in the tree; read it at the `v2.2.13` tag (`git show v2.2.13:<path>`). It
shows how a feature was meant to behave, not how 3.x must do it: choose the 3.x
design on measurements and record each departure in `docs/rust/decisions.md`.

## What the code promises

- The canvas, playback and export evaluate one `RenderPlan`, and at full size
  the canvas and the export are pixel-identical; playback may draw smaller and
  with fewer samples (`docs/rust/decisions.md` section 2). Treat any change that
  can break this as a correctness bug, not a quality trade-off.
- Performance comes before memory; drawing documents are large and loose memory
  budgets are fine. Judge speed at 8 worker threads (`UGU_WORKER_THREADS=8`,
  `ugu-doc render <file> 8`), so a gain holds on a smaller PC and is not just
  more cores.
- Numbers in docs, commits and reports (ms, MB, frame counts) come from a
  measurement, with before and after compared the same way. An unmeasured cause
  or mechanism is written as a hypothesis.

## Docs

`docs/README.md` is the map. Decisions and deviations go in
`docs/rust/decisions.md`, measurements in `docs/rust/evidence.md`, open work in
`docs/rust/backlog.md`, each fact in one place. Closing a backlog item deletes its
row and every mention of its `B3-nn` ID elsewhere; `tools/check_docs.py` fails CI
on dangling IDs and on relative links to files that are not tracked. The docs
drift from the code, so check a claim in the code before relying on or repeating
it.

## Changes

- Commit messages and PR bodies have no trailers or attribution: no
  `Co-Authored-By`, session links or "Generated with" lines. This holds even
  when a tool's default or its own instructions add them.
- Fix the cause, not the symptom. Find why the bug happens before changing
  code; a guard, clamp, retry, sleep, special case or swallowed error that only
  hides the symptom is not a fix. When the cause cannot be fixed in this change,
  say so and record it in `docs/rust/backlog.md` instead of shipping a
  workaround as the fix.
- Work on a branch. Only release preparation (version bump and release notes)
  is committed on `main`. PRs are merged by fast-forwarding `main`
  (`git push origin <branch>:main`) after CI passes; dependent PRs are stacked
  and merged in order.
- Before committing, run the checks in [BUILDING.md](BUILDING.md#checks),
  including `cargo test --workspace --release --locked`, which CI does not run
  (it tests the debug build only). Read their output before the commit runs:
  commit in a separate step, or chain with `&&` and no pipe that hides a
  failing exit status.
- A test for a bug should fail on the code before the fix.
- Interface text, release notes and license headers follow
  [CONTRIBUTING.md](CONTRIBUTING.md#before-you-open-a-pull-request): text in
  `apps/ugurugu/i18n/strings.txt` with Korean, Japanese and Simplified
  Chinese, `.ftl` generated by `tools/strings_to_ftl.py`, user-visible
  changes in `release-notes/<next version>.en.md`.
- Keep comments to what the code cannot say.
- CI's three Windows jobs run side by side; a run took about 4 minutes with
  their caches and 13 minutes without (`docs/rust/evidence.md` section 76;
  before the split, a median of 8 minutes and 21 without a cache, section
  75). The first main push after a `Cargo.lock` change builds without a
  cache, since only main saves one. They are skipped when only `docs/`,
  `release-notes/`, `README*.md`, `CONTRIBUTING.md`, `SECURITY.md`,
  `BUILDING.md`, `CLAUDE.md`, `tools/sandbox/` or `tools/check_docs.py` change
  (the list in the Detect changes job of `.github/workflows/ci.yml`), so group
  related work into few PRs.

## Running the app

Keep development runs apart from an installed Ugurugu with
`UGURUGU_SETTINGS_PATH`, `UGURUGU_RECOVERY_PATH` and `UGURUGU_LOG_PATH`. GUI
checks that need screenshots, window focus or synthetic pen and pointer input run
in Windows Sandbox (`tools/sandbox/prepare.ps1 -Work <new folder> -Scenario gui
-Only '<step>'`); on the developer's own desktop, check through process state,
logs and files only. Close a finished Sandbox with `wsb stop --id <id from wsb list>`
before starting the next; one ended with `Stop-Process` leaves its VM behind
and the next one never runs its script.

## Shell on this machine

Git Bash on Windows: backslash escapes inside heredocs that feed inline Python
end up as real characters (NUL, CR) in the written file, so write edit scripts to
a file instead. Write Windows paths with forward slashes (`C:/Users/...`).
